# 01. 고객 요구사항 (RQ) — 화면 시나리오 · 수용 기준

> 근거 보드: `docs/screens/webapp1/` 의 `UC_RQ`, `RQ0`, `RQ1`, `RQ1D`, `RQ1G`, `RQ2`, `RQ3`, `RQ3A`, `RQ3B`, `RQ3C`, `RQ4`, `RQ5`, `RQ6`, `RQ7`, `RQ7B` (15장 = 유스케이스 맵 1 + 화면 14)
> 공통 컴포넌트: `Sidebar`, `TopBar`, `Stepper` · 아키텍처: `docs/ARCHITECTURE.md` · 서비스 레지스트리: `config/services.yaml`
> 작성일 2026-10-06 · 이 문서가 requirements 서비스와 `web/src/features/requirements` 구현의 수용 기준이다.

## 0. 이 문서 읽는 법

- `"…"` 안의 한국어는 보드 문구 **그대로**다. 띄어쓰기 · 가운뎃점(` · `) · 화살표(`→`) · 따옴표(`'…'`, `“…”`)까지 맞춘다.
- `{…}` 는 데이터로 바뀌는 자리다. 보드에 보이는 숫자 · 회사명 · 문장(예: `5 / 9`, `E 자산운용`, `58%`)은 **예시 데이터**이고, 구조와 규칙을 따른다.
- **(제안)** 은 보드에 그려지지 않았지만 실제 구현에 필요한 동작으로, 이 문서가 정한 기본값이다. 바꾸려면 §11 열린 질문에서 결정한다.
- 모델 호출은 테스트에서 결정적으로 mock 된다. 수용 기준(§9)은 LLM 문장 내용이 아니라 구조 · 동작 · 상태를 검증한다.
- **조사 처리**: 버전 · 숫자 뒤 조사는 발음으로 고른다 — `v{n}로/으로`(3 · 6 · 10 → 으로, 그 밖 → 로; ㄹ받침 1 · 7 · 8 → 로), `v{n}을/를`(1 · 3 · 6 · 7 · 8 · 10 → 을, 2 · 4 · 5 · 9 → 를). 보드 `"v2로 저장"`. 셸 공용 `josa()` 유틸을 쓴다.

## 1. 목적과 진입점

### 1.1 목적

영업 담당자가 고객의 요청서 · 회의록 · 메일 · 메모를 넣으면 **폼 하나**(프로젝트명 · 고객사 · 최종 제안대상 · 키맨별 요구사항 · 제작자 의견, 모두 선택)로 정리하고, **심층 작성**에서 LLM이 부족한 곳을 찾아 추가 질의로 폼을 강화한 뒤, **버전이 있는 요구사항 정의서**로 저장한다. 모르는 것은 추정하지 않고 **고객에게 물을 것**으로 모으고, 나중에 고객 답변을 붙여 넣으면 바뀐 곳만 찾아 다음 버전(v2…)을 만든다. 정의서는 Storyboard · MI · 경쟁사 분석 · VP · Spec · 제안서가 함께 쓰는 출발 데이터다(홈 카드 문구: "모든 콘텐츠가 함께 써요").

## 3. 사용자 흐름

### 3.1 기본 흐름

1. **목록** — 사이드바 `"고객 요구사항"` → RQ0. `"새 요구사항"` → RQ1.
2. **입력(직접)** — RQ1에서 칸을 채운다(모두 선택). 첫 입력이 생기는 순간 자원을 만들고(`POST /v1/requirements`) URL을 `/requirements/:rqId/form` 으로 바꾼다. 이후 입력은 자동 저장(작업본, 버전 아님).
3. **입력(파일)** — 파일을 화면 어디에 끌어도(RQ1D 오버레이) 또는 `"파일 첨부"` 로 고르면 files 서비스에 올리고 `rq.fill` 잡을 시작한다(RQ1G). 칸은 채운 순서대로 보이고, 출처 배지(`PPTX`, `TXT` …)가 붙는다. 잡이 끝나면 RQ2.
4. **바로 저장** 또는 **심층 작성** 중 하나를 고른다.
   - `"바로 저장"` → 버전 `v{n}` 생성 → RQ4.
   - `"심층 작성"` → `rq.deep.analyze` 잡 → RQ3 `"보강할 곳 {n}"`.
5. **심층 작성** — RQ3에서 다룰 곳을 체크(기본 모두 체크) → `"시작"` → RQ3A/RQ3B에서 한 번에 질문 하나씩. 답에 따라 값은 바로 반영, 고객 문장은 `"이렇게 바꿀까요?"` 로 확인 후 반영, 모르면 `"모름 · 고객에게 확인"`, 넘기려면 `"건너뛰기"`. 마지막 질문이 끝나거나 `"끝내기"` → RQ3C.
6. **저장** — RQ3C `"저장"` → 버전 생성 → RQ4. RQ4에서 `"정의서 보기"`(RQ6), `"고객에게 물을 것 {n}"`(RQ5), 다음 작업(Storyboard 기본 추천 · MI · 제안서).
7. **고객 확인** — RQ5에서 물을 것을 체크하고 `"메일 문구 복사"` 로 메일을 보낸다(앱 밖).
8. **나중에** — 고객 답장이 오면 RQ5 `"답변 반영하기"` 또는 RQ6 → RQ7에 붙여 넣고 `"바뀌는 곳 찾기"` → RQ7B에서 바뀔 곳을 확인(체크) → `"v{n+1}로 저장"` → RQ6(새 버전). 이 정의서를 쓰는 Storyboard가 있으면 `"Storyboard {n}곳에도 반영"` 으로 함께 갱신한다.

### 3.2 분기

| 지점 | 조건 | 동작 |
|---|---|---|
| RQ1 `"심층 작성"` | 폼이 비어 있어도 | 허용. 빈 칸 전부가 보강할 곳이 된다(직접 인터뷰 흐름). 자원이 없으면 먼저 만든다. |

### 3.4 에이전트 라우팅 규칙 — 에이전트가 정하는 것 / 사람이 정하는 것

원칙: **정할 수 있는 것은 에이전트가 자동으로 정하고, 사람은 꼭 필요한 것만 정한다.** 고객 문서에 들어갈 문장을 새로 쓰거나 바꾸는 일은 사람이 확인하고, 값 · 배치 · 정렬은 자동이다.

| 상황 | 에이전트가 자동으로 | 사람에게 |
|---|---|---|
| 파일 → 폼 | 칸 나누기, 출처 기록, 여러 파일 중 어느 값을 쓸지(§7.2 우선순위), 키맨 이름 합치기, 항목 중복 제거, 균등 가중치 | 없음(RQ2에서 확인 · 수정) |
| 사용자가 이미 쓴 칸 | 파일 값으로 **덮어쓰지 않음**(다른 값은 `alternatives` 로 보관) | 없음 |
| 보강할 곳 찾기 | 규칙 · LLM · KB(B2)로 찾고 우선순위 · 상한(7) 적용, 질문과 선택지 생성 | 다룰 곳 체크(RQ3, 기본 모두) |
| 선택지 칩 · 직접 입력이 **값**인 질문(최종 제안대상, 가중치) | 바로 반영하고 기록 줄 `✓ {칸} → {값}` 추가 | 없음 |
| 답이 **고객 문장**을 바꾸거나 새 항목을 만듦 | 폼 문장으로 다듬어 반영 제안 + 부수 효과(고객 확인 추가) 제안 | `"반영"` / `"고치기"` |
| `"모름 · 고객에게 확인"` | 고객용 질문 문장과 짧은 이름 생성, 해당 키맨 태그, 항목에 `확인 필요` 표시 | 없음 |
| 보강할 곳 순서 | 빈 칸 → 가중치 → 영향 큰 항목 순(§10) | 없음 |
| 메일 문구 | 체크한 질문으로 문구 생성(실패 시 템플릿) | 어떤 질문을 넣을지 체크(RQ5) |
| 고객 답변 → 정의서 | 답과 질문 짝 맞추기, 바뀔 곳과 전 → 후, 근거 파일 연결, 영향받는 Storyboard 위치 계산 | 바뀔 곳 체크, Storyboard 반영 여부(RQ7B) |

### 3.5 상태

**정의서 목록 상태(파생, `list_state`)**

| `list_state` | 조건 | RQ0 상태 글 | 탭 | 행 버튼 |
|---|---|---|---|---|
| `input` | `version = 0`, 진행 중 세션 없음 | `"입력 중"` | 진행 중 | `"이어서"` → RQ2(또는 RQ1 빈 폼) |
| `filling` | 활성 `rq.fill` 잡 | `"입력 중"` | 진행 중 | `"이어서"` → RQ1G |
| `deepening` | 세션 상태 `analyzing`/`ready`/`asking` | `"심층 작성 {i} / {N}"` (i = 현재 질문 번호, 시작 전이면 1) | 진행 중 | `"이어서"` → RQ3/RQ3A |
| `editing` (제안) | `version ≥ 1` & 작업본이 최신 버전과 다름 | `"고치는 중 · v{n}"` | 진행 중 | `"이어서"` → RQ2 |

**심층 작성 세션 상태**: `analyzing`(잡 실행) → `ready`(RQ3) → `asking`(RQ3A/B) → `finished`(RQ3C) / `canceled`. 세션은 정의서마다 진행 중인 것이 최대 1개.

**보강할 곳 상태**: `pending` → (`applied` 값 반영 | `proposed` 제안 대기 → `applied` | `deferred` 고객 확인 | `skipped` 건너뜀 | `resolved_by_form` 폼에서 해결) · RQ3에서 체크 해제하면 `deselected`.

| 칸 입력 | 800ms 디바운스 자동 저장 `PATCH /v1/requirements/{id}/draft` (`set_field`). 저장 표시는 없음(보드에 없음). |
| `"+ 요구사항"`(키맨 카드 안, 왼쪽 들여쓰기 38px) | 그 키맨 아래 요구사항 입력 줄 추가(숨김 라벨 `"요구사항 {n}"`), 포커스 이동 |

| `"심층 작성"` | 자원 없으면 생성 → `POST /v1/requirements/{id}/deep-sessions` → RQ3(분석 중 로딩) |

**상태**: 빈 상태(보드 그대로) · 자원 생성 중(입력 막지 않음, 생성 응답 뒤 쌓인 입력을 한 번에 PATCH) · 자동 저장 실패 시 토스트 + 3회 재시도.

**버전 · 내보내기**: 없음(작업본만).

### 4.4 `RQ1D` — 1 입력 · 파일 끌어다 놓기

**상태 정의**: RQ1 · RQ2 화면에서 `dragenter`(파일 포함)일 때 본문 섹션 전체(위 24 · 좌 40 · 우 40 · 아래 24 여백)를 덮는 오버레이. `role="region"`, `aria-label="여기에 놓기"`.

**표시**

- 파란 점선(2px `#1428a0`) + 반투명 배경 `rgba(234, 238, 251, 0.9)`.
- 큰 아이콘 + `"놓으면 폼을 채워요"` + `"파일 {n}개"`(드래그 중인 파일 수, `DataTransfer.items` 길이).
- 커서 옆 파일 칩 미리보기: 형식 배지(`PPTX`, `TXT` …) + 파일 이름(예: `"제안지원요청서_용산 업무시설 재개발.pptx"`, `"고객 미팅 메모_11월 4일.txt"`). 브라우저가 이름을 주지 않으면 개수만.

**동작**

| 이벤트 | 동작 |
|---|---|
| `dragleave`(창 밖) · Esc | 오버레이 닫기 |
| `drop` | ① 지원 형식 거르기(§10) — 지원 안 하는 파일은 토스트 (제안) `"PPTX · PDF · DOCX · TXT · 메일만 넣을 수 있어요"` ② 자원 없으면 생성 ③ 파일마다 `POST /api/files/v1/files`(multipart) ④ 업로드 끝난 `file_id` 들로 `POST /v1/requirements/{id}/files` → `202 {job_id}` ⑤ RQ1G 상태 |
| 이미 채워진 폼(RQ2)에 놓기 | 같은 흐름. 새 파일만 읽고 기존 값에 합친다(§7.2 병합 규칙). |

**메일 파일(.eml/.msg)**: 본문과 첨부를 files 서비스가 풀고, 지원 형식 첨부는 같은 채우기 잡에 함께 들어간다. 출처 배지는 본문 `메일`, 첨부는 각 형식.

### 4.5 `RQ1G` — 1 입력 · 폼 채우는 중

**라우트** `/requirements/:rqId/form`, 자원의 `active_job.kind = "rq.fill"`. TopBar `title` 은 제목이 생기기 전까지 `"새 요구사항"`.

**파일 줄**(드롭존이 52px 줄로 접힘, 점선 `#c9d0e6`)

| 요소 | 내용 |
|---|---|
| 업로드 아이콘 | — |
| 파일 칩 | 형식 배지 + 이름(넘치면 말줄임) + 상태: **완료** = 파란 원 안 체크, **읽는 중** = 회전 원(`role="status"`, `aria-label="읽는 중"`), **실패** (제안) = 빨간 느낌표 + 툴팁 `"읽지 못했어요"` + 칩 클릭 시 `"다시 시도"` |
| 진행 | `"채우는 중"` + 막대(120px, 채운 비율) + `"{filled} / {total}"`(예: `"5 / 9"`) |

`filled` = 지금까지 채운 칸 수, `total` = 채울 예정 칸 수(§7.2 `plan_slots`). 나중 파일을 읽으며 `total` 이 늘 수 있지만 `filled` 아래로 줄지 않는다.

**폼**

- 채운 칸: 값 + 오른쪽 출처 배지(`PPTX` …), 배경 `#f5f7fe`(이번 잡에서 막 채운 칸 강조). 잡이 끝나면 흰 배경(RQ2).
- 아직 안 채운 칸: 회색 스켈레톤 막대(`aria-busy="true"`). 끝까지 못 찾은 칸은 잡 종료 후 빈 입력(placeholder)으로 돌아간다(RQ2의 `"최종 제안대상"` 처럼).
- 오른쪽: `"키맨별 요구사항"` + `"{n}명"`(예: `"2명"`) + `"+ 키맨"` · 키맨 2명 이상이면 가중치 줄 · 키맨 카드마다 항목 줄(번호 + 문장 + 출처 배지) 또는 스켈레톤 줄(폭 62% / 44% 번갈아).
- 키맨이 발견되면 균등 가중치(2명 → `50` / `50`)와 `"균등"` 배지.

**버튼**: `"바로 저장"` 활성(§3.2: 채우기 끝난 뒤 저장), `"심층 작성"` 비활성(`aria-disabled="true"`, `opacity: 0.4`, `pointer-events: none`).

**사용자 입력**: 채우는 중에도 칸 입력 가능. 사용자가 입력한 칸은 잡이 덮어쓰지 않는다.

**종료**: SSE `done` → 자원 재조회 → RQ2(같은 라우트). 일부 파일 실패: 나머지 결과는 반영, 실패 칩 표시. 전체 실패: 토스트 + 파일 칩 실패 상태, 폼은 그대로.

### 4.6 `RQ2` — 1 입력 · 채워진 폼 (출처 · 가중치)

**라우트** `/requirements/:rqId/form`. TopBar · Sidebar `current` = 제목(예: `"E 자산운용 용산 AI Ready 오피스"`). Stepper `current=1`.

**파일 줄**: 칩마다 `"빼기"` 버튼(×, `aria-label="빼기"`) · 오른쪽 `"파일 첨부"`.

**왼쪽 카드**

| 칸 | 값 예 | 타입 | 출처 | 배지 |
|---|---|---|---|---|
| 프로젝트명 | `"용산 업무시설 재개발 AI Ready 오피스"` | string | 파일 추출 | `PPTX` |
| 고객사 | `"E 자산운용"` | string | 파일 추출 | `PPTX` |
| 최종 제안대상 | 빈 칸(placeholder `"예) 대표이사"`) | string \| null | — | 없음 |
| 제작자 의견 | `"설계 단계 스펙인이 목표. 성수 오피스 대비 '최초 AI Ready'를 강조."` | string | 파일 추출(메모) | `TXT`(textarea 오른쪽 아래) |

**출처 배지 규칙**

- `source.kind = file` 이면 배지 = 파일 형식 라벨. 마우스를 올리면 (제안) 툴팁 `"{파일 이름} · {위치}"` + 원문 근거 문장(`quote`).
- 사용자가 값을 고치면 `source.kind = user` 가 되고 배지가 사라진다(원래 출처는 `derived_from` 에 남김).
- 심층 작성 · 고객 답변으로 바뀐 값은 배지 없음(`source.kind = deep | reply`).

**오른쪽 카드 — 키맨별 요구사항**

| 요소 | 내용 · 동작 |
|---|---|
| 머리 | `"키맨별 요구사항"` + `"{n}명"`(Manrope, `#1428a0`) + `"+ 키맨"` |
| 가중치 줄(키맨 ≥ 2) | `"가중치"` + 분할 막대(`role="group"`, `aria-label="키맨 가중치 · 경계를 끌어서 조정"`): 조각 너비 = 가중치, 안에 `"{w}%"`, 키맨 색. 기본 균등이면 `"균등"` 배지 |
| 막대 경계 끌기 | 이웃한 두 키맨 사이 가중치를 1% 단위로 옮김, 각 최소 5%. 놓으면 `set_weights` 저장, `weights_mode = custom`, `"균등"` 사라짐 |
| 키맨 카드 머리 | 아바타(첫 글자, 키맨 색) · 이름 · 가중치 스테퍼(− `{w}%` +, `aria-label="{이름} 가중치 낮추기"` / `"{이름} 가중치 높이기"`, 키맨 ≥ 2일 때만) · `"+ 요구사항"` |
| − / + | 5 단위로 맞춰 이동(+: 다음 5의 배수, 예 34 → 35 → 40; −: 이전 5의 배수, 예 34 → 30). 바뀐 만큼 나머지 키맨에서 현재 비율대로 빼거나 더함(최대 나머지 반올림, 각 ≥ 5, 합 100). `weights_mode = custom` |
| 요구사항 줄 | 번호(Manrope 회색) · 문장(넘치면 말줄임) · 출처 배지. 문장 클릭 → 그 자리 입력으로 바뀌어 수정, Enter/blur 저장, Esc 취소 (제안) |
| 줄 삭제 · 키맨 삭제 | 보드 없음. (제안) 줄에 마우스를 올리면 `×`(`aria-label="요구사항 삭제"`), 키맨 머리에 `⋯` 메뉴 `"키맨 삭제"`. 삭제 후 가중치: 균등 모드면 다시 균등, custom이면 남은 키맨에 비율대로 나눔 |
| 키맨 이름 | 클릭해 수정 (제안) |

**예시 데이터(보드)**: 대표이사 34%(3) — `"사용자를 인식하고 반응하는 'AI Ready' 오피스"` `PPTX`, `"'최초 AI Ready' 공간으로 알리기"` `PPTX`, `"에너지 절감 · 정량 데이터 확보"` `TXT` · 공간컨텐츠실장 33%(3) — `"오피스를 업무환경 플랫폼으로"` `PPTX`, `"예측 · 반응형 공간 (Connecting-AI)"` `TXT`, `"건물 가치 · 임대 선호도 제고"` `TXT` · 개발사업팀장 33%(1) — `"AI 인프라를 설계 단계에 미리 반영"` `TXT`.

**파일 `"빼기"`**: `DELETE /v1/requirements/{id}/files/{file_id}?rollback=true` — 그 파일에서 와서 **아직 사람이 고치지 않은** 값 · 항목 · 키맨을 지운다(사람이 고친 값은 남김). 가중치는 규칙대로 다시 맞춘다. (제안) 토스트 `"파일을 뺐어요"` + `"되돌리기"`(5초, `POST .../files` 로 다시 붙이되 재추출 없이 스냅숏 복원).

**버튼**: `"바로 저장"` → `POST save` → RQ4 · `"심층 작성"` → 진행 중 세션이 있으면 그 세션, 없으면 새 분석 → RQ3.

**레이아웃 전환 규칙**: 키맨이 하나도 없거나 이름 · 항목이 모두 빈 키맨 1개뿐이면 RQ1의 입력형 카드, 그 밖에는 RQ2의 목록형 카드.

| `empty_field`(최종 제안대상 · 고객사 · 프로젝트명) | **바로 반영** — 값 저장(`source.kind = deep`), 기록 줄 `✓ {칸} → {값}`, 다음 질문 |
| `default_weights` | 선택지는 LLM이 만든 배분안(예 `"대표이사 50 · 공간컨텐츠실장 30 · 개발사업팀장 20"`, `"균등 유지"`) + 직접 조정 (제안: 입력부 위에 키맨별 − / + 편집기, `"반영"`). 고르면 **바로 반영**, 기록 줄 `✓ 가중치 → 50 · 30 · 20` |
| 항목 · 키맨 종류(`unquantified`, `vague_scope`, `too_few_items` …) | **반영 제안**(RQ3B) — 사람 확인 후 반영 |

**보내는 중**: (제안) 에이전트 말풍선 자리에 점 세 개 애니메이션, 입력부 잠금. 30초 넘으면 `504 LLM_TIMEOUT` → 토스트 + 답을 입력창에 되돌림.

**폼 패널**(오른쪽)

| 요소 | 내용 |
|---|---|
| 머리 | `"폼"` + `"열기"`(→ RQ2) |
| `"프로젝트명"`, `"고객사"`, `"최종 제안대상"`, `"제작자 의견"` | 작은 라벨(11.5px 회색) + 값(13.5px, 한 줄 말줄임). 빈 값은 `"—"`(회색 `#a3a9b5`) |
| `"가중치"` | 작은 분할 막대(높이 18), 숫자만(예 `34` `33` `33`) |
| 키맨 줄 | 아바타(20px) · 이름 · `"{w}% · {항목 수}"`(예 `"34% · 3"`). 키맨 1명이면 `"{항목 수}"` 만 (제안) |

### 4.9 `RQ3B` — 2 심층 작성 · 질의 3/5 구체화 → 반영

같은 라우트, 세션에 `pending_proposal` 이 있는 상태. 대화 본문은 아래로 붙는다(`justify-content: flex-end`).

**기록 줄**(이전 반영 결과, 높이 32, 배경 `#f5f6f8`): 체크 아이콘 + **칸 이름**(굵게) + `"→ {값}"`. 보드 예: `"최종 제안대상"` `"→ 대표이사"`, `"가중치"` `"→ 50 · 30 · 20"`. (제안) 고객 확인으로 보낸 것은 `"고객 확인"` 칩 + 짧은 이름, 건너뛴 것은 `"건너뜀 · {주제}"`.

**말풍선**: 에이전트 질문 `"'에너지 절감'의 목표 수치가 있나요?"` → 사용자 답(오른쪽 파란 말풍선, 흰 글자) `"유사 건물 대비 20%. 실측 데이터로 보여 주길 원해요"`.

**반영 제안 카드**(테두리 1.5px `#1428a0`, 아바타 `W`)

| 요소 | 내용 |
|---|---|
| 머리 | `"이렇게 바꿀까요?"` (파랑 13px 굵게) |
| 전 | 회색 취소선 — `"에너지 절감 · 정량 데이터 확보"` (항목 추가 제안이면 전 줄 없음 + `"추가"` 배지) |
| 후 | 15.5px 굵게 — `"에너지 사용량 20% 절감 (유사 건물 대비) · 실측 데이터로 증빙"` |
| 부수 효과 체크박스(기본 체크) | `"고객 확인에 '유사 건물 사용량 자료' 추가"` — 체크된 채 반영하면 고객 질문 생성(§5.6, `origin.kind = deep_side_effect`) |
| `"반영"` | `POST .../proposals/{pid}/accept {side_effects}` → 작업본 반영, 기록 줄 추가, 다음 질문 |
| `"고치기"` | 후 문장이 그 자리 textarea로 바뀜 + (제안) `"반영"` · `"취소"`. 고친 문장으로 accept(`edited_text`) |
| 제안 대기 중 입력창 전송 | 고칠 지시로 보고 `POST .../proposals/{pid}/revise {instruction}` → 새 제안으로 교체 |

**폼 패널(제안 대기)**: 질문 대상 키맨(대표이사)을 펼쳐 항목을 보여 주고, 바뀔 항목 자리에 점선 상자(`1.5px dashed #1428a0`, 배경 `#f5f7fe`) — 전(회색 취소선, 11.5px) / 후(파랑 12.5px). 반영 전까지 작업본은 바뀌지 않는다. 반영된 칸(최종 제안대상 `"대표이사"`, 가중치)은 체크 아이콘. 다른 키맨은 접힌 `"30% · 3"`, `"20% · 1"`.

**마지막 질문 처리 후**: 자동으로 `POST .../finish` → RQ3C.

| `"뒤로"` (←) | RQ7 (붙여 넣은 글 유지) |
| `"v{n+1}로 저장"` (→, 주 버튼) | `POST .../replies/{rid}/apply {selected_change_ids, propagate: ["storyboard"]?}` → 새 버전 → RQ6. 체크 0이면 비활성 |

**변경 종류**(§5.7): 항목 문장 바꿈(`업무환경 플랫폼` → 구체 서비스), 근거 자료 붙임(`근거 자료 없음` → 파일 이름), 칸 값 바꿈(`최종 제안대상`), 새 항목, 가중치. 답이 고객 질문에 대응하면 반영 시 그 질문은 `answered`, 연결 항목의 `확인 필요` 해제.

**`"미리 보기"`**: Storyboard 버전 비교(SB3V)를 미리 보기 모드로 연다 — `/storyboard/{sb_id}/versions?preview_rq={rq_id}&reply={reply_id}` (Storyboard가 `dry_run` 동기화 잡으로 계산, 02-storyboard.md §4 SB3V). 이어진 Storyboard가 여럿이면 (제안) 작은 메뉴로 고른다.

**Storyboard 반영 실행**: 저장 응답의 `pending_sync_links` 마다 웹 모듈이 `POST /api/storyboard/v1/storyboards/{sb_id}/requirement-sync {requirement_id, to_version}` 를 호출(응답 202, 기다리지 않음). 실패해도 Storyboard가 다음에 열릴 때 링크의 `sync_state = pending` 을 보고 스스로 동기화한다(§8.4).

### 5.9 `RequirementVersion` — 저장 스냅숏(불변)

`{version, created_at, created_by, reason: "direct"|"deep"|"edit"|"reply"|"restore", note?, summary: "키맨 3 · 요구사항 8", snapshot: {form, context, items_flat: [{id, code, text, short, keyman_id, keyman_name, needs_confirmation, evidence, entities}], customer_questions: [{id, text, short_label, status, keyman_id, target}], source_files: [{file_id, name, type_label}]}, change_count}`

- 저장은 작업본이 최신 버전과 다를 때만 새 버전(같으면 `created: false`, 버전 그대로).
- 되돌리기(restore)는 옛 스냅숏을 **새 버전**으로 복사하고 작업본도 바꾼다. 역사는 다시 쓰지 않는다.
- 스냅숏의 `author_note` 는 내부용 표시(`internal: true`)와 함께 저장 — 소비자는 고객용 산출물에 넣지 않는다.

## 6. API 스케치 (서비스 내부 `/v1`, 게이트웨이 `/api/requirements/v1`)

공통: ID `<접두사>_<ULID>`, 시간 ISO 8601 UTC, 오류 `{"error": {"code", "message"(한국어), "details"}}`, 목록 `{items, next_cursor}`, 오래 걸리는 작업 `202 {"job_id", "status": "queued"}` (+ 이 기능은 편의상 `ref` 도 함께 돌려줌). 모든 ai-tools 호출에 `confidential: true`.

### 6.1 정의서

| 메서드 · 경로 | 요청 | 응답 | 비고 |
|---|---|---|---|
| `POST /v1/requirements` | `{project_id?: string, form?: Partial<Form>}` | `201 Requirement` | RQ1 첫 입력, RQ1 심층 작성, 파일 놓기 |
| `GET /v1/requirements` | `?tab=all\|in_progress\|saved&q=&has_version=bool&limit=20&cursor=` | `200 {items: RequirementListItem[], next_cursor}` | RQ0, SB1(`has_version=true`), CA1R |
| `GET /v1/requirements/counts` | `?q=` | `200 {all: int, in_progress: int, saved: int}` | RQ0 탭 |
| `GET /v1/requirements/{id}` | — | `200 Requirement` | |
| `PATCH /v1/requirements/{id}/draft` | `{base_revision: int, ops: DraftOp[]}` | `200 Requirement` | 자동 저장 · 모든 폼 편집 |
| `POST /v1/requirements/{id}/save` | `{reason?: "direct"\|"deep"\|"edit", note?: string}` | `201 {version, created: true, requirement}` / `200 {version, created: false}` | `409 JOB_RUNNING`, `422 EMPTY_FORM` |
| `POST /v1/requirements/{id}/share` | — | `200 {url}` | (제안) workspace 공유 링크 |

`RequirementListItem`: `{id, title, customer_name, project_name, list_state, state_label, version, keyman_count, item_count, open_question_count, updated_at, saved_at, route, active_deep: {current_index, total}?}`

### 6.2 파일로 채우기

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `POST /v1/requirements/{id}/files` | `{file_ids: string[]}` (files 서비스에 이미 올린 것) | `202 {job_id, status: "queued", ref: {kind: "requirement", id}}` — 잡 `rq.fill` |
| `DELETE /v1/requirements/{id}/files/{file_id}` | `?rollback=true\|false` | `200 Requirement` |

오류: `422 UNSUPPORTED_FILE_TYPE`(details: 파일 이름 · 형식), `404 FILE_NOT_FOUND`. 이미 채우는 중에 파일을 더 놓으면 오류가 아니라 `202` 로 새 `rq.fill` 잡을 큐에 넣고 앞 잡이 끝난 뒤 순서대로 실행한다(제안). 자원의 `active_job` 은 지금 실행 중인 잡, 대기 잡은 `queued_jobs` 로 보인다.

**SSE 이벤트(잡 `rq.fill`)** — `data` 형태:
- `step` `{key: "file:{file_id}", label: "{파일 이름}", state: "reading"|"done"|"failed"}`
- `progress` `{ratio: 0..1, filled: int, total: int}` — 받을 때마다 자원 재조회
- `result` `{ref: {kind: "requirement", id}}` · `error` `{code, message}` · `done`

### 6.3 작업본 편집 ops (`DraftOp`)

| op | 필드 | 규칙 |
|---|---|---|
| `set_field` | `field: "project_name"\|"customer_name"\|"final_audience"\|"author_note"`, `value: string\|null` | 사용자 값은 `source.kind=user` |
| `add_keyman` | `keyman_id?`(클라이언트 생성 ULID 허용), `name`, `after_keyman_id?` | 균등 모드면 재균등 |
| `update_keyman` | `keyman_id`, `name` | |
| `remove_keyman` | `keyman_id` | 가중치 재분배 |
| `set_weights` | `weights: {km_id: int}` | 합 100, 각 ≥ 5 아니면 `422 WEIGHTS_SUM_INVALID` / `WEIGHT_MIN`. `weights_mode=custom` |
| `reset_weights_equal` | — | `weights_mode=equal_default` |
| `add_item` | `keyman_id`, `item_id?`, `text`, `after_item_id?` | 새 `code` 부여 |
| `update_item` | `item_id`, `text` | `source.kind=user`, `short` 는 비동기로 다시 만듦 |
| `remove_item` | `item_id` | code는 재사용 안 함 |
| `move_item` | `item_id`, `keyman_id`, `index` | (제안) 끌어 옮기기 |

충돌: 다른 쓰기(잡 · 다른 탭)가 `base_revision` 이후 같은 대상을 바꿨으면 `409 REVISION_CONFLICT` + `details.current` (클라이언트는 다시 읽고 사용자의 최근 입력을 다시 적용). 대상이 사라졌으면 그 op만 무시하고 `details.skipped_ops` 로 알림.

### 6.4 심층 작성 — **결정: 분석은 202 잡, 질의응답은 동기 REST**

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `POST /v1/requirements/{id}/deep-sessions` | — | `202 {job_id, status, ref: {kind: "deep_session", id: "ds_…"}}` (잡 `rq.deep.analyze`) · 진행 중 세션이 있으면 `409 SESSION_ACTIVE {details: {session_id}}` · 채우는 중이면 `409 JOB_RUNNING` |

**왜 awaiting_input 잡이 아닌가**
1. 세션은 며칠 이어진다(RQ0 `"심층 작성 3 / 5"` → `"이어서"`). awaiting_input 잡을 그동안 열어 두면 잡 레코드 · 체크포인트 수명 관리가 jobs 서비스 부담이 되고, 재시작 · 만료 처리가 복잡해진다.
2. 질의 중에 사용자가 `"열기"` 로 폼을 직접 고칠 수 있다. 그래프 안 상태와 작업본이 갈라지지 않도록 세션 상태를 requirements DB 한 곳에 둔다.
3. 답 하나 처리는 LLM 한 번(문장 다듬기) 이하라 수 초 안에 끝난다 — 큐 · SSE 왕복이 오히려 느리다. 값 답(칩)은 LLM 없이 즉시.
4. 무거운 부분(보강할 곳 찾기: 전체 문서 · LLM · KB)만 202 잡으로 두어 §3 "오래 걸리는 작업" 규약을 지킨다.
5. mock LLM으로 질의 하나하나를 API 테스트하기 쉽다(§9).
답 처리 그래프(`rq_deep_answer`)는 API 프로세스 안에서 LangGraph로 동기 실행한다(큐 없음, 30초 타임아웃).

## 7. 워크플로 (LangGraph)

모든 그래프: 워커가 `wm:q:requirements` 에서 꺼내 실행, 체크포인터는 `${DATA_DIR}/requirements/` 의 SQLite, `thread_id = job_id`. 노드 경계에서 취소 플래그(`wm:job:<id>:cancel`) 확인. LLM은 ai-tools **JSON 스키마 응답**, 고객 자료가 들어가므로 `confidential: true`. **웹 검색은 쓰지 않는다** — 정의서는 고객 자료와 사용자 답에서만 나온다.

**7.2.1 병합 규칙(결정적)**
1. `source.kind ∈ {user, deep, reply}` 인 값은 덮어쓰지 않는다. 다른 값은 `alternatives` 에 보관.
2. 같은 칸을 여러 파일이 주면 문서 종류 우선순위 `rfp` > `mail` > `meeting_memo` > `other`(프로젝트명 · 고객사 · 최종 제안대상), 같으면 먼저 놓은 파일.
3. 최종 제안대상은 문서에 **명시**된 경우만(추론 금지).
4. 제작자 의견: 비어 있을 때만 채움. 후보가 여럿이면 `meeting_memo` 우선, 여러 문장은 한 문단으로. 영업 목표 · 내부 전략 문장(예 "스펙인이 목표")은 고객 요구가 아니라 제작자 의견으로 분류(LLM 규칙).
5. 키맨: 정규화 이름이 같으면 합치고 항목을 덧붙임(중복 제거). 새 키맨은 파일 순서대로 뒤에.
6. 가중치: `equal_default` 면 다시 균등(내림 + 앞에서부터 나머지 1씩: 3명 `34/33/33`, 2명 `50/50`). `custom` 이면 새 키맨에 `floor(100/n)` 을 주고 나머지를 비율대로 줄임(최대 나머지 반올림, 각 ≥ 5). 문서에 가중치 근거가 있어도 자동 적용하지 않고 `alternatives` 로만 둔다(가중치는 심층 작성에서 정함).

**7.3.1 완성도(결정적)**
검사 항목: 프로젝트명 · 고객사 · 최종 제안대상 채움(각 1), 키맨 ≥ 1(1), 키맨 ≥ 2면 가중치 확정(1), 키맨마다 항목 ≥ 2(키맨당 1), 항목마다 LLM 보강할 곳 없음(항목당 1).
`completeness = round(100 × (충족 + 0.5 × 고객 확인으로 넘긴 것) / 적용 항목 수)`. 질의 중 반영할 때마다 다시 계산. 보드 `58% → 86%` 는 예시 값.

### 8.2 이 서비스를 호출하는 것

| 호출자 | 무엇 |
|---|---|
| Storyboard | 목록(`has_version=true`) · 버전 스냅숏 · diff · 고객 질문 추가 · 링크 등록 · 답변 분석 읽기(미리 보기) |

### 8.3 소비자가 쓰는 필드(계약으로 유지할 것)

스냅숏(`GET /versions/{n}`)의 `form.project_name`, `form.customer_name`, `form.final_audience`, `form.keymen[].{name, weight, color_index}`, `items_flat[].{id, code, text, short, keyman_id, needs_confirmation, evidence, entities}`, `form.author_note`(**internal**), `context.{vertical, spaces, products, solutions, scale_text, deadline_text}`, `customer_questions[]`, `source_files[]`, `open_question_count`. Storyboard SB1 줄 `"요구 {n}개 · 확인 필요 {m}개 · {시각} 저장"` = `item_count` · `open_question_count` · `saved_at`. 경쟁사 CA1R `"정의서에서 채운 것"`(고객사 · 업종 · 장소 · 제품) = `customer_name` · `context.vertical` · `context.spaces` · `context.products`.

### 8.4 Storyboard가 정의서에서 받는 것(요약, 상세는 02-storyboard.md §8)

1. SB1: 저장된 정의서 목록과 최신 버전.
2. 전 단계: 선택 버전 스냅숏(항목 code · short · entities, 키맨 · 가중치, 최종 제안대상, 제작자 의견 = 내부 목표 판별용, 열린 고객 질문).
3. Storyboard → 정의서 쓰기: 고객 질문 추가(SB3S `"모르겠어요 → 고객에게 묻기"`, SB3S2 자동 추가, SB4U), 링크 `depends_on` 갱신.
4. 정의서 새 버전 반영: 링크 `sync_state=pending` → 웹이 즉시 호출 / Storyboard가 열릴 때 확인해 `requirement-sync` 잡 실행 → 다시 등록해 `up_to_date`.

### 8.5 프로젝트

첫 저장(v1) 때 `project_id` 가 없으면 workspace에 프로젝트를 만든다(`{name: project_name ?? title, customer: customer_name}`). 이 정의서에서 시작한 다른 작업은 같은 `project_id` 를 이어 쓴다.

## 9. 수용 기준

모델 호출(ai-tools)과 kb는 결정적 mock. 각 기준은 API 테스트(`services/requirements/tests`) 또는 Playwright E2E(`web/e2e/requirements.spec.ts`)로 검증한다.

### 9.1 API

1. **생성** — Given 정의서 없음, When `POST /v1/requirements {}`, Then `201`, `id` 가 `^rq_[0-9A-HJKMNP-TV-Z]{26}$`, `version=0`, `list_state="input"`, 폼 값 모두 null, `keymen=[]`; workspace mock에 `PUT /items/{id}` 1회(`feature="RQ"`, `route="/requirements/{id}/form"`).
2. **자동 저장** — Given 정의서, When `PATCH draft {ops:[set_field project_name "A"]}`, Then `200`, `revision` +1, `form.project_name.value="A"`, `source.kind="user"`.
3. **균등 가중치** — When 키맨 2명 추가, Then 가중치 `[50,50]`, `weights_mode="equal_default"`; 3명째 추가 Then `[34,33,33]`; 1명만 남기면 `100`.
4. **가중치 검증** — When `set_weights` 합 99, Then `422 WEIGHTS_SUM_INVALID`; 한 명 3, Then `422 WEIGHT_MIN`; 합 100 · 각 ≥ 5, Then `200`, `weights_mode="custom"`.
5. **스테퍼 재분배** — Given `[34,33,33]` custom, When 웹 규칙으로 첫 키맨 + (→ 35) 계산 후 `set_weights`, Then 합 100, 나머지 각 ≥ 5(웹 단위 테스트 포함).
6. **파일 채우기** — Given PPTX·TXT `file_id` 2개(mock 파싱), When `POST files`, Then `202 {job_id}`; SSE에 파일별 `step`(`reading`→`done`) 2쌍, `progress.filled` 가 줄지 않고 마지막에 `filled = total`, 이어 `done`; 결과 프로젝트명 · 고객사 `source.kind="file"`, `file_label="PPTX"`, 제작자 의견 `file_label="TXT"`.
7. **사람 값 보호** — Given 사용자가 프로젝트명 `"직접 입력"`, When 다른 이름이 든 파일을 채우면, Then 값 `"직접 입력"` · `source.kind="user"` 유지, 파일 값은 `alternatives` 에.
8. **지원 형식** — When `.xlsx` file_id로 `POST files`, Then `422 UNSUPPORTED_FILE_TYPE`.
9. **파일 빼기** — Given 파일 A에서 온 항목 2개 중 1개를 사용자가 고침, When `DELETE files/A?rollback=true`, Then 고치지 않은 항목만 사라지고 고친 항목은 남음; 키맨이 비면 제거 · 가중치 재균등.
10. **채우는 중 막기** — Given 활성 `rq.fill`, When `POST deep-sessions`, Then `409 JOB_RUNNING`; When `POST save`, Then `409 JOB_RUNNING`.
11. **보강할 곳 분석** — Given 최종 제안대상 비어 있음 · 키맨 3명 균등 · 한 키맨 항목 1개 · mock LLM이 항목 2개에 `unquantified`·`vague_scope`, When `POST deep-sessions` 후 잡 완료, Then 세션 `ready`, 보강할 곳 5개, 순서 첫째 `empty_field(final_audience)`, 둘째 `default_weights`, 모든 `problem` ≤ 24자, `0 ≤ completeness ≤ 100`.
12. **상한** — Given mock LLM이 보강할 곳 12개를 냄, Then 세션 보강할 곳 ≤ 7.
13. **세션 하나** — Given 진행 중 세션, When `POST deep-sessions`, Then `409 SESSION_ACTIVE`, `details.session_id` = 그 세션.
14. **값 답 즉시 반영** — Given 현재 보강할 곳 `final_audience`, When `answers {kind:"option", option_id: "대표이사"}`, Then `outcome="applied"`, 작업본 최종 제안대상 `"대표이사"`·`source.kind="deep"`, `log_entry` = `{label:"최종 제안대상", value_display:"대표이사"}`, `current_index` +1.
15. **문장 답은 제안** — Given 현재 `unquantified` 항목, When `answers {kind:"text", text:"유사 건물 대비 20%…"}`, Then `outcome="proposal"`, `proposal.before_text` = 원 항목 문장, 작업본 항목 **불변**; 이어서 `accept {side_effects:[{id, checked:true}]}`, Then 항목 문장 = `after_text`, 고객 질문 1개 생성(`origin.kind="deep_side_effect"`).
16. **제안 대기 중 다른 답 금지** — Given 제안 대기, When 다음 보강할 곳 `answers`, Then `409 PROPOSAL_PENDING`.
17. **숫자 가드** — Given mock LLM 재작성이 답에 없는 숫자 `"30%"` 를 넣음, Then 결과 제안 문장에 `30` 없음.
18. **모름** — When `answers {kind:"unknown"}` (대상 항목), Then `outcome="deferred"`, 고객 질문 `open` · `keyman_id` = 그 키맨 · `target.id` = 항목, 항목 `needs_confirmation=true`, `open_question_count` +1.
19. **건너뛰기** — When `skip`, Then 보강할 곳 `skipped`, 작업본 `revision` 불변.
20. **폼에서 해결** — Given `asking` 세션 · 보강할 곳 `empty_field(customer_name)` 대기, When 폼에서 고객사 입력 후 세션 GET, Then 그 보강할 곳 `resolved_by_form`.
21. **끝내기 결과** — Given 반영 4 · 고객 확인 1 · 건너뜀 0, When `finish`, Then `result.reinforced_count=4`, `completeness_after ≥ completeness_before`, `result.customer_question_ids` 길이 = 세션에서 생긴 질문 수.
22. **저장과 버전** — When `save`, Then `201 {version:1, created:true}`; 바꾸지 않고 다시 `save`, Then `200 {version:1, created:false}`; 바꾼 뒤 `save`, Then `version:2`.
23. **빈 폼 저장 금지** — Given 완전히 빈 정의서, When `save`, Then `422 EMPTY_FORM`.
24. **스냅숏 불변 · 되돌리기** — Given v1, v2, When `GET versions/1`, Then v1 내용 그대로; When `POST versions/1/restore`, Then `201 {version:3}`, v3 스냅숏 폼 = v1 폼, 작업본도 같음.
25. **항목 code** — Given RQ-01..RQ-03, When RQ-02 삭제 후 항목 추가, Then 새 항목 `code="RQ-04"`(재사용 안 함).
26. **메일 초안** — Given 열린 질문 2개(하나 `include_in_mail=false`), When `mail-draft {question_ids:[체크된 1개]}`, Then `200`, `body` 에 그 질문 문장 포함 · 다른 질문 미포함 · 제작자 의견 문장 미포함; mock LLM 실패 시 `generated_by="template"`.

28. **답변 분석** — Given 열린 질문 2개 · 링크(storyboard, `depends_on` 이 질문 대상 항목에 places 2개), When `POST replies` 후 잡 완료, Then `status="ready"`, `changes` 각각 `label`·`before_display`·`after_display` 있음, `storyboard_impact.count=2`.
29. **선택 반영** — Given 변경 3개 중 2개 선택, When `apply {propagate:["storyboard"]}`, Then `201 {version: n+1}`, 선택한 변경만 작업본에 반영, 해결된 질문 `answered`, 연결 항목 `needs_confirmation=false`, 선택 안 한 변경이 답하던 질문 `open` 유지, 링크 `sync_state="pending"`·`pending_version=n+1`, 응답 `pending_sync_links` 에 그 링크.

### 9.2 E2E (Playwright)

1. **목록** — RQ0에 탭 `"전체 {n}"`·`"진행 중 {n}"`·`"저장됨 {n}"`, 진행 중 행 버튼 `"이어서"`, 저장됨 행 `"열기"`. `"새 요구사항"` → 빈 폼(placeholder `"예) 용산 업무시설 재개발 제안"`, `"키맨 (예: 대표이사)"` 보임), TopBar `"새 요구사항"`, Stepper 1단계 활성.

8. **문장 답 → 반영** — 입력창에 답 입력 후 Enter → `"이렇게 바꿀까요?"` 카드(전 취소선 · 후 굵게 · 부수 효과 체크박스) → `"반영"` → 폼 패널 해당 항목이 새 문장. `"고치기"` 는 후 문장을 편집 가능하게 바꾼다.
9. **모름 · 끝내기** — `"모름 · 고객에게 확인"` → 다음 질문; `"끝내기"` → RQ3C에 `"{k}곳 보강했어요"`, `"완성도"` `a% → b%`, `"고객 확인 {n}"` 카드(클릭 시 RQ5).
10. **저장 완료** — RQ3C `"저장"` → `"저장했어요"`·`"v1"`, `"정의서 보기"`, `"고객에게 물을 것 {n}"`, 다음 카드 3개(`"전략 수립 Storyboard"` 가 강조 테두리). Stepper 3단계 모두 체크.
11. **고객에게 물을 것** — RQ5 질문 행마다 키맨 태그. 하나 체크 해제 후 `"메일 문구 복사"` → 클립보드에 체크된 질문 문장만, 제작자 의견 문장 없음.
12. **정의서** — RQ6에 `"정의서 v1"`, 키맨 막대 `"%"`, 고객 확인으로 넘긴 항목 끝에 `"확인 필요"`, 제작자 의견 자물쇠(`title="고객 문서 제외"`), `"쓰는 곳"` 칩 3개. `"고치기"` → 폼.
13. **답변 → v2** — RQ5 `"답변 반영하기"` → RQ7, 글 붙여 넣고 `"바뀌는 곳 찾기"` → RQ7B `"{n}곳이 바뀌어요"`, 한 줄 체크 해제 → `"v2로 저장"` → RQ6 `"정의서 v2"`, 해제한 변경은 반영 안 됨, 반영된 항목의 `"확인 필요"` 사라짐.
14. **Storyboard 반영 줄** — 이 정의서를 쓰는 Storyboard가 있으면 RQ7B에 `"Storyboard {n}곳에도 반영"`(기본 체크)과 `"미리 보기"`, 없으면 줄 없음. 저장 시 storyboard `requirement-sync` 요청이 나간다(네트워크 mock 확인).
15. **사이드바 · 이어서** — 심층 작성 중 다른 화면으로 갔다가 사이드바 `"고객 요구사항"` 그룹의 그 항목을 누르면 질의 화면(현재 번호)으로 돌아온다. RQ0 상태 알약 `"심층 작성 {i} / {N}"`.
16. **새로고침 복구** — 채우는 중 새로고침 → 파일 칩 상태와 진행이 다시 보이고 끝나면 RQ2.
