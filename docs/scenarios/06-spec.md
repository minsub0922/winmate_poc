**표기 규칙**

- `백틱` 안은 보드 문구 그대로다. `{변수}` 부분만 데이터로 바뀐다. 문장부호(`·`, `→`, `—`, `' '`)와 띄어쓰기도 그대로 쓴다.
- **(제안)** = 보드에 없는 문구 · 동작으로 이 문서가 정한 것. 구현은 따르되 디자인 검토 대상이다(§11).
- **[불일치]** = 보드끼리, 또는 보드와 KB 사실이 다른 곳. 구현 기준을 함께 적는다.
- 보드의 `[00]` `[000]` `[0000]` `[0.0]` `[0]` 은 **디자인 자리표시**다(보드를 그릴 때 실제 값을 몰랐음). 구현은 카탈로그의 실제 값을 넣는다. 실행 중 화면에 남는 자리표시는 둘뿐이다.
  - `[확정 필요]` — 값이 없거나 출처끼리 달라 사람이 정해야 하는 칸. 추측해서 채우지 않는다(SP3G `값이 비었거나 출처끼리 다른 곳은 추측하지 않고 여기서 여쭤볼게요.`).
  - `[값]` — 카탈로그에 항목은 있지만 값 동기화를 기다리는 칸(SP3 `[값]은 카탈로그 동기화 후 자동 채움`). KB 어댑터(v1)는 이 상태를 만들지 않는다(§11 Q-SP-05).
- 모델 표시명(`QM55C`) · 영문 계열명(`Smart Signage`)은 KB 에 없다 → 셸 갭 G-PRD-1 규칙(셸 §7.6)을 쓴다. 저장 · 계약은 KB ID(`mdl_LH55QMCEBGCXKR`)와 모델코드(`LH55QMCEBGCXKR`)로 한다.
- **사내 카탈로그** = spec 서비스의 카탈로그 어댑터가 가리키는 현재 원천(§4.15.1). v1 은 KB(`winmate_kb.sqlite`, samsung.com 수집, 등급 T2)이고 버전 라벨은 `kb_meta.products_fetched_at` 의 `YYYY-MM`(현재 KB `2026-10`)이다. 보드의 `2026-09` · `2026-10` 은 예시다.

## 1. 목적과 진입점

### 1.1 목적

삼성 제품의 스펙을 사내 카탈로그에서 가져와 **비교표 · 단일 제품 시트 · 고객 요구사항 대응표**를 만들고, **단종 · 값 불일치 · 요구 미충족**을 경고하고, 언어 · 단위 · 용지 · 숫자 형식을 바꿔 **XLSX · PDF · PPT** 로 내보내거나 제안서 '제품 스펙' 섹션(표준 `PRS8` · 퀵윈 `PRQ5`)으로 보낸다. 홈 카드 `Spec 시트 생성` · `제품을 골라 비교 가능한 스펙 시트를 만들어요.` · 결과가 들어가는 곳 `제안서 제품 스펙 섹션`. 작업 목록 머리 `제품 스펙 비교표와 단일 제품 시트를 만들고, 제안서 '제품 스펙'으로 보냅니다.`

원칙:

1. **값은 출처에서만.** 셀 값은 사내 카탈로그 · 업로드한 데이터시트 · 보증 정책 문서 · 사용자 입력에서만 온다. 비었거나 출처가 엇갈리면 묻고, 답이 없으면 `[확정 필요]`로 두고 시트를 완성한다. 모델(LLM · I2T)은 값을 만들지 않는다(§7.11).
2. **한 화면에 한 가지.** 가운데 대화 줄(사용자 말풍선 · 에이전트 `W`) + 아래 입력 도크(제목 `… · {n} / 3` · 칩 · 입력 · 보조 버튼 · 큰 버튼 하나). 3단계 `제품 입력` · `항목 · 형식` · `시트 생성`.
3. **에이전트가 정하고, 사람은 꼭 필요한 것만.** 시트 종류 · 항목 미리 체크 · 우위 항목 · 단위 변환 · 대체 모델 후보는 자동. 사람은 값 확인(SP3G)과 경고 결정(SP3W)만 한다. 답하지 않아도 진행한다.
4. **편집은 시트에 남는다.** 숨김 · 강조 · 메모 · 순서는 내보내기와 제안서로 그대로 넘어간다(숨긴 행 · 내부 메모는 빠짐).
5. **제안서와 연결을 유지한다.** 보낸 뒤 값이 바뀌면 제안서에 알리고(PR7Q `— Spec 시트와 다름`), 시트에도 경고로 보인다(SP3W `제안서와 다름`).

## 3. 사용자 흐름

### 3.1 기본 흐름

1. **SP1 제품 입력** — 모델명을 입력하면 사내 카탈로그 모델로 매칭(파란 버블). 1개면 단일 제품 시트, 2개 이상이면 비교표(SP1 `하나만 넣으면 단일 제품 시트, 둘 이상이면 비교표로 만들어 드립니다.`). 첫 제품을 넣는 순간 작업(`sp_`)을 만들고 URL 을 `/spec/:id/products` 로 바꾼다(history replace).
2. **SP2 항목 · 형식** — 두 모델의 차이를 한 문장으로 알려 주고, 기본 항목 7개(고객 요구사항이 연결돼 있으면 관련 항목 포함)를 미리 체크. `형식` · `언어` · `차이 강조` 고르기. 자세한 출력 설정은 SP2L.
3. **SP3G 생성 중** — 5단계 잡(`spec_generate`). 비었거나 출처끼리 다른 칸은 값 확인 카드로 묻는다. 답하지 않으면 `[확정 필요]`.
4. **SP3 결과** — 우위 셀 파랑, 셀 직접 수정, 말로 수정, 빠른 내보내기, `저장`.
5. **SP4 내보내기 · 제안서로** — 파일 다운로드 또는 `제안서에 넣기`(넘김 → 제안서 PRS8 · PRQ5).

### 3.2 1단계 입력 갈래

| `start` | 화면 | 끝 조건 | 큰 버튼 → 다음 | 비고 |
|---|---|---|---|---|
| `model` | SP1 | 제품 ≥ 1 | `항목 · 형식 선택` → SP2 | 기본(UC_SP `기본 흐름`) |
| `explorer` | SP1Product(SP1 + 팝오버) | 제품 ≥ 1 | `항목 · 형식 선택` → SP2 | 시리즈 폴더에서 여러 크기 |
| `find` | SP1C | 선택 ≥ 1 | `{n}개로 비교표 만들기` → SP2 | 선택 모델이 제품 목록이 된다. `모델명으로 직접 입력` → SP1(선택 모델을 버블로 가져감) |
| `requirements` | SP1R | 대응표 분석 끝 | `대응표로 시트 만들기` → SP2 | 미충족 → `대안 보기` · `대안 모델 찾기` → SP1C(조건 미리 채움) |
| `clone` | SP0 `⋯` → `복제해서 새 버전` | — | SP1(복제본) | UC_SP `복제해서 새 버전` `다른 고객용으로 재사용` |
| `link` | E4 ~ E8 쿼리 · 라우트 상태 | — | SP1(버블 미리 채움) | `from` 기록 |

### 3.3 시트 종류 · 배치 (결정적)

| 조건 | `kind` | 시트 | 제안서 템플릿(§4.20) |
|---|---|---|---|
| 제품 1개 | `single` | 단일 제품 시트(항목 · 값 2열, 그룹 머리) | `SD-A` |
| 제품 ≥ 2 | `compare` | 비교표(항목 + 모델 열) | `SC-A` (열 2~5) |
| `start=requirements` | `req` | 요구사항 대응표 + (선택) 모델 스펙표 | `SC-B` (+ `SC-A` · `SD-A`) |
| SP2 `제품별 개별 시트` | `layout=per_product` | 제품마다 시트(탭 · 쪽) | `SD-A` × 제품 수 |

- 비교표 열 수 상한은 두지 않되 **(제안)** 8 을 넘으면 SP1 큰 버튼 옆에 `한 시트에 8개까지 비교할 수 있어요.`를 보이고 막는다. 제안서 `SC-A` 는 `사양 비교표 2~5개` → 6개 이상이면 넘길 때 여러 장으로 나눈다(§4.13.5).
- `kind` 는 제품 수가 바뀌면 다시 정한다(시트 생성 뒤에도). `req` 는 고정.

### 3.5 사람에게 묻는 곳 (전부 끊지 않는 질문)

| # | 무엇을 | 화면 | 답이 없으면 |
|---|---|---|---|
| 1 | 카탈로그에 값이 없는 칸 | SP3G 값 확인 `사내 카탈로그에 값이 없어요. 데이터시트가 있으면 읽어서 채울게요.` | `[확정 필요]` |
| 2 | 출처끼리 값이 다른 칸 | SP3G 값 확인 `카탈로그와 국내 보증 정책 문서의 값이 서로 달라요.` | `[확정 필요]`. 눌린 칩(카탈로그 값)은 미리 골라 둔 답일 뿐이고 `답 반영하고 완성`을 눌러야 적용된다 **(제안 — 원칙 1)** |
| 3 | 단종 모델 처리 | SP3W `단종` 카드 | 기본 선택(`'기존 장비'로 표기하고 유지 — 교체 전 ↔ 후 비교`) 유지, 경고는 열린 채 |

| 6 | 고객 요구 미충족 | SP3W `요구 미충족` 카드 | 경고 열린 채 |
| 7 | 판정할 근거가 없는 요구 항목 | SP1R `확인 필요` 행 | `확인 필요` 그대로 시트에 들어감 |

- jobs `awaiting_input` 은 쓰지 않는다. 묻는 것은 자원(값 확인 · 경고 · 요구 행)으로 남고 화면이 그 자원을 고친다. 그래서 잡은 멈추지 않는다.
- 판단 기록: 잡의 `log` 이벤트로 `{t, text, mode}`(모드 `auto` · `check` · `ask` · `pin`, MI · VP 와 같은 4종)를 남긴다. spec 보드에는 모드 칩이 없으므로 화면에 보이지 않고 `변경 내역`(SP3E) · 디버그용이다 **(제안)**.

### 3.8 재확인 · 카탈로그 갱신 흐름

1. 트리거: (a) 카탈로그 버전이 바뀜 — 매일 1회 `GET /api/kb/v1/meta` 의 `products_fetched_at`(또는 사내 카탈로그 반입 이벤트)을 비교 **(제안: jobs 예약 `wm:sched` 매일 06:00 KST)**, (b) 사용자가 시트에 제품을 더함(SP3W `최신 카탈로그와 다시 대조했어요.`), (c) 제안서 연결 상태 변화(보낸 뒤 시트가 바뀜), (d) `POST /v1/sheets/{id}/recheck`.
2. `spec_recheck` 가 저장된 시트(보관 제외)마다 셀 값을 새 카탈로그로 다시 계산해 차이를 경고(`catalog_changed`)로, 모델 생애주기 변화를 `discontinued` 로, 연결된 제안서와의 차이를 `value_mismatch_proposal` 로 만든다(§4.17). **시트 값은 바꾸지 않는다** — 사용자가 SP3W 에서 정한다.
3. 상태 `warn` → SP0 배너 `사내 카탈로그가 {M}월 {D}일 갱신되었습니다. 저장된 시트 {n}개에서 값이 달라져 다시 확인이 필요해요.` · workspace 알림 · 사이드바 상태.
4. 사용자가 SP3W 에서 결정 → `선택한 대로 반영` → version +1 → 연결된 제안서가 있으면 `제안서에도 반영`(SP4 교체 넘김).

### 4.3 SP1 — 제품 입력 (`/spec/new` → `/spec/:id/products`)

### 4.4 SP1Product — 제품 탐색 팝오버, 작업 중 (`?pop=product`)

팝오버 자체(검색 · 트리 · 모델 표 · 추가 버튼 · 트레이 · 푸터 · 끌기)는 **셸 소유**다(셸 §5.3, `role="dialog"` `aria-label="제품 탐색"`, 700×540). spec 은 맥락만 넘긴다.

| spec 이 넘기는 것 | 값 |
|---|---|
| `hasTask` | true(`/spec/new` 포함) |
| `accepts` | `['product']` — 솔루션 · 이미지 · 사례 추가 버튼은 꺼진다(셸 Q-UI-7) |
| `added` | 시트 제품의 `kb:model:*` ref → 해당 행 `✓ 추가됨` |
| `onAdd('product', refs)` | 작업이 없으면 `POST /v1/sheets {start: 'explorer', products: refs}`, 있으면 `POST /v1/sheets/{id}/products {refs}` → 성공 시 `{added}` 를 돌려줌 |

- 보드 상태: TopBar `popover="product"`, 경로 `전체 › 디스플레이 › 스마트 사이니지 › QMC Series`, `끌어서 바로 추가`, 표 `모델` `크기` `밝기` `해상도`(QM43C ~ QM85C · `500nit` · `4K UHD`), `상세`, 추가 버튼 `+ 추가` / `✓ 추가됨` / `✓ 선택`, 툴팁 `진행 중인 작업이 없어 추가할 수 없습니다` · `이미 현재 작업에 있습니다`, 푸터 `선택 {n}` + `현재 작업에 추가`. 작업 없음 상태 안내 `진행 중인 작업이 없어 탐색만 할 수 있어요. 작업을 시작하면 제품을 추가할 수 있습니다.`(spec 화면에서는 나오지 않음).
- 아래 SP1 화면: 에이전트 `스펙 시트를 만들 제품을 입력해 주세요. 하나만 넣으면 단일 제품 시트, 둘 이상이면 비교표로 만들어 드립니다.`, 도크 `제품 입력 · 2개 추가됨 · 1 / 3`, 버블 `Smart Signage QM55C` · `Flip Pro WA75D`, 큰 버튼 `항목 · 형식 선택`. [불일치] SP1 의 셋째 문장이 빠져 있음 — 같은 화면이므로 SP1 문구를 쓴다. Tip · 조합 칩은 팝오버에 가려 보드에 없을 뿐 그대로 있다.
- 모델 행을 입력창으로 끌어 놓으면(셸 §5.7) `onAdd` 와 같다. 팝오버는 추가 뒤에도 열린 채(셸). 버블은 즉시 갱신.
- [불일치] 보드 팝오버의 QM55C 는 `✓ 선택`(이미 버블에 있는데) — 구현은 `added` 를 따른다(`✓ 추가됨`, 셸 §5.3.4). `Flip Pro WA75D` 는 KB 에 없다(테스트는 KB 모델로).

### 4.5 SP1C — 조건으로 모델 찾기 (`/spec/new/find` → `/spec/:id/find`)

TopBar `새 작업`, Stepper 1.

#### 4.5.1 대화 줄

- 사용자 말풍선: 처음 입력한 문장(보드 `C 물류센터 관제실에 24시간 켜 둘 55" 전후 벽걸이 디스플레이가 필요해요`). 문장 없이 칩만 고르면 말풍선 없음.
- 처음(조건 없음) **(제안)**: 에이전트 `어떤 디스플레이가 필요한지 말해 주세요. 크기 · 밝기 · 용도 · 설치 조건으로 후보를 찾아 드려요.`
- 결과 에이전트: `조건에 맞는 후보 {n}개를 찾았습니다. 필수 조건({필수 " · "})을 먼저 맞추고 {정렬}으로 정렬했어요. 시트에 넣을 모델을 고르면 비교표로 만듭니다.` — 보드 `조건에 맞는 후보 4개를 찾았습니다. 필수 조건(24시간 운영 · 벽걸이)을 먼저 맞추고 밝기가 높은 순으로 정렬했어요. 시트에 넣을 모델을 고르면 비교표로 만듭니다.` 정렬 = 밝기 `높은 순` → `밝기가 높은 순` · 그 밖 **(제안)** `조건 일치 순`. 필수가 없으면 **(제안)** `필수 조건(…)을 먼저 맞추고 ` 부분을 뺀다. `{n}` = 보이는 카드 수.

#### 4.5.2 후보 영역

- 머리: `후보 {n}개 · 조건 일치순` · `사내 카탈로그 {버전} 기준`(보드 `2026-09`) · 버튼 `표로 비교` · `조건 밖 후보 숨기기`(토글).
- 카드(2열 그리드 **(제안)** — 보드 4장):

| 요소 | 규칙 |
|---|---|
| 선택 상자 | 오른쪽 위 18×18 r5. 선택 시 바탕 `#1428a0` 흰 체크 |
| 화면 상자 | 60" 미만 64×36, 60" 이상 74×42 (보드 55 → 64×36, 65 → 74×42), 2px `#121417` 테두리 · 그라데이션 `#3d4452 → #121417`. 조건 밖이면 `opacity: 0.55` |
| 이름 | 표시명(Manrope 15/800, 조건 밖이면 `#596170`) |
| 점수 | `조건 {ok}/{n}` (11.5/600, 모두 ok 이면 `#1428a0`, 아니면 `#596170`) |
| 계열 | `{분류 짧은 이름} {시리즈 코드}`(보드 `스마트 사이니지 QHC`) — 짧은 이름은 큐레이션(G-PRD-1 · Q-KB-3) |
| 조건 막대 | 조건 행마다 높이 4 칸(ok `#1428a0` · no `#121417` · check `#e2e5ea`) |
| 조건 행 | 아이콘 14 + 이름(`크기` · `밝기` · `운영` · `설치` …) + 값(ok `#121417` 600 · check `#596170` 600 · no `#121417` 700) |
| 버튼 | `선택됨`(바탕 `#1428a0` 흰 글) / `+ 시트에 담기`(흰 바탕 1px `#e2e5ea` 글 `#1428a0`), h30 r8 |
| 카드 테두리 | 선택 1.5px `#1428a0` + 그림자 `0 4px 14px rgba(20,40,160,0.10)` · 아니면 1px `#e2e5ea` |

- `표로 비교` **(제안)**: 카드 대신 표(행 = 후보, 열 = `모델` · `계열` · 조건 행들 · `밝기` · `운영` · `소비전력` · `무게`, 행 끝 담기 버튼). 다시 누르면 카드.
- `조건 밖 후보 숨기기`: 켜면 조건 밖 카드를 숨기고 머리 `{n}` 도 보이는 수로.

#### 4.5.3 도크

| 요소 | 문구 | 동작 |
|---|---|---|
| 제목 | `조건으로 찾기 · {n}개 선택 · 1 / 3` | |
| 링크 | `모델명으로 직접 입력` | 선택한 모델을 제품으로 넣고 SP1 로(`start` 유지) **(제안)** |
| `크기` 칩 | `43"` `50"` `55"` `65"` `75" 이상` (보드 `55"` 켬) | 여러 개 고를 수 있음 **(제안)** |

#### 4.5.4 조건 행 판정 (결정적)

| 행 | 언제 보이나 | ok | check(`확인 필요`) | no(조건 밖) | 값 표시 |
|---|---|---|---|---|---|
| `크기` | 크기 칩 ≥ 1 | 모델 인치 ∈ 고른 크기(`75" 이상` = ≥ 75). 인치 = 모델코드 크기 숫자, 없으면 `ceil(cm ÷ 2.54 − 0.05)`(셸 §9.2) | 인치 모름 | 그 밖 | `{n}"` · no 면 `{n}" · 조건 밖` |
| `밝기` | 항상 | 값 있음(`실외용`이면 근거 충족) | 값 없음 | `실외용` 인데 근거 없음 · 미달 | `{n} nit`, **(제안)** 700 nit 이상이면 ` · 고휘도` (보드 QH55C `· 고휘도`) |

| `설치` | 설치 칩 ≥ 1 또는 필수 `벽걸이` | 벽걸이 = `기구사양 › VESA 마운트` 값 있음 또는 `추가 기능 › 마운트` 값 있음 · 스탠드 = `추가 기능 › 스탠드` 값 있음 | 천장 · 세로 설치(KB 근거 속성 없음) · 근거 없음 | 명시적 불가 근거(KB v1 없음) | 고른 설치 이름(`벽걸이`) |

- **조건 밖** = 행 하나라도 `no`(보드 로직 `out = conds.some(no)`).
- `실외용` 근거 **(제안)**: 제품군 `provides` 에 `cap_sunlight_readable` 또는 `cap_weatherproof` 가 있거나 밝기 ≥ 2,500 nit.
- 정렬(`조건 일치순`): ① 조건 밖 아님 먼저 ② 필수 행 모두 ok 먼저 ③ ok 행 수 내림차순 ④ 밝기 `높은 순`이면 nit 내림차순 ⑤ C2 점수 내림차순 ⑥ 모델코드 오름차순. 말로 더한 정렬 조건(`베젤 얇은 순`)은 ④ 다음.
- 후보 풀 = `C2(category=분류, space=, vertical=, soft=용도 · 필수 역량, text=문장)` 상위 제품군 15개 → 제품군의 모델 전부 → 판정. 보이는 카드 = 조건 밖 아닌 것 전부 + 조건 밖 중 `no` 행이 가장 적은 2개 **(제안)**, 최대 6장 **(제안)**. hard 역량은 C2 에 넘기지 않는다(근소하게 못 미친 모델도 보여야 하므로 — 판정은 spec 이 모델 단위로 한다).
- 용도 → C2 신호 **(제안)**: `메뉴보드` soft `remote_content_mgmt` · 공간 매장 · `안내` 공간 로비 · `관제 · 모니터링` soft `continuous_operation` · `회의` soft `touch_interactive` · 공간 회의실. 분류 기본값은 사이니지(KB `top_display`), 문장에서 A1 이 다른 분류를 찾으면 그 분류.

#### 4.6.1 대화 줄

- 사용자: 파일 카드 `{파일명}`(보드 `B병원_로비디스플레이_요구규격서.pdf`) + `{형식} · {쪽}쪽 · 요구 항목 {n}개 인식`(보드 `PDF · 4쪽 · 요구 항목 12개 인식`) + 함께 쓴 말(보드 `이 규격서 기준으로 QM55C 대응표를 만들어 주세요`).

- 결과 에이전트: `규격서에서 요구 항목 {n}개를 찾아 {모델} 스펙과 맞춰 봤습니다. 충족 {a} · 미충족 {b} · 확인 필요 {c}입니다.` + (`b ≥ 1` 이고 대안이 있으면) ` 미충족 항목에는 대안 모델을 함께 붙였어요.` — 보드 `규격서에서 요구 항목 12개를 찾아 QM55C 스펙과 맞춰 봤습니다. 충족 8 · 미충족 1 · 확인 필요 3입니다. 미충족 항목에는 대안 모델을 함께 붙였어요.`

- 머리: `요구사항 대응표` · `대응 모델 {모델}` + 셰브론 아이콘(`M6 9l6 6 6-6`)(메뉴: 시트 제품 + **(제안)** `다른 모델 고르기…` → 제품 탐색 팝오버) · 요약 칩 `충족 {a}` · `미충족 {b}` · `확인 필요 {c}`(`c ≥ 1` 이면 `확인 필요` 칩 켬 스타일; 누르면 그 판정만 거르기 **(제안)**).
- 열: `요구 항목` · `고객 요구` · `{모델}` · `판정` · `원문`. 행 h34, 미충족 행 바탕 `#f5f6f8`.

| 열 | 내용 | 출처 |
|---|---|---|
| 요구 항목 | 짧은 이름(`화면 크기`) | LLM 추출 `item` |
| 고객 요구 | 요구 짧은 문장(`55인치 이상`) | LLM 추출 `requirement` — 수치는 원문 문장(`quote`)의 수치와 같아야 한다(§7.11) |
| `{모델}` | 모델 값(600, 없으면 `—` `#8a91a0`) | 카탈로그(§4.14 표시 규칙, 해상도 요구면 등급 라벨 `UHD`) · 역량이면 근거 이름(`MagicINFO`) |
| 판정 | 아이콘 16 + `충족` / `미충족` / `확인 필요` + 메모(11.5px) | §4.6.3 |
| 원문 | `p.{n}` 링크 | 추출 `page` |

#### 4.6.3 판정 규칙 (결정적 우선)

| 요구 종류 | 방법 | 충족 | 미충족 | 확인 필요 |
|---|---|---|---|---|
| 수치(크기 · 밝기 · 운영 시간 · 무게 · 해상도 픽셀 · 소비전력 …) | A3 → 정규 키(A3 가 못 붙이면 LLM `key_hint` 를 허용 목록 안에서만) → 비교. 값이 하나인 키는 `C6`, 값이 여럿인 키(`power_consumption` · `weight_kg`)는 spec 이 속성 이름으로 고른 값으로 직접 비교(§4.15.4) | 조건 맞음 | 조건 틀림 | 모델 값 없음 · 요구 수치 없음 |

- 단위: `cd/㎡` = `nit`(1:1) · `인치`·`inch`·`"` = 인치(셸 인치 규칙으로 비교) · `W` · `kg` · `24시간`·`24/7` = 24.
- A3 주의: `normalize_spec` 은 속성 이름이나 값의 `"` 로만 인치를 알아본다. `화면 크기` + `55인치 이상` 은 `screen_size_cm` 55(cm 로 오해) → spec 이 값에 `인치`·`inch` 가 있으면 인치로 바꿔 판정한다(kb 요청 §8).
- 범위 요구(`대기실 2곳 65인치 이상`)는 별도 행(항목 `대기실 화면 크기`). 미충족이면 **대안 찾기**: ① 같은 제품군에서 요구를 맞추는 가장 작은 크기 ② 없으면 §4.5 찾기 1위. 대안은 시트 제품에 넣지 않고 메모로만(`시트에 넣기` `대안 모델 {대안} 비교` 를 켜면 넣음).
- `확인 필요` 행은 SP0 상태 `확인 필요 {n}`(§3.6)의 n 이다.

### 4.7 SP2 — 항목 · 형식 (`/spec/:id/items`)

TopBar 작업 제목, Stepper 2.

#### 4.7.1 대화 줄

- 사용자 요약 말풍선: `제품 {n}개 · {영문 계열명} {표시명 " / "}` — 계열명이 모두 같으면 한 번만(보드 `제품 2개 · Smart Signage QM55C / QB55C`). 다르면 `{계열명 표시명}` 을 ` / ` 로.
- 에이전트(비교): `두 모델은 같은 {공통점}지만 {차이 1}와 {차이 2}이 다릅니다. 시트에 넣을 스펙 항목과 출력 형식을 골라주세요.` + (요구사항으로 미리 체크했으면) ` 고객 요구사항과 관련된 항목을 미리 체크해 두었습니다.` — 보드 `두 모델은 같은 55" 4K 사이니지지만 밝기(500 vs 350nit)와 운영 시간(24/7 vs 16/7)이 다릅니다. 시트에 넣을 스펙 항목과 출력 형식을 골라주세요. 고객 요구사항과 관련된 항목을 미리 체크해 두었습니다.`
  - 공통점(결정적): 크기가 같으면 `{n}"` + 해상도가 같으면 등급(`4K`) + 분류 짧은 이름(`사이니지`).
  - 차이: 기본 항목 순서대로 값이 다른 항목 최대 2개, `{항목 짧은 이름}({값1} vs {값2}{단위})`(단위는 뒤 값에만 붙임: `500 vs 350nit`, 단위 없는 값은 그대로: `24/7 vs 16/7`). 조사(와/과, 이/가)는 앞 낱말 받침으로 고른다.
  - 3개 이상 **(제안)**: `{n}개 모델은 같은 …지만 …`, 값은 ` / ` 로(`700 / 500 / 350nit`). 차이가 없으면 **(제안)** `두 모델의 주요 스펙이 같습니다.`
- 에이전트(단일) **(제안)**: `{표시명}의 스펙 항목과 출력 형식을 골라주세요.` + 같은 꼬리.

### 4.11 SP3W — 단종 · 값 불일치 경고 (`/spec/:id/warnings?w={swn}`)

#### 4.11.1 대화 줄

- 사용자 말풍선: 경고를 만든 요청이 있을 때(보드 `고객 매장 기존 장비 QM55R도 같이 비교해줘`).
- 에이전트: `최신 카탈로그와 다시 대조했어요. {요약}. 오른쪽에서 하나씩 정하면 시트에 반영할게요.` — 보드 `최신 카탈로그와 다시 대조했어요. QM55R은 단종 모델이고, 출처나 제안서와 값이 다른 곳이 2곳, 고객 요구와 맞지 않는 곳이 1곳 있어요. 오른쪽에서 하나씩 정하면 시트에 반영할게요.`
  - 요약 조각(있는 것만 `, ` 로 잇고 끝을 `있어요` 로): 단종 `{모델 " · "}은/는 단종 모델이고` · 값 불일치 `출처나 제안서와 값이 다른 곳이 {n}곳` · 요구 미충족 `고객 요구와 맞지 않는 곳이 {m}곳` · 카탈로그 변경 **(제안)** `카탈로그에서 바뀐 값이 {k}곳`.

- 바닥: `결정 {d} / {n}`(결정 = 선택값이 있는 카드 — 기본 선택 포함, 보드 `2 / 4`) · `나중에`(→ SP3, 경고 열린 채, 상태 `warn`) · `선택한 대로 반영`(→ `POST /v1/sheets/{id}/warnings:apply` → SP3).
- 즉시 이동 조작: `다른 후보 찾기` → SP1C(그 모델의 크기 · 용도로 조건 미리 채움) · `제안서에도 반영` → SP4(대상 = 그 연결의 제안서, 기존 시트 처리 `새 버전으로 교체` 미리 고름) · `요구사항 대응표 보기` → SP1R. 이동 전 그때까지의 선택은 저장(`PATCH …/warnings/{swn}`)된다.

### 4.12 SP3E — 시트 편집 (`/spec/:id/edit?session={ses}`)

TopBar 작업 제목, Stepper 3. 들어올 때 `POST /v1/sheets/{id}/edit-sessions` → `{id: ses_…, base_version}`. 모든 조작은 세션 안에 쌓이고(서버 보관 — 새로고침해도 유지) `편집 완료` 때 한 번에 반영된다.

- 에이전트: `편집 모드예요. 행을 끌어 순서를 바꾸고, 오른쪽 아이콘으로 숨기기 · 강조 · 메모를 달 수 있어요. 숨긴 행은 내보낼 때 빠지고, 메모는 각주나 내부 메모로 남길 수 있어요.`
- 도구줄: 태그 `편집 중` · 시트 제목 · `실행 취소`(`aria-label`) · `다시 실행`(`aria-label`) · 스위치 `숨긴 행 보기 {n}`(`role="switch"`, 기본 켬 — 켜면 숨긴 행을 회색으로 보이고 끄면 감춤) · `열 순서 바꾸기`(누르면 열 머리에 끌기 손잡이 **(제안)**).
- 표 머리: `항목` · 모델 열 · `숨김 · 강조 · 메모`.
- 행: 끌기 손잡이(`aria-label="끌어서 순서 바꾸기"`, 이동 · 선택 행은 `#1428a0`, 그 밖 `#b8bec8`) · 항목 이름 + 태그 · 셀 · 아이콘 버튼 28×28 r7 — 눈(`숨기기` / 숨긴 행은 `다시 보이기`) · `강조` · `메모`(켜진 아이콘 바탕 `#eaeefb` 글 `#1428a0`, 꺼짐 `#b8bec8`). 키보드 **(제안)**: 손잡이에 포커스 + `Alt+↑/↓` 이동.
- 태그: `강조` · `↑ {k}칸` / `↓ {k}칸`(세션 시작 위치 대비) · `숨김` · `추가됨`.
- 메모 편집기(행 아래 펼침): 제목 `{항목} 메모`(보드 `밝기 · 명암비 메모`), 글 상자(보드 `창가 매장은 오후 직사광이 들어 QM55C 권장 — 고객 미팅에서 언급`), 라디오 `시트에 각주로 표시`(기본) / `내부 메모만 (내보내지 않음)`, 버튼 `삭제` · `메모 저장`.
- 항목 추가 줄: 버튼 `항목 추가`(누르면 시트에 없는 행 목록 — 항목 아래 행 단위, 예 `크기 (W×H×D)` · `무게 (제품 · 포장)` **(제안)**) · `빠진 항목` 칩(행이 하나도 없는 항목: 보드 `입출력 단자` `베젤` `인증` `액세서리`, 누르면 그 항목의 행 전부를 맨 아래에 `추가됨`) · 오른쪽 `보이는 행 {v} / {t}`(보드 `7 / 8`).
- 추가된 행의 값은 서버가 카탈로그에서 바로 계산해 세션에 넣는다(결정적, LLM 없음). 값이 없으면 `[확정 필요]`, 커밋 때 값 확인을 만든다.

- 사양 비교표(`SC-A`, `사양 비교표 2~5개`): 모델이 6개 이상이면 장 수 = ⌈n ÷ 5⌉, 열은 고르게 나눈다(6 → 3 + 3, 7 → 4 + 3) **(제안)**. 제목 끝 **(제안)** ` (1/2)`.
- 제품별 상세(`SD-A`): 제품마다 한 장, 행은 항목 카탈로그 그룹(§4.14) 순.
- 요구사항 대응표(`SC-B`): 대응표 행 전부(`원문 쪽 번호 표기` 켜면 원문 열 포함).
- 공통: 숨긴 행 · 내부 메모 제외, 각주 메모 · 강조 · 우위 표시 포함, `[확정 필요]` 칸은 묶음의 `fact_check[]` 로도 나간다(제안서 PR7Q `사실 확인 필요`).
- 넘김이 확인되면(proposal `:ack`) 연결(`slk_`)이 생기고 `sent_version` · 보낸 값 스냅숏을 남긴다 → 이후 값이 바뀌면 경고(§4.17) · 제안서 알림(§6.10).

#### 4.15.7 파생 행 (말로 추가, 예 `소비전력을 연간 전기료로 환산한 행 추가`)

- 결정적 계산만. **(제안)** `annual_energy_cost`: 연간 kWh = 일반 소비전력(W) × 하루 운영 시간(`24/7` → 24, `16/7` → 16) × 365 ÷ 1000, 연간 전기료 = kWh × 전기 단가(원/kWh).
- 단가는 설정값(`SPEC_ELECTRICITY_KRW_PER_KWH`)이 있으면 쓰고 각주 `* 계산 기준: 하루 {h}시간 · 365일 · 1kWh당 {단가}원`, 없으면 값 확인(`missing`, `계산 기준`) → 답이 없으면 `[확정 필요]`. 일반 소비전력이 `[확정 필요]` 면 결과도 `[확정 필요]`.
- 행 이름 **(제안)** `연간 전기료 (추정)`, 우위 = 작은 쪽, 출처 `계산`.

#### 4.15.8 보증 원천

- KB v1 에는 보증 연수가 없다(사이니지 `품질보증기준` 은 일반 문구). **(제안)** `services/spec/config/warranty.yaml`(시리즈 · 분류 → 연수, 원천 문서 이름 `국내 보증 정책 문서` · `file_id` · 기준일) + internal 카탈로그(있으면)의 보증 값. 둘 다 있고 다르면 `conflict`(보드 SP3G 2번), 하나만 있으면 그 값, 없으면 `missing`. Q-SP-02.

#### 4.15.9 MagicINFO 호환 근거

- `지원` 근거(하나면 충분): 모델 상세 `supported_solutions` 에 MagicINFO(셸 §7.2.6 — PDP `mention` · `feature_block`) 또는 제품군 `provides` 의 `cap_remote_content_mgmt` 근거 문장에 `MagicINFO`(KB: QMC · QBC `…MagicINFO와 VXT를 지원합니다.…`). QHC 근거는 `VXT Player Support` 만 → MagicINFO 근거가 따로 없으면 `[확정 필요]`.
- 등급 T2(문구 근거) → SP3G 미리보기에서 `chk`(검증 중)로 보이다 `ok`.

### 4.16 단위 · 숫자 · 언어 · 용지 · 파일명 · 내 기본값

#### 4.16.1 길이

| 설정 | 변환 | 표시 예(QM55C 크기) |
|---|---|---|
| `mm` (원문) | 그대로 | `1,237.9×708.8×28.5 mm` |
| `inch` | mm ÷ 25.4 | `48.7 × 27.9 × 1.1 in` |
| `둘 다 표기` | 둘 다 | `1,237.9×708.8×28.5 mm (48.7 × 27.9 × 1.1 in)` **(제안)** |

- 대상: 크기(W×H×D) · 베젤 · VESA(`200 x 200 mm` → `7.9 × 7.9 in`). 화면 크기는 언제나 인치 `"`(설정과 무관), 픽셀 피치는 mm 유지 **(제안)**.
- 영문 길이 표기는 숫자 사이 ` × `(공백 있음, SP2L), 한국어는 `×`(공백 없음, SP3E `크기 (W×H×D)`).

#### 4.16.2 무게

| 설정 | 변환 | 표시 예(QM55C) |
|---|---|---|
| `kg` | 그대로 | `15.7 kg · 포장 19.9 kg` |
| `lb` | kg × 2.20462 | `34.6 lb / 43.9 lb` |
| `둘 다 표기` | 둘 다 | `15.7 kg (34.6 lb) · 포장 19.9 kg (43.9 lb)` **(제안)** |

#### 4.16.3 반올림 · 바뀐 셀

- 변환 값은 소수점 첫째 자리 반올림(ROUND_HALF_UP). 원래 값(KB 원문 `1237.9 x 708.8 x 28.5 mm`)은 셀 메모(XLSX comment)와 `Notes & Sources` 에 보관(SP2L `mm 원래 값은 셀 메모에 보관`).
- 단위가 바뀐 셀은 미리보기에서 파랑(`#eaeefb`/`#1428a0` 600), 개수는 안내 줄 `단위 바뀐 셀 {n}개`. 내보낸 파일에서는 파랑 표시 없음 **(제안)**.

#### 4.16.4 숫자 형식

| 설정 | 천 단위 | 소수점 | 예 |
|---|---|---|---|
| `1,234.5` (기본) | `,` | `.` | `1,237.9` · `4,000:1` · `48.7` |
| `1.234,5` | `.` | `,` | `1.237,9` · `4.000:1` · `48,7` |

- 천 단위는 1,000 이상의 수에만. 해상도(`3840×2160`) · 모델코드 · 연도 · 버전 숫자(`Tizen 7.0`, `HDCP 2.2`, `60950-1`) · KC 번호에는 적용하지 않는다.
- [불일치] SP3 표본 `4000:1` 은 이 규칙이면 `4,000:1`.

#### 4.17.2 생애주기 · 대체 모델 (v1)

| 순서 | 원천 | 결과 |
|---|---|---|
| 1 | internal 카탈로그 생애주기(있으면) | `on_sale` · `discontinued` · `eol_planned` + 후속 |
| 2 | KB `C5`(계획: `chain[{id, relation, spec_diff_summary}]`, `recommended_current`) | 후속 · 관계 |
| 3 | spec 생애주기 표 `lifecycle`(관리자가 채움, 시드 `services/spec/config/lifecycle.yaml` **(제안)**) | 단종 · 후속 모델코드 · 원천 이름 · 기준일 |
| 4 | KB 존재 여부 | 있으면 `on_sale`(DR09), `sold_out_flag='Y'` 는 **(제안)** 경고 없이 출처 보기에만 `품절 표시`, 없으면 `unknown` → `not_in_catalog` |

- 대체 모델(후속이 없을 때, 결정적 **(제안)**): 표시명에서 시리즈 글자 · 크기를 뽑아(`QM55R` → `QM` · 55) 같은 시리즈 · 같은 크기의 판매 중 모델 중 출시가 가장 최근인 것(`QM55C`). 관계 문구 `같은 {크기}" {시리즈} 라인업`, 이미 시트에 있으면 ` · 이미 비교 중`.
- KB 사실: DR10(세대 · 후속) `succession 엣지 0 · blocked_by_source`, 단종 모델은 사이트에 없다 → v1 은 3 · 4 로 동작. 보드의 `QM55R` 은 KB 에 없으므로 테스트는 생애주기 표 픽스처로 한다.

#### 4.17.3 결정 반영 (`선택한 대로 반영`)

| 결정 | 반영 |
|---|---|
| `'기존 장비'로 표기하고 유지` | 열 역할 `existing`, 열 머리 아래 줄 `고객 기존 장비`, 열 이름 **(제안)** 그대로(`QM55R 열 이름을 '기존 장비'로` 같은 수정 요청으로 바꿈). 우위 계산에서 제외 **(제안)** |
| `시트에서 빼기` | 열 삭제 |
| `대체 모델 {대체}로 바꾸기` **(제안)** | 열 모델 교체 → 그 열만 다시 채움(`spec_generate` 부분 실행, 202) |
| 칩 선택(출처 · 카탈로그 변경) | 셀 값 · 출처를 고른 것으로. 고른 것이 카탈로그가 아니면 `edited` 아님 — 출처 표시만 바뀜 |
| `제안서에도 반영` | 즉시 SP4 로 이동(교체 넘김). 넘김이 확인되면 경고 해결 |
| `그대로 두기` · `확인함` | 경고 `dismissed`(이유 기록), 같은 원인으로 다시 만들지 않음(값이 또 바뀌면 새로 만듦) |

- 반영 = 한 번의 버전(+1). 결정이 없는 카드는 열린 채 남는다. `나중에` 는 아무것도 반영하지 않는다.

#### 4.17.4 재확인 비교 규칙 (`spec_recheck`)

1. 시트의 카탈로그 원천 셀(`edited` · `derived` 제외)마다 새 카탈로그 값으로 표시값을 다시 만든다 → 표시값이 다르면 `catalog_changed`(같은 칸에 열린 것이 있으면 갱신).
2. 시트 제품마다 생애주기를 다시 본다 → 단종으로 바뀌면 `discontinued`.
3. 연결(`slk_`)마다 보낸 스냅숏과 지금 보이는 값을 비교 → 다르면 `value_mismatch_proposal`(그 연결의 제안서 · 섹션 번호 · 이름).
4. 요구 원천(대응표 · 정의서)이 있으면 `C6` · §4.6.3 으로 다시 판정 → 미충족 `requirement_unmet`.
5. 결과 수가 바뀐 시트만 상태 · workspace 갱신, 카탈로그 버전이 바뀐 경우 SP0 배너 수 집계.

### 4.18 고객사 양식 올리기 (SP2L `고객사 양식 올리기`)

- 문구 근거: `고객사 양식이 있으면 올려 주세요. 같은 칸 순서로 맞춰 드립니다.`
- 받는 파일 **(제안)**: XLSX(권장) · PDF · DOCX · 이미지(PNG · JPG). files 업로드 → `POST /v1/sheets/{id}/templates {file_id}` → `202`(`spec_template`).
- 읽기: XLSX 는 결정적으로 첫 시트의 라벨 열 · 머리 행을 읽음(병합 셀 포함). PDF · DOCX 는 files 추출 텍스트, 표가 그림이면 i2t `spec.page_ocr.v1`.
- 맞추기: LLM `spec.template_map.v1`(confidential) → 양식 행 ↔ 시트 행(`row_key` 또는 없음), 양식 열 ↔ 제품 · 라벨. 결정적 검사: 행 · 열 번호가 양식 안에 있어야 하고, 같은 시트 행을 두 번 쓰지 않음.
- 결과:
  - 시트 행 순서 · 행 이름을 양식대로(양식 행 이름이 시트 이름을 대신함).
  - 양식에만 있는 행은 `template:*` 행으로 들어가고 값은 `[확정 필요]` + 값 확인(제목 `{양식 행 이름}`, 본문 **(제안)** `고객사 양식에 있는 항목이에요. 값을 넣어 주세요.`).
  - 시트에만 있는 행은 **(제안)** 양식 아래 `추가 항목` 으로.
  - XLSX 내보내기는 고객사 파일을 바탕으로 같은 칸에 값을 써 넣는다(서식 유지). PDF · PPT 는 우리 디자인에 양식 순서만 반영.
- 미리보기 머리에 **(제안)** 칩 `고객사 양식 · {파일명} ×`(지우면 양식 해제).

### 4.19 내보내기 형식 (XLSX · PDF · PPT)

모든 파일은 export 서비스가 만든다(spec 은 렌더 모델을 넘김). 잡 `spec_export` → export 계약(`docs/requests/export.md` 에 `spec_table` 템플릿 요청) → `file_id`.

| 형식 | 구성 | 비고 |
|---|---|---|
| XLSX (`값 수정 · 견적 첨부용`) | 시트 1: 1행 시트 제목(병합) · 2행 머리(`Item` / `항목` + 모델) · 항목 행(보이는 행, 편집 순서) · 각주. 시트 2 `Notes & Sources` / `메모 · 출처`: 출처 목록(행 · 열 · 출처 · 등급 · 버전 · 인용), 변환 원래 값, 계산 기준, `[확정 필요]` 목록. 셀 메모 = 변환 원래 값 · 직접 입력 표시 | 숫자 한 개짜리 칸은 숫자 셀 + 서식, 합친 칸은 글. 우위 셀 채우기 `#eaeefb` · 글 `#1428a0` 굵게, 강조 행 굵게 + 왼쪽 테두리 **(제안)**. 머리 행 고정 **(제안)**. 양식이 있으면 양식 파일 바탕 |
| PDF (`메일 · 인쇄용, 레이아웃 고정`) | 용지(§4.16.7), 제목 · 표 · 각주 · 출처 줄, 쪽 번호 **(제안)** | 긴 표는 쪽 넘김 시 머리 반복 |
| PPT 슬라이드 (`1장 · 삼성 B2B 표준 디자인`) | 16:9 1장: 제목 · 표 · 각주 · 출처 줄 | 행이 12개를 넘으면 **(제안)** 2장으로 나누고 내보내기 결과에 `슬라이드 2장으로 나눴어요` |

- 공통 옵션(SP4 체크): `drop_hidden`(숨긴 행 빼기) · `memo_footnotes`(각주 메모를 `*` 각주로) · `keep_pending_marks`(`[확정 필요]` 표시 유지). 내부 메모는 언제나 빠진다.
- 대응표(`req`)는 `요구사항 대응표` 탭 · 쪽이 먼저, `원문 쪽 번호 표기` 가 켜져 있으면 `원문` 열(`p.{n}`).
- 고객 자료가 든 내보내기(대응표 · 양식)는 파일 메타에 `confidential: true`.

### 4.20 제안서 시트 템플릿 (넘김 받는 쪽, `SectionStep` 섹션 `spec`)

제안서 섹션 `spec`: 이름 `제품 스펙`, 소개 `제안한 제품의 스펙을 정리합니다. 공간별 제품에 들어간 모델로 비교표를 만들었고, Spec 시트 작업이나 제품 탐색에서 끌어 놓아 더할 수 있습니다.`, 기본 시트 `스펙 비교`(SC · SC-A · `제품 3종의 사양 차이를 보여줘요`) · `제품 상세 · QM55C`(SD · SD-A · `주력 제품 1종의 전체 사양이에요`), 옆 자료 `Spec 시트 작업`, 받는 것 `product`, 빠른 요청 `제품별로 나누기` · `영문 스펙`, 딸깍 자동 문구 `공간별 제품 모델로 비교표 생성`. 표준 8번째 · 퀵윈 5번째 섹션, Solution형에는 없음.

| 코드 | 이름 | 언제 | Thumb `kind` | spec 이 넘기는 데이터 모양 | SP4 칩 |
|---|---|---|---|---|---|
| `SC-A` | `사양 비교표 2~5개` | `제품 간 사양 차이를 볼 때` | `specTable` | `{title, columns: [{product_id, model_ref, label, role}], rows: [{row_id, label, highlighted, footnote_mark?, cells: [{text, win, pending}]}], footnotes: [{mark, text}], source_line}` | `사양 비교표` |
| `SC-B` | `요구사항 대응표` | `요구사항 충족을 증명해야 할 때` | `checkTable` | `{title, model_label, columns: ['요구 항목', '고객 요구', model_label, '판정', '원문'?], rows: [{item, requirement, value, verdict: 'pass'\|'fail'\|'unknown', note, page?}], counts: {pass, fail, unknown}}` | `요구사항 대응표` |
| `SD-A` | `그룹별 상세 사양` | `사양 전체를 정리할 때` | `specGroups` | `{title, model_ref, label, groups: [{name, rows: [{label, value, pending}]}], footnotes, source_line}` | `제품별 상세` |
| `SD-B` | `치수 · 설치 정보` | `설치 검토가 필요할 때` | `drawing` | **(제안)** `{model_ref, dims_mm: {w, h, d}, vesa, weight_kg, mounts: string[]}` — 도면 이미지 원천 없음 | (없음 — 제안서가 직접 고를 때 `GET /v1/sheets/{id}/package?templates=SD-B`) |

- 템플릿 · 레이아웃 카탈로그는 export 서비스 소유(`시트 템플릿 카탈로그`). spec 은 코드만 넘긴다.

### 4.21 이미지

Spec 시트와 내보내기에는 이미지 칸이 없다(보드 그대로). 제안서가 `SD-A` 에 제품 사진을 넣고 싶으면 넘김 묶음의 `model_ref` 로 kb 에서 공식 제품 컷(`G4`, ImageMeta 출처 메타 포함 — 셸 §7.2.1 · §9.6 공식 사진 우선)을 직접 고른다. spec 은 이미지를 고르거나 만들지 않는다.

## 6. API 스케치

모든 경로는 서비스 내부 `/v1/...`(게이트웨이 `/api/spec/v1/...`). ARCHITECTURE §3 규약: ID `<접두사>_<ULID>`, ISO 8601 UTC, 오류 `{"error": {"code", "message", "details"}}`, 목록 `?limit=&cursor=` → `{items, next_cursor}`, 오래 걸리는 작업은 `202 {"job_id", "status": "queued"}` 후 SSE · 자원 재조회, 문서형 자원 `version` + `/versions` · `/versions/{n}/restore`, 고객 자료가 든 모델 호출은 `confidential: true`.

**공통 부수효과**: 작업을 만들거나 상태 · 제목 · 단계가 바뀔 때 `PUT /api/workspace/v1/items/{sp_id}` `{feature: 'SP', title, status: ui_status, summary: status_text, route: resume_route, project_id}`. 버전이 오르는 쓰기(`:save`, 편집 커밋, 경고 반영, 생성 완료)는 `If-Match: {version}` 을 받으면 검사(`409 VERSION_CONFLICT`).

## 7. 워크플로(LangGraph)

공통: 그래프마다 SQLite 체크포인터(`thread_id = job_id`, `${DATA_DIR}/spec/checkpoints.sqlite`). 노드 경계에서 취소 플래그(`wm:job:<id>:cancel`)와 조종 메모(`wm:job:<id>:memos`)를 읽는다. 진행은 jobs Stream 이벤트: `progress`(`{pct, eta_s}`) · `step`(`{stage, status: 'done'|'run'|'wait', note}`) · `log`(`{t, text, mode}` 판단 기록) · `result` · `error`(`{code, message}`) · `done`. **`awaiting_input` 은 쓰지 않는다**(묻는 것은 값 확인 · 경고 · 요구 행 자원으로 남김, §3.5). 모델 호출은 모두 ai-tools 경유. 고객 자료(규격서 · 고객사 양식 · 사용자가 올린 데이터시트 · 고객사 이름이 든 문장)가 든 호출은 `confidential: true`. 같은 입력이면 다시 계산하지 않도록 노드 출력에 입력 해시를 남긴다.

### 7.11 결정적 검증 (모든 모델 출력 뒤)

1. **셀 값은 출처 레코드에서만**: 모든 셀 숫자는 카탈로그 행 · 데이터시트 행(`value_raw` 가 쪽 텍스트에 그대로 있음) · 정책 문서 · 사용자 입력 · 파생 계산(입력 id 참조) 중 하나에 묶인다. 어느 LLM 스키마도 셀 값을 직접 쓰지 않는다.
2. **인용 실재**: 요구 항목 `quote` 는 그 쪽 텍스트 안에 있어야 하고, `requirement` 의 숫자는 `quote` 의 숫자 집합 안에 있어야 한다.
3. **판정 근거**: `pass` · `fail` 은 결정적 비교 또는 근거 id 를 인용한 LLM 판정만. 근거 없는 판정은 `unknown`.
4. **모델 이름**: LLM 출력의 모델코드 · 이름은 `KB:A1` · kb 검색 · `lifecycle` 표로 해소될 때만 모델로 쓰고, 아니면 직접 입력(점선)으로.
5. **번역 보존**: 번역 전후 숫자 · 단위 · 모델코드 집합이 같아야 한다. 다르면 원문(한국어) 유지 + 로그.
6. **조작 검사**: 대상이 있는 조작만 반영, 나머지는 `needs_clarification` 으로 돌려줌.
