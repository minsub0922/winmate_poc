## 0. 이 문서 읽는 법

- `"…"` 안의 한국어는 보드 문구 **그대로**다(가운뎃점 ` · `, 화살표 `→`, `—`, 따옴표 `'…'` `“…”` 포함).
- `{…}` 는 데이터 자리. 보드의 숫자 · 고객사 · 문장(예: `요구 12개`, `섹션 11개`, `로비`)은 **예시 데이터**다.
- **(제안)** = 보드에 없지만 구현에 필요해 이 문서가 정한 기본값. 바꾸려면 §11.
- 수용 기준(§9)은 모델 호출이 결정적 mock 이라는 가정에서 구조 · 동작을 검증한다.
- **조사 처리**: 숫자 · 버전 뒤 조사는 발음으로 고른다 — `v{n}을/를`(1·3·6·7·8·10 → 을, 2·4·5·9 → 를), `v{n}로/으로`(3·6·10 → 으로, 그 밖 → 로; ㄹ받침 1·7·8 → 로). 보드 `"스토리보드 v1을 저장했어요"`, `"v2로 계속"`. 공용 `josa()` 유틸을 쓴다.

## 1. 목적과 진입점

### 1.1 목적

저장된 **요구사항 정의서**를 근거로 제안의 뼈대를 만든다: 설정을 정의서에서 읽어 미리 고르고 → 영향 큰 기획 질의 ≤ 3개 → 요구가 빠지지 않는 **기획 방향(추천 조합)** 과 파트별 **핵심 메시지(Key Message)** → **5단 목차**(시작 · Part 1 · Part 2 공간 시나리오 · Part 3 · 마무리)와 서사 → 비어 있는 공간 시나리오만 질문으로 채우기 → **요구 추적**(정의서 항목 ↔ 스토리보드 위치) → **제작 일정 · 분담** → 저장 · 내보내기 · 다음 작업(제안서 · MI · 공간 시나리오)으로 넘기기. 확인 필요한 값은 추정하지 않고 `TBD` · `[확인 필요]` · `[00]` 으로 둔다.

보드 머리 문구(UC_SB): `"전략 수립 Storyboard — 한 화면에 한 가지만"` / `"흐름은 그대로 5단계. 화면마다 할 일 하나, 큰 버튼 하나 — 표 · 지표 · 범례는 '전체 보기' 뒤로 보냈어요."`

## 3. 사용자 흐름

### 3.1 기본 흐름

1. **목록** — SB0 → `"새 스토리보드"` → SB1(또는 RQ4에서 `?rq=` 로 바로 SB1).
2. **불러오기** — SB1에서 정의서를 고른다(미리 선택됨). 스토리보드가 만들어지고 `sb.prepare` 잡이 설정 4항목을 정의서에서 읽고(`"정의서에서 읽었어요"`) 영향 큰 기획 질의 ≤ 3개를 고른다. 필요하면 `"바꾸기"` → SB1S.
3. **기획 질의** — `"다음 · 기획 질의 {n}개"` → SB1Q → SB1Q2 → SB1Q3(한 화면에 질문 하나). 모르면 `"모르겠어요 → 확인 필요로 남기기"`. 마지막 `"기획 방향 만들기"`. 질의를 건너뛰려면 SB1 `"질의 건너뛰고 기획 방향"`.
4. **기획 방향** — `sb.direction` 잡 → SB2: 추천 조합 1 + 축 3, 요구 커버 수. 기본은 추천 조합. 메시지를 손보려면 `"핵심 메시지 고치기"` → SB2E.
5. **목차** — `"이대로 목차 만들기"`(SB2) 또는 `"저장하고 목차 만들기"`(SB2E) → `sb.outline` 잡 → SB3G(진행, 끝나면 자동으로 SB3).
6. **빈 공간 시나리오 채우기** — SB3 Q 배너 `"{공간}부터 채우기"` 또는 SB3P `"질의로 채우기"` → SB3S(빈 칸만, 칸당 질문 하나) → SB3S2(완성 결과) → `"다음 공간 · {공간}"` … 
7. **필요할 때** — `"수정 요청"`(SB3R → SB3R2 → 적용), `"버전"`(SB3V), `"전체 보기"`(SB3D).
8. **요구 추적** — SB3 `"요구 추적 확인"` → SB4T. 정리할 요구가 있으면 `"{n}개 정리하기"` → SB4U 1/n … → SB4U2. 전체는 SB4TD, 확장은 SB4X.
9. **일정 · 공유** — `"일정 · 분담으로"` → SB5 → `"저장하고 공유"` → 버전 저장 → SB4 → `"내보내기"`(SB4E) / `"내부 검토 요청"` / 다음 작업(제안서 · MI · 공간 시나리오).

### 3.4 에이전트 라우팅 규칙

원칙: **정할 수 있는 것은 에이전트가 정하고, 사람은 꼭 필요한 것만 정한다.** 사람이 정하는 화면에는 `Q` 표시가 붙는다(SB1Q · SB1Q2 · SB1Q3 · SB3S · SB3S2 · SB4U · SB4U2, SB3 배너, SB3P 버튼, SB4T 버튼).

| 결정 | 에이전트가 자동으로 | 사람에게 |
|---|---|---|
| 설정 4항목 | 정의서에서 읽어 미리 고름(근거 힌트 표시) | 필요할 때만 SB1S |
| 기획 질의 | 질의 후보 중 정의서로 답할 수 없고 영향 큰 것만 ≤ 3, 선택지 생성, 근거 있으면 미리 선택 | 답하기 / 모름 |
| Intro 여는 방식 | 답에 맞춰 정함(묻지 않음) | 없음(나중에 `추가 논의` 로 검토) |

| 단계 알약 | 진행 중 `"{step}/5 {단계 이름}"`(배경 `#eaeefb`) · 완료 `"완료"` / `"완료 · 공유됨"`(배경 `#f0f2f5`) |

| 상태 | 문장 (보드 예) |
|---|---|
| step 1 | (제안) `"정의서를 고르는 중"` / 질의 중 `"기획 질의 {i} / {n}"` |

| step 3, 빈 공간 있음 | `"{공간 이름 ' · ' 연결} 시나리오가 비어 있어요"` (최대 2개, 넘으면 `" 외 {k}"`) — 예 `"로비 · 라운지 시나리오가 비어 있어요"` |
| step 3, 그 밖 | (제안) `"목차를 다듬는 중"` |
| step 4 | `"정리할 요구 {n}개 · {첫 정리할 요구 short}"` (예 `"정리할 요구 1개 · 반도체 박물관 협업"`) · 0개면 (제안) `"요구 추적 확인 중"` |
| step 5 | `"일정 · 분담 작성 중"` |
| done | (제안) `"v{n} 저장"` |
| shared(다음 작업 넘김) | `"{넘긴 곳 ' · '}로 넘겼어요"` (예 `"제안서 · MI로 넘겼어요"`) · 내보내기만 했으면 (제안) `"내보냈어요"` |

정렬 `updated_at` 내림차순, 커서 페이지 20. 빈 목록 (제안) `"아직 스토리보드가 없어요"` + `"새 스토리보드"`.

## 7. 워크플로 (LangGraph)

### 7.0 공통

- 워커가 `wm:q:storyboard` 소비, 체크포인터 `${DATA_DIR}/storyboard/` SQLite, `thread_id = job_id`, 노드 경계에서 취소 확인.
- LLM = ai-tools **JSON 스키마 응답**, `confidential: true`. **웹 검색은 쓰지 않는다** — 외부 근거 · 수치는 MI로 넘긴다(SB4 `"Market Intelligence"` 카드).
- **사람 확인은 잡 밖**: SB1Q · SB3S · SB3R2 · SB4U 등은 REST로 답을 저장하고 다음 잡을 부른다. awaiting_input을 쓰지 않는 이유는 01-requirements.md §6.4와 같다(며칠 이어지는 세션, 화면 사이 자유 이동, 답 하나는 LLM 없이 저장).
- **결정적 가드**(모든 고객용 문장 출력 뒤):
  1. *숫자 가드* — 정의서 · 기획 답 · 공간 답 · KB 근거에 없는 수치는 `[00]` 로 바꾸고 그 섹션 · 칸을 `확인 필요`.
  2. *주장 가드* — 정규식 목록(`최초`, `국내 최초`, `세계 최초`, `업계 최초`, `유일`, `1위`, `No.1`, `최고`, `최대`, `최소` …)에 출처 없는 문장 → `unverified_claim` 표시(메시지) 또는 `확인 필요`(섹션).
  3. *내부 목표 가드* — 정의서 제작자 의견에서 뽑은 내부 목표 구절 + 사전(`스펙인`, `영업 목표`, `영업목표`, `수주`, `매출 목표`, `점유율`) → 고객용 문장에서 빼고 `internal_memos` 로.
  4. *토큰 보존* — 수정 · 동기화 전후로 `[00]` · `[확인 필요]` 개수와 `reviewing` 줄이 줄면 거절하고 1회 재시도, 그래도 줄면 원래 줄을 유지(`kept` 행).
  5. *추적 완전성* — 정의서 항목은 추적에 정확히 한 번씩, 하나도 버리지 않는다.

#### 7.4.2 섹션 상태(결정적, 위가 우선)

1. `tbd` — `tbd_reason` 있음 → `"TBD"`
2. `needs_confirmation` — 줄에 `[00]`/`[확인 필요]` 토큰, 또는 기획 질의 `unknown` 이 영향, 또는 연결 항목 `needs_confirmation` → `"확인 필요"`
3. `reviewing` — 열린 추가 논의 연결 → `"검토 중"`
4. `writing` — Part 2 섹션에서 5/5 아닌 공간이 있음 → `"작성 중"` (Part 2 섹션은 이 규칙을 1–3보다 먼저 본다)
5. `confirmed` → `"확정"`

#### 7.4.3 묶음 배지(SB3, 최대 2개, 이 순서)

`"작성 중"`(Part 2에 5/5 아닌 공간) · `"미완 {n}"`(0/5 공간 수) · `"확인 필요 {n}"` · `"검토 중 {n}"` · `"TBD"`(1개) / `"TBD {n}"`. 모두 확정이면 배지 없음.

#### 7.4.4 일정(결정적 템플릿 + LLM 담당)

6단계 · D-범위는 템플릿(20장: `D-21~D-17`, `D-16~D-14`, `D-15~D-10`, `D-12~D-6`, `D-5~D-2`, `D-1~D-0`; 12장 · 30장 배율은 §10 제안). 담당 기본값: 1 · 6 `"영업 기획"`, 2 `"영업 · 고객"`, 3 `"사업부 · 관계사"`, 5 `"디자인"`, 4 = 파트별 담당 `"Part 1 영업 기획 · Part 2 솔루션 · Part 3 관계사 협업"`(LLM이 파트 성격으로 조정). 배지: 현재 단계 `"지금"`, 2단계 `"고객 확인 {n}"`.

## 9. 수용 기준

모델 · kb 는 결정적 mock, requirements · workspace · export 는 계약 mock(호출 기록). API 테스트는 `services/storyboard/tests`, E2E는 `web/e2e/storyboard.spec.ts`.

### 9.1 API

1. **생성** — Given 저장된 정의서(v2), When `POST /v1/storyboards {requirement_id}`, Then `201`, `id` `^sb_[0-9A-HJKMNP-TV-Z]{26}$`, `started=false`, `step=1`, `prepare_job_id` 있음; prepare 완료 후 설정 4값 모두 `source="rq"`(mock 근거), 질의 ≤ 3, requirements mock에 `PUT links/storyboard/{sb}` 1회.
2. **초안 재사용** — Given 내 `started=false` 초안, When 다시 `POST /v1/storyboards`, Then 같은 id(`200`).
3. **목록 숨김** — Given 시작 전 초안 1 · 시작된 것 2, When `GET /v1/storyboards`, Then 2개만, `counts.all=2`.
4. **버전 없는 정의서** — When 버전 0 정의서로 생성, Then `422 RQ_NOT_SAVED`.
5. **정의서 바꾸기 잠금** — Given step 2, When `PUT requirement`, Then `409 STAGE_LOCKED`.
6. **질의 답 순서** — When `PUT planning/{q1} {selected_option_ids:[B, A]}`, Then 답 순서 `[B, A]`, 역할 = B→`order_roles[0]`, A→`order_roles[1]`; 빈 요청 `422 NOTHING_SELECTED`.
7. **질의 건너뛰기** — When `POST direction {skip_planning:true}`, Then 모든 답 `unknown=true`, 잡 시작, `started=true`, `step=2`.
8. **기획 방향 구조** — 잡 완료 후 `options` = `combo` 1 + `axis` 3, `recommended_option_id` = combo, 각 `coverage.count ≤ total`, combo 커버 = 축 커버 합집합(결정적 검증).
9. **표현 검사** — Given mock 메시지에 `"국내 최초"` 와 정의서 제작자 의견 구절 `"스펙인"`, Then 플래그 2개: `unverified_claim`(`auto_applied=false`, `suggestion` 있음, 문장 그대로) · `internal_goal`(`auto_applied=true`, 문장에서 빠지고 `internal_memos` 에 있음); `apply` 후 문장에 대체안, `revert` 후 원문 복원.
10. **메시지 편집 재검사** — When `PATCH key-messages/{id} {text:"업계 1위 …"}`, Then 응답에 새 `unverified_claim` 플래그.
11. **목차 잡 이벤트** — `sb.outline` SSE에 `step` 키 순서 `classify → map_axes → write_sections → trace`, `write_sections` 의 `done/total` 증가, 마지막 `done`.
12. **묶음 5 · 섹션** — 결과 `groups` 키 순서 `start, part1, part2, part3, end`; start 섹션 이름 `Overview, Key considerations, Intro`, end `Outro, Timeline`; Part 2 공간 각 5칸.
13. **숫자 가드** — Given mock 섹션 문장에 입력에 없는 `"35%"`, Then 저장된 줄은 `[00]%`, 섹션 상태 `needs_confirmation`.
14. **상태 규칙** — Given mock 결과(tbd_reason 1, 토큰 1, 논의 연결 2, Part 2 0/5 공간 2), Then 섹션 상태 각각 `tbd` / `needs_confirmation` / `reviewing` / Part 2 `writing`, 묶음 배지 Part 2 = `["작성 중", "미완 2"]`.
15. **추적 완전성** — 정의서 항목 N개 → `trace.items` 길이 N, `rq_item_id` 중복 없음, 각 `state ∈ {ok, to_resolve, owner_check}`, `ok + to_resolve + owner_check = N`.
16. **링크 depends_on** — 목차 완료 후 requirements mock `PUT links` 의 `depends_on` 이 `ok` 항목마다 places ≥ 1.
17. **공간 질의 빈 칸만** — Given 로비 0/5 · 회의실 3/5, When 각각 `POST questions`, Then 로비 질문 5개(칸마다 1), 회의실 2개(빈 칸만), 선택지 2–4.
18. **모름 → 고객 질문** — When `PUT slots/exception {unknown:true}`, Then 칸 `state="unknown"` · 문장에 `[확인 필요]`, requirements mock `POST customer-questions` 1회(`origin.kind="storyboard"`, `place_label="Part 2 로비"`); 같은 요청 재시도 시 멱등.
19. **compose** — 완료 후 로비 `status="supplemented"`, 5칸 `filled`, 답에 없던 구간 `ai_added=true` ≥ 0, 지표 모르는 수치 `[00]`, mock이 준 고객 질문 수만큼 requirements 호출, 변경 기록 태그 `author_supplemented`.
20. **수정 요청** — `POST revisions` → 완료 후 `rows` 에 `changed`/`added`/`kept`; `[확인 필요]` 가 든 원래 줄은 `kept` 로 남음(가드 4); `apply` → 작업본 줄 교체 · `ChangeEntry(cause=revision)`; `discard` → 작업본 불변.
21. **수정 경합** — Given 수정안 준비 후 같은 섹션이 동기화로 바뀜, When `apply`, Then `409 REVISION_STALE`.
22. **저장 · 버전** — `POST save` → `201 {version:1}`, `status="done"`, `step=5`; 바로 다시 → `200 {created:false}`; 그 뒤 변경 → `draft_label="v2 초안"`.
23. **비교 · 되돌리기** — Given v1 저장 후 변경 3(유지 1 포함), When `GET compare?from=1&to=draft`, Then 행 4, 유지 행 `revertible=false`; `POST changes/{id}/revert` → 작업본 복원, 다시 비교 시 행 3.
24. **동기화 dry-run** — When `POST requirement-sync {reply_id, dry_run:true}`, Then `SyncPreview.rows` 생성, 작업본 `revision` 불변, requirements `PUT links` 호출 없음.
25. **동기화 반영** — When `{to_version:2, dry_run:false}`, Then 영향 위치만 바뀜(다른 섹션 `lines` 동일), `ChangeEntry.cause.label="요구사항 정의서 v2"`, `requirement_ref.version=2`, requirements `PUT links {rq_version:2}`.
26. **열 때 자동 동기화** — Given requirements 링크 `sync_state="pending"`, When `GET /v1/storyboards/{id}`, Then `active_job.kind="sb.rq_sync"`.
27. **정리 — 놓기** — When `PUT resolution {kind:"place", option_id}`, Then 항목 `state="resolved"`, `link_types` 에 `direct`, `apply_job_id` 있음, 잡 완료 후 대상 섹션 · 공간에 내용 추가 + 변경 기록(`cause=trace`).
28. **정리 — 고객에게 · 제외** — `ask_customer` → requirements 고객 질문 추가, `link_types` 에 `unconfirmed`, `resolved`; `exclude` 사유 없음 `422 REASON_REQUIRED`, 사유 있으면 `resolved` 이고 **trace.items 길이 그대로**(버리지 않음).
29. **확장은 정의서에 안 씀** — 전체 흐름에서 requirements mock에 항목 추가 · 수정 호출(`PATCH draft`) 0회.
30. **일정** — `GET schedule` → 6단계 순서 고정, `d_from ≥ d_to`, 정확히 1단계 `current=true`, 열린 고객 질문 > 0이면 2단계 배지 `"고객 확인 {n}"`.
31. **내보내기 옵션** — `POST exports {format:"pptx", options:{internal_memo:false}}` → export mock 페이로드에 `internal_memos` · 제작자 의견 문장 없음, 마커(`[00]`, `[확인 필요]`, `TBD`) 있음; `internal_memo:true` → 내부 메모 포함 · 파일 이름 `_내부검토`; 작업본 ≠ 최신 버전이면 먼저 저장(버전 +1).
32. **넘기기** — `POST handoffs/proposal` → `status="shared"`, `sub_line` 에 `"제안서"` 포함, 응답 `route` 가 `/proposal/new?sb=…`.
33. **기밀 · 웹 검색 없음** — ai-tools mock 요청 전부 `confidential:true`, 웹 검색 엔드포인트 호출 0회.
34. **오류 형식** — 없는 id → `404 {error:{code:"NOT_FOUND", message}}`.

2. **SB1 미리 선택** — RQ4 `"전략 수립 Storyboard"` → SB1에서 그 정의서 카드 `aria-pressed="true"`, 버전 배지, 둘째 줄 `"요구 {n}개 · 확인 필요 {m}개 · … 저장"`; prepare 동안 설정 줄 스켈레톤 · 주 버튼 비활성, 끝나면 설정 요약(4값 `" · "`)과 `"정의서에서 읽었어요"`, 주 버튼 `"다음 · 기획 질의 {n}개"`.
3. **설정 바꾸기** — `"바꾸기"` → SB1S 분할 버튼 4행, `"약 30장"` 선택 후 `"저장"` → SB1 요약에 `"약 30장"`, `"정의서에서 읽었어요"` 사라짐.
4. **순서 선택** — SB1Q 두 선택지를 차례로 누르면 `1`·`2` 번호와 `"Overview 목적"`·`"Outro 다음 단계"` 라벨, 첫 것을 해제하면 남은 것이 `1` + `"Overview 목적"`; 선택 0이면 `"다음"` 비활성.
5. **꼬리 질문** — SB1Q3 고객사 기존 자산 선택지 클릭 → `"이어서 하나만"` 상자; 칩 선택 전 `"기획 방향 만들기"` 비활성, 선택 후 활성 → SB2 로딩 → 추천 카드(`"추천"` 배지, `"요구 {k} / {N}"`, 매핑 3줄) + 축 카드 3.
6. **메시지 표시** — SB2 `"핵심 메시지 고치기"` → SB2E 블록 3, 표시 구간 강조, `"바꾸기"` 클릭 시 문장이 대체안으로 바뀌고 안내 사라짐, `"되돌리기"` 클릭 시 원문 구절 복귀.
7. **목차 생성 자동 넘김** — `"저장하고 목차 만들기"` → SB3G 단계 4줄(끝 · 진행 `"{i} / {n}"` · 대기), 완료되면 자동으로 SB3; SB3에 묶음 5행, 버전 배지 `"v1 초안"`, 부제 `"… · 섹션 {n}개 · 청중 …"`.
8. **부분 보기** — SB3G `"기다리지 않고 지금까지 쓴 것 보기"` → SB3 표시, 잡 완료 뒤 같은 화면에서 갱신.
9. **빈 공간 채우기** — SB3 Q 배너 `"{공간}부터 채우기"` → SB3S 칸 칩(지금 칸 강조), `"다음"` 반복 → SB3S2 `"{공간} 시나리오 5칸을 채웠어요"`, 점선 밑줄 구간, `[00]`, `"고객에게 물을 것에 {n}개 더했어요 — …"` → `"보기"` 가 RQ5로 감; SB3P에서 그 공간이 `5/5`.
10. **수정 요청** — SB3 `"수정 요청"` → SB3R 기본 고칠 섹션 표시, 글 입력 · 칩 `"비교표로"` 켬 → `"다시 쓰기"` → SB3R2 `"{n}줄이 바뀌어요"`(유지 제외 수), `"적용"` → SB3; `"버전"` 이 저장 전에는 비활성.
11. **버전 비교** — SB5 `"저장하고 공유"` 로 v1 저장 → 수정 하나 적용 → SB3V `"v1 → v2, 바뀐 곳 {n}"`, 행 `"되돌리기"` → 행 사라지고 n 감소, `"v2로 계속"` → SB3.
12. **요구 추적** — SB4T H1 `"요구 {N}개 중 {k}개는 잘 들어갔어요"`, 카드 3 숫자 합 + 담당 확인 = N, `"{n}개 정리하기"` → SB4U `"정리 1 / {n} · RQ-…"`, 한 개씩 답(제외는 사유 입력 전 `"다음"` 비활성) → SB4U2 `"{n}개를 정리했어요"`; SB4TD 행 수 = N, 범례 문구 그대로.
13. **확장** — SB4X 행에 `"확장"`/`"검토 중"` 배지, `"확인했어요"` → SB4T.
14. **일정 · 저장** — SB5 6행, `"지금"` 배지 1개, `"물을 것 보기"` → RQ5; `"저장하고 공유"` → SB4 `"스토리보드 v1을 저장했어요"`, 부제에 `"섹션 {n}개"`, Stepper 모두 체크, 다음에 할 일 3장.
15. **내보내기** — SB4E 기본 PPTX 선택, `"확인 필요 · TBD 표시 유지"` 는 `aria-disabled="true"` 로 끌 수 없음, `"내보내기"` → 다운로드 이벤트 발생(파일 이름에 `_스토리보드_v`).
16. **정의서 v2 반영** — 정의서 RQ7B에서 `"Storyboard {n}곳에도 반영"` 체크 상태로 `"v2로 저장"` → 스토리보드 SB3V에 원인 `"요구사항 정의서 v2"` 행이 보이고 되돌리기 가능. RQ7B `"미리 보기"` → SB3V 미리 보기 모드(되돌리기 없음, `"뒤로"`).
