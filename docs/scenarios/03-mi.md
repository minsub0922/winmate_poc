# 03. Market Intelligence (MI) — 화면 수용 기준

> 대상 보드(webapp1, 18개): `UC_MI` `MI0` `MIR` `MIC` `MI1` `MI2` `MI3` `MI1I` `MI2C` `MI3G` `MI3S` `MI3V` `MI3R` `MI4` `MI2A` `MI1Q` `MI3P` `MI3L`
> 원천: `docs/screens/webapp1/<보드>.dc.html`(보드 끝 로직 클래스의 예시 데이터·상태 포함), canvas 노트 `miRoute`, `docs/ARCHITECTURE.md`, `config/services.yaml`, `winmate-kb/docs/*`
> 이 문서는 mi 서비스(`services/mi/**`)와 웹 모듈(`web/src/features/mi/**`)을 구현하는 코드 에이전트 세션의 수용 기준이다. 애플리케이션 코드는 담지 않는다.

**표기 규칙**

- `백틱` 안은 보드 문구 그대로다. `{변수}` 부분만 데이터로 바뀐다. 문장부호(`·`, `→`, `—`, `“ ”`)와 띄어쓰기도 그대로 쓴다.
- **(제안)** = 보드에 없는 문구·동작으로 이 문서가 정한 것. 구현은 따르되 디자인 검토 대상이다(§11).
- 보드의 예시 수치(`0.94`, `31곳`, `58%` …)는 예시 데이터다. 규칙·임계값의 원천은 §10이다.
- 보드가 `[0]` `[00]` `[0,000]` `[0000]` 처럼 쓴 자리는 "값을 모르는 수치"의 자리표시다. 구현에서는 **모르는 수치는 `[00]`, 모르는 글은 `[확인 필요]`** 로 통일하고, 단위는 남긴다(예: `[00]%`, `[00]억 원`). 모델이 수치를 지어내는 것은 금지다(§7.6).

## 1. 목적과 진입점

### 1.1 목적

고객 요구사항(직접 입력 · Storyboard · 요구사항 정의서 · 첨부한 RFP/회의록/IR)을 기준으로 4개 영역 — **시장조사 · 고객사 · 비즈니스 · 사용자 · 경쟁사 → 삼성 강점** — 을 분석해, **주장(claim)마다 출처와 검증 상태가 붙은 리포트**를 만든다. 결과는 제안서 MI 섹션(시트 + 템플릿), Why Samsung, Value Proposition 재료, Storyboard 근거로 넘긴다.

에이전트가 판단할 수 있는 것은 스스로 정하고(자동 · 확인 권장), 사람은 네 경우에만 답한다(§3.3). 한 화면에는 할 일 하나만 둔다.

## 3. 사용자 흐름

### 3.1 기본 흐름

```
 E1/E2/E4/E5 ─→ MI1 ──[다음 · 분석 설계]──→ design 잡 ─┬─(선택 필요 0)──→ MI2A ──[분석 시작 (약 3분)]──┐
                                                      └─(업종 두 갈래)─→ MI1Q ──[{업종}로 분석 시작]──┤
                                                                                                    ▼
                                         MI3 ←──(자동, 끝나면)── MI3G (run 잡 · 검색 → 정리 → 작성)
                                          │
        ┌───────────────┬─────────────────┼───────────────────┬──────────────────────────────┐
        ▼               ▼                 ▼                   ▼                              ▼
   MI3S(출처 보기)  MI3V(수치 근거   MI3R(경쟁사 추가 분석 ·  MI4(리포트 저장)        [제안서 MI 섹션으로]
     ⇄ MI3V          더 찾기)          후속 수정 요청)                                   ├ 넘길 수 있으면 → 제안서 MI 섹션(PRS1)
                                                                                         └ 물을 것 · 연결 제안서 없음 → MI4
```

- **MI1 다음 기본 화면은 MI2A(자동 설계)** 다. 직접 고르기는 MI2(`범위 직접 고르기`)다 (canvas 노트 `miRoute`).
- 분석이 끝나면 슬라이드 구성(MI3P)은 run 잡 안에서 자동으로 계산돼 있다. 사람은 바꾸고 싶을 때만 MI3P · MI3L 을 연다.
- `제안서 MI 섹션으로`(MI3 기본 버튼)는 **바로 넘길 수 있으면 넘기고**(연결된 제안서가 있고 §3.3 물을 것이 없을 때), 아니면 MI4로 간다(§4 MI3, §11 Q5).

### 3.2 갈래

| 갈래 | 경로 | 조건 · 비고 |
|---|---|---|
| 업종에서 바로 시작 | MI0 업종 칩 / `업종 인사이트로 시작` → MI1I(그 업종 선택) → `이 프리셋으로 분석 범위 선택` → MI2 → (MI2C) → MI3G | 업종은 `고정`. `MI1I에서 고른 요구 항목은 MI1의 요구사항과 MI2C의 비교 기준으로 함께 들어갑니다.` |
| 직접 고르기 | MI1 `직접 고르기` → MI1I → MI2 | 위와 같음 |
| 범위 직접 고르기 | MI2A `범위 직접 고르기` → MI2 → `분석 시작 (약 3분)` → MI3G | 바꾼 값은 `고정` |
| 경쟁사 · 비교 기준 | MI2A `경쟁사 · 비교 기준` / MI2 경쟁사 지정 영역 → MI2C → MI3G | `경쟁사 영역을 빼면 MI2C는 건너뜁니다.` |

### 3.3 라우팅 규칙 (MIR 원문 · 판단 모드)

판단 모드는 4가지다. 화면의 모드 칩 문구는 그대로 쓴다.

| 모드 | 칩 | 뜻(범례) | 동작 |
|---|---|---|---|
| `auto` | `자동` | `진행` | 에이전트가 정하고 진행, 결과에 이유 한 줄 |
| `check` | `확인 권장` | `진행 + 결과에 표시` | 진행하되 결과 화면에 칩으로 남김 |
| `ask` | `선택 필요` | `답 받고 진행` | 답을 받아야 진행 |
| `pin` | `고정` | `사람이 정함` | 사람이 정한 값은 다시 고르지 않음 |

`답이 없으면 추천값으로 진행 · 하나를 바꾸면 그 뒤 단계만 다시 돕니다` — 묻는 화면에는 항상 추천값이 미리 골라져 있고, CTA 를 누르면 그 값으로 진행한다. 결정 하나를 바꾸면 그 결정에 의존하는 뒤 단계만 다시 계산한다(§7.2 의존 해시).

**단계 1 · 입력 판별** — `무엇으로 시작했나 — 직접 입력 · 문서 · 다른 작업 · 업종 칩`

| 신호 | 결정 | 모드 |
|---|---|---|
| `RFP · 회의록 첨부` | `요구 · 평가 기준 · 일정 추출` | 자동 |
| `Storyboard 작업 연결` | `요구사항 · Key Message 상속` | 자동 |
| `업종 칩에서 시작 (MI1I)` | `업종 확정 · 요구 프리셋` | 고정 |
| `이전 MI 작업 · 30일 경과` | `바뀐 자료만 찾아 다시 분석` | 자동 |
| `한 줄 메모뿐` | `사례 DB로 빈칸 추론 · 표시` | 확인 권장 |

**단계 2 · 업종 판별** — `16개 업종 + 범용 · 단서 키워드 · 사례 DB 유사도`

| 신호 | 결정 | 모드 |
|---|---|---|
| `확신 0.80 이상` | `자동 확정` | 자동 |
| `0.50 ~ 0.79` | `진행하고 결과에 업종 확인 칩` | 확인 권장 |
| `1 · 2위 차이 0.10 미만` | `한 번 묻기 (섞어서 보기 포함)` | 선택 필요 |
| `16개 업종 밖 (예: 스크린골프장)` | `범용 레이아웃으로` | 자동 |
| `연결된 Storyboard · 제안서에 업종` | `그대로 상속` | 자동 |

평가 순서(구현 규칙): ① 사람이 정한 업종(MI1I · `바꾸기` · 결과 화면 업종 칩) → `pin` ② 연결된 작업에 **Winmate 업종 코드**가 있으면(다른 MI · 경쟁사 분석 · 제안서 업종 레이아웃) 상속 → `auto`. 정의서 · Storyboard 의 `context.vertical` 은 KB A2 의 KR 업종(`kr_*`, `ask` 표시 포함)이므로: `ask=false` 이고 `segment_mapping` 으로 Winmate 업종 **하나**에 대응하면 상속(`auto`), 아니면 상속하지 않고 §7.3 판별의 근거로만 쓴다 ③ 확신도(§7.3) 1위 < 0.50 → 범용(`GEN`) `auto` ④ 1위 − 2위 < 0.10 → `ask`(MI1Q) ⑤ 1위 ≥ 0.80 → `auto` ⑥ 나머지(0.50 ≤ 1위 < 0.80) → `check`.

비교 정밀도: 확신도는 소수 둘째 자리로 반올림한 뒤 **100배 한 정수**로 비교한다(차이 `85 − 75 = 10` → `< 10` 아님 → 묻지 않음). 부동소수점 그대로 빼면 `0.85 − 0.75 = 0.0999…` 가 되어 판정이 바뀌므로 금지한다(AC-MI-05). 경쟁사 분석(04 문서)의 업종 · 신뢰 비교도 같은 규칙.

**단계 3 · 쓰임 판별** — `결과가 어디로 가나 — 연결된 제안서 유형 · 요청 문구`

| 신호 | 결정(시트) | 모드 |
|---|---|---|
| `표준 제안서 연결` | `MI 섹션 3시트 (시장 · 고객 · 경쟁)` | 자동 |
| `Solution형 연결` | `대규모 MI 5~6시트 + 시사점` | 자동 |
| `퀵윈 연결` | `MI 섹션 없음 → 리포트 + VP 재료로` | 자동 |
| `'경영진 한 장' 요청` | `IM-B 1장 + 부록 2장` | 자동 |
| `연결 없음` | `리포트 · 보낼 때 다시 매핑` | 자동 |

**단계 4 · 범위 · 경쟁사** — `무엇을 얼마나 — 요구 문구 · 공개 자료 양 · 제출 대상`

| 신호 | 결정 | 모드 |
|---|---|---|
| `요구에 '경쟁 · 대체 · 교체'` | `경쟁 영역 포함` | 자동 |
| `'손님 · 직원 · 동선 · 대기'` | `사용자 영역 포함` | 자동 |
| `고객 공개 자료 3건 미만` | `고객사 영역 축소 → CB-A` | 자동 |
| `경쟁사 지정 없음` | `업종 사례 빈도 상위 3곳` | 확인 권장 |
| `고객에게 내는 제안서` | `경쟁사 익명 표기 (A · B · C)` | 자동 |

**단계 5 · 레이아웃 선택 — 시트마다** — `고정한 시트는 건너뜀 → 업종 레이아웃 (16개 업종 × 3장) → 데이터 모양 → 메시지 · 고른 이유는 한 줄로 시트에 남김`. 시트 유형별 표는 §10.5.

**단계 6 · 결측 · 충돌 처리** — `값이 없거나 부딪칠 때 — 먼저 스스로 메우고, 못 메우면 표시해서 남김`

| 신호 | 결정 | 모드 |
|---|---|---|
| `레이아웃에 필요한 값이 없음` | `추가 검색 → 대체 레이아웃 (MS-B → MS-E) + [확정 필요]` | 자동 |
| `사람이 고정한 시트` | `대체하지 않음 · 자리표시 [00] · 확정 필요 목록으로` | 고정 |
| `출처끼리 수치 차이 20% 이상` | `최신 · 공신력 순으로 쓰고 두 값을 함께 표시` | 확인 권장 |
| `24개월 지난 출처` | `제외하고 최신 자료로 대체 · 대체 못 하면 표시` | 자동 |

**사람에게 묻는 경우는 이 넷뿐** (`사람에게 묻는 경우는 이 넷뿐`)

| # | 문구 | 언제 · 어디서 | 답이 없을 때 |
|---|---|---|---|
| 1 | `업종이 두 갈래 — 1 · 2위 차이 0.10 미만` | 분석 전 · design 잡 `awaiting_input` → MI1Q | 추천(1위) 업종 |
| 2 | `경쟁사 실명을 고객에게 내는 제안서에 넣을 때` | 넘길 때(MI3 바로 보내기 · MI4) · 익명 표기가 꺼져 있고 대상이 고객 제출물 | 익명 표기로 넘김 |
| 3 | `사내 대외비 수치를 고객 제출물에 넣을 때` | 넘길 때 · 넘길 시트에 `classification=confidential` 출처 값이 있음 | 그 값은 `[00]` 로 바꾸고 `[확정 필요]` 노트 |
| 4 | `사람이 고정한 시트를 덮어써야 할 때` | 넘길 때(제안서에서 고정된 시트) · 다시 분석 결과 반영 시 | 덮어쓰지 않음 · 확정 필요 목록으로 |

분석 잡(run) 도중에는 사람을 기다리지 않는다. 2~4번은 분석 결과를 넘기는 순간에만 묻고, 다시 분석 중 고정 시트를 만나면 덮어쓰지 않은 채 결정 대기 항목으로 남긴다(MIC 11번 `고정 시트 덮어쓸지` = 고정).

### 3.4 작업 상태

```
draft ──design──→ designing ──┬→ ask(업종 두 갈래, MI1Q) ──answer──┐
                              └→ designed ─────────────────────────┤
                                                                   ▼
                       queued → running ─┬→ done ──30일 재확인(바뀐 자료 있음)──→ upd ──다시 분석──→ queued
                                         ├→ stopped(중지 · 정리된 영역 보존) ──분석 시작──→ queued
                                         └→ failed ──다시 시도──→ queued
```

| 내부 상태 | MI0 상태 칩 | MI0 행 동작 | 사이드바 · 행 링크(route) |
|---|---|---|---|
| `draft`, `designing`, `ask`, `designed`, `stopped` | `작성 중` | `이어서` | 마지막으로 머문 입력 화면(MI1 · MI2 · MI2A · MI1Q · MI2C) |
| `queued`, `running` | `진행 중` | `진행 보기` | MI3G |
| `done` | `완료` | 확정 필요 항목이 남았으면 `수치 확정`(→ MI3V), 없으면 (제안) `열기`(→ MI3) | MI3 (사용자가 MI3V에 머물렀다면 MI3V) |
| `upd` | `업데이트 필요` | `다시 분석` | MI3 |
| `failed` | `작성 중` + 메모 (제안) `분석을 마치지 못했어요` | (제안) `다시 시도` | MI3G |

## 4. 화면별 상세

### 4.0 모든 MI 화면 공통

- **레이아웃**: 1440 × 900 기준. 사이드바 260px + 본문 1180px. 본문은 가운데 한 줄(800~820px), 아래쪽에 입력 카드(대화 입력 + 버튼)를 고정한다. 큰 버튼은 화면마다 하나(오른쪽 아래, 삼성 블루 `#1428a0`).
- **에이전트 말**: 왼쪽 `W` 아바타 + 문장 하나(14.5px). 사용자가 보낸 말은 오른쪽 말풍선.
- **셸**: `Sidebar group="market" current="{작업 제목}"`(작업 전 화면은 빈 값), `TopBar section="Market Intelligence"`. 화면마다 셸 맥락(00-shell.md §7.5) `{section: "Market Intelligence", title, hasTask, accepts: [], added}` 를 넘긴다 — MI0 은 `hasTask=false`(탐색만), 그 밖의 MI 화면은 `hasTask=true`. MI 화면에는 드롭 영역이 없으므로 `accepts` 는 비운다(끌기 손잡이 없음). 웹 모듈은 `onAdd('product' | 'solution' | 'case', refs)` 를 등록한다 — 제품 · 솔루션은 경쟁사 비교의 `삼성` 쪽 제품으로, 사례는 `사내 사례 DB` 출처로 들어간다(§6.13). `image` 는 등록하지 않는다(셸이 그 버튼을 끔).
- **Stepper**: `['고객 요구사항', '분석 범위', '분석 결과']`. MI1 · MI1I = 1, MI2 · MI2A · MI2C · MI1Q = 2, MI3G · MI3 · MI3S · MI3V · MI3R = 3, MI3P · MI3L · MI4 = 3 + `complete`.
- **판단 모드 칩**: §3.3 표의 문구 · 색을 그대로 쓴다(자동 `#eaeefb/#1428a0`, 확인 권장 흰 바탕 + 파란 테두리, 선택 필요 `#121417/흰 글자`, 고정 `#f0f2f5/#3d4452`).
- **경쟁사 이름 표시**(§5.6 `display_name`): 작업 화면 안에서는 `경쟁사 {글자}` 와 실명을 함께 보인다(실명은 회색 보조 글자). 목록 · 사이드바 · 홈 최근 작업 · 공유 링크 · 고객 제출물에는 실명을 쓰지 않는다. 보드는 실명 자리에 글자만 그렸다(§11 Q6).
- **자리표시**: 모르는 수치 `[00]`, 모르는 글 `[확인 필요]`, 확정 전 수치 표시는 `[확정 필요]`.
- **로딩 · 오류**(모든 화면, 제안): 첫 로드 스켈레톤, API 오류 시 화면 위 띠 `잠시 후 다시 시도해 주세요` + `다시 시도`. 422/409 오류는 서버 `error.message`(한국어) 를 그대로 띄운다.

### 4.3 `MIR` — 에이전트 라우팅 규칙 (`/mi/rules`, 읽기 전용 시트)

- **문구**: 머리 `ROUTING · MARKET INTELLIGENCE` / `에이전트가 스스로 정하는 것, 사람에게 묻는 것` / `여섯 단계마다 신호를 읽고 갈 길을 정해요. 오른쪽 아래 네 경우만 사람에게 묻습니다.` 범례 `자동` `진행` · `확인 권장` `진행 + 결과에 표시` · `선택 필요` `답 받고 진행` · `고정` `사람이 정함`. 단계 1~4 · 6 표는 §3.3 그대로(`→ {결정}` 형식). 5 `레이아웃 선택 — 시트마다` · `고정한 시트는 건너뜀 → 업종 레이아웃 (16개 업종 × 3장) → 데이터 모양 → 메시지 · 고른 이유는 한 줄로 시트에 남김` · 열 머리 `시트` / `업종이 정해지면` / `업종 레이아웃이 없거나 업종이 범용이면 — 데이터 모양 → 템플릿` · 밴드 표는 §10.5. 6 `결측 · 충돌 처리` · `값이 없거나 부딪칠 때 — 먼저 스스로 메우고, 못 메우면 표시해서 남김`. 묻는 상자 `사람에게 묻는 경우는 이 넷뿐` + 4항목 + `답이 없으면 추천값으로 진행 · 하나를 바꾸면 그 뒤 단계만 다시 돕니다`.
- **앱에서 숨기는 것**: 설계 캔버스 링크 `유스케이스 맵` · `시나리오 12개 보기` · `묻는 화면 보기`.

**동작**

1. 첫 의미 있는 입력(고객사 · 요구사항 · 파일 · 가져오기) 때 `POST /v1/analyses` 로 작업을 만들고 URL 을 `/mi/:id/input` 으로 바꾼다. 이후 800ms 디바운스 `PATCH`(자동 저장). MI0 에 `작성 중` · `고객 요구사항까지 입력` 으로 보인다.
2. `가져오기` → 웹이 Storyboard 묶음(요구사항 · Key Message · 고객 정보)을 읽어 `POST /v1/analyses/{id}/imports/storyboard` 로 올린다(mi 는 storyboard 를 직접 부를 수 없음, §8). 고객사 · 요구사항 칸이 채워지고 카드는 (제안) `"{SB 제목}" 에서 가져왔어요` 로 바뀐다.
3. `?rq=` 로 들어오면 작업을 바로 만들고(`links.requirements_id`, `rq_version` = 최신 저장 버전) 정의서 스냅숏(`GET /api/requirements/v1/requirements/{rq}/versions/{n}` — `form.customer_name` · `items_flat[]` · 키맨 가중치 · `context`)으로 고객사 · 요구사항(가중치 포함)을 채운다. `form.author_note`(제작자 의견, **internal**)는 요구사항 칸에 넣지 않고 분석 문맥에만 쓴다. 이어서 정의서에 사용 링크를 등록한다: `PUT /api/requirements/v1/requirements/{rq}/links/mi/{mi_id} {title, route, rq_version, depends_on}`(RQ6 `쓰는 곳` 칩용). `?sb=` 도 있으면 2번 가져오기를 자동으로 한다(카드 없이).
4. `직접 고르기` → MI1I(현재 입력 기준 업종 감지).
5. `다음 · 분석 설계` (입력이 하나도 없으면 비활성) → `POST /v1/analyses/{id}/design` (202) → MI2A 로 이동. MI2A 는 design 잡이 끝날 때까지 로딩, `awaiting_input`(업종 두 갈래)이면 MI1Q 로 바꿔 보낸다.

### 4.6 `MI2` — 분석 범위 (`/mi/:id/scope`)

**목적**: 분석할 영역을 사람이 직접 고른다(자동 설계를 바꾸고 싶을 때만).

**표시 데이터**

| 필드 | 형식 | 출처 | 표시 |
|---|---|---|---|
| 고객 요약 칩 | `{고객사} · {업종}` + `· {요구 요약}` | 작업 입력 + 설계(LLM 요약 ≤ 60자) | 예 `A 커피 프랜차이즈 · 리테일/F&B` `· 320개 매장 디지털 메뉴보드 교체, 본사 일괄 관리, 전기료 절감, 프로모션 회전 속도` |

| 선택 수 | 정수 | 클라이언트 | `분석 범위` `· 복수 선택 · {n}개 선택됨 · 2 / 3` |
| 경쟁사 지정 칩 | `{표기} ×` | `analysis.competitors`(삭제 안 된 것) | 경쟁사 영역을 고른 경우에만. 칩 글자는 내보내기 표기 미리보기(§5.6) |

| 영역 키 | 제목(고정) | 설명 템플릿(LLM 실패 시) |
|---|---|---|
| `market` | `비즈니스 시장조사` | `{지역} {업종} {제품군} 시장 규모·성장률, 도입 트렌드, 규제` (예 `국내 F&B 디지털 사이니지 시장 규모·성장률, 도입 트렌드, 규제`) |
| `customer` | `고객사 · 비즈니스 분석` | `{고객사}의 매장 전략, 최근 투자·확장 계획, 운영 구조(직영/가맹)` |
| `user` | `비즈니스 사용자 분석` | `{사용자 유형 나열}의 페르소나와 동선, 현재 불편 지점` |

**문구**: `분석할 범위를 골라주세요. 4개 모두 선택하면 약 3~4분이 걸리고, 결과는 탭으로 나뉘어 제안서 근거 자료로 바로 쓸 수 있습니다.` / `모두 해제` / `경쟁사 지정` / 라벨 `경쟁사 추가`, 자리 `경쟁사 추가…` / `이전` / `분석 시작 (약 3분)`.

**동작**

- 체크 변경 → `PATCH /v1/analyses/{id} {scope, scope_mode:"pin"}`. 0개면 큰 버튼 비활성, `모두 해제` 는 (제안) `모두 선택` 으로 바뀐다.
- 큰 버튼 문구의 시간은 `분석 시작 (약 {m}분)` 으로 계산한다(§10.8).
- 경쟁사 칩 `×` → 그 경쟁사 `removed=true, pinned=true`. `경쟁사 추가…` Enter → `POST /v1/analyses/{id}/competitors {name}`(직접 추가, 고정).
- `경쟁사 지정` 영역(칩 바깥)을 누르면 MI2C(`경쟁사 고르면`).
- `이전` → MI1. `분석 시작` → `POST /v1/analyses/{id}/runs {mode:"full"}` → MI3G.
- MI1I 에서 왔으면 업종 · 요구 프리셋이 이미 고정돼 있다. 설계의 나머지(쓰임 · 경쟁사 · 표기 · 사내 자료 · 깊이)는 화면을 열 때 design 잡을 조용히 돌려 채운다(업종은 고정이므로 묻지 않는다).

### 4.7 `MI3` — 분석 결과 (`/mi/:id/result?tab=`)

**목적**: 영역별 결과를 탭으로 보고, 출처 · 수치 확정 · 부분 수정 · 보내기로 이어간다.

**문구(고정)**: `분석이 끝났습니다. {n}개 영역의 결과를 탭으로 정리했고, 각 항목은 출처와 함께 제안서에 인용할 수 있습니다.` / 탭 `시장조사` · `고객사 · 비즈니스` · `사용자` · `경쟁사 → 삼성 강점` / 아래 막대 `분석 결과` `· 3 / 3 · 완료` · `경쟁사 추가 분석` · `수치 근거 더 찾기` · `한 장 요약` · 라벨 `후속 질문` · 자리 `후속 질문 (예: 가맹점주 입장에서의 도입 장벽은?)` · `aria-label="보내기"` · `리포트 저장` · `제안서 MI 섹션으로`.

**확인 권장 칩 줄**(제안 — MIR "결과에 표시", MI1Q `결과 화면의 업종 칩에서 언제든 바꿀 수 있어요.` 를 구현): 에이전트 말 아래 한 줄.

| 칩 | 보이는 조건 | 누르면 |
|---|---|---|
| `업종 · {업종 short} {점수}` + 모드 칩 | 항상(모드 `check` 면 `확인 권장`) | 업종 선택 시트(MI1Q 선택지 형식). 바꾸면 업종 의존 영역(시장 · 고객 · 사용자)과 레이아웃만 부분 재분석 → MI3R |
| `경쟁사 자동 선정` | 경쟁사 결정 모드가 `check` | MI3R(범위 `경쟁사 탭`) |
| `출처 간 값 다름 {n}` | 충돌 주장 ≥ 1 | MI3S(`확인 필요` 필터) |
| `빈칸 추론 {n}` | 한 줄 메모 입력에서 사례 DB 로 채운 항목 ≥ 1 | 해당 항목 강조 |

**탭 내용**(분석한 영역만 탭으로 보인다. 첫 탭 또는 `?tab=` 선택)

| 탭 | 블록(위→아래) | 데이터 형식 | 주 출처 |
|---|---|---|---|
| `시장조사` | 시장 규모(연도별 막대 + 표), 성장률, 도입 트렌드(제목 · 설명 · `그래서 {고객사}는` 한 줄), 규제 | `size_series[{year, value, unit, claim}]`, `cagr{value, period, claim}`, `trends[{title, desc, implication, claims[]}]`, `regulations[{title, desc, claims[]}]` | 웹 검색 · 수집, KB D2(업종 사례 통계) · E1/E2(업종 메시지) · search |
| `고객사 · 비즈니스` | 한 줄 요약, 전략, 투자 · 확장 계획, 운영 구조(직영 : 가맹 등), 운영 단계별 과제 | `summary`, `strategy[]`, `expansion[]`, `structure{items[]}`, `ops_challenges[{stage, problem, claims[]}]` | 첨부 IR · RFP(파일), 웹, 정의서, KB D1(유사 사례의 요구 · 제약) |
| `사용자` | 페르소나(최대 3: 역할 · 목표 · 불편 · 맥락), 여정(단계 → 접점 → 불편 → 기회), 구성 비율(데이터 있을 때) | `personas[]`, `journey[]`, `composition[]` | KB B1(업종 공간 시퀀스 · 장면), D1, 웹, 요구사항 |
| `경쟁사 → 삼성 강점` | 비교표, `도출된 삼성 강점 {n}`, 출처 요약 줄 | `table{criteria[], columns[], cells}`, `strengths[{title, note, claims[]}]` | 경쟁사: 웹(공개 자료만) · 사용자가 올린 공개 자료. 삼성: KB 스펙 · 솔루션 메시지 · 사례 KPI |

- **비교표**: 열 `요구사항 항목` · 경쟁사 열들(§5.6 화면 표기) · `삼성`(파란 배경 `#eaeefb`, 굵게). 행 = 켜진 비교 기준을 가중치 내림차순(같으면 MI2C 순서). 칸 = 짧은 문장. 모르는 경쟁사 값은 `[00]{단위}` 또는 `[확인 필요]`, 삼성 값은 KB 스펙에서(없으면 `[00]` + 확정 필요 항목).
- **강점**: `도출된 삼성 강점 {n}` + 줄마다 `{강점 제목}` `— {한 줄 근거}`(예 `서버 없는 통합 관리` `— 320개 매장 규모에서 인프라 비용 우위`).
- **출처 요약 줄**: `출처 {n}건 · 사내 사례 DB {a} · 공개 자료 {b}` + 탭에 확정 안 된 수치가 있으면 `· [수치는 검증 후 확정]` + `출처 보기` + `표 복사`(경쟁사 탭만).
- **인용 표시**: 주장 끝에 출처 번호 칩(탭 안에서 1부터, MI3S 와 같은 번호). 칩을 누르면 MI3S(그 주장 선택). `원문 일치`·`확정` 이 아닌 주장의 수치는 점선 밑줄 + 툴팁 `확인 필요`(제안).

**컨트롤 · 동작**

| 요소 | 동작 |

### 4.8 `MI1I` — 업종 인사이트 프리셋 (`/mi/new/industry?segment=`, `/mi/:id/industry`)

**목적**: 업종을 고르면 삼성 도입사례에서 그 업종 고객이 요구한 것 · 많이 쓰인 제품 · 솔루션을 분석 출발점으로 채운다.

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 업종 감지 | `{고객사} →` `{업종 full}` `· {기준}` | 현재 작업 입력으로 `POST /v1/segments/detect`. 기준: `Storyboard '{SB 제목}' 기준` / (제안) `입력한 요구사항 기준` · `정의서 기준`. 입력이 없으면 줄 숨김 |
| 집계 | `· 삼성 도입사례 {allCases}건 · {indCount}개 업종 · 1 / 3` | `GET /v1/segments`(kb 프록시). allCases = 업종별 사례 수 합(보드 198) |
| 업종 타일 16 | `role=radio`, `title="{full}"`, `{short}` + `{n}건` | 같은 목록. 선택 = 파란 테두리 |
| 상세 머리 | `{full}` + `도입사례 {cases}건 기준` | `GET /v1/segments/{code}/insights` |
| 요구 6 | 체크 + `{label}` + `{n}건` + 막대(폭 = n ÷ cases %) | insights `req_types` 상위 6 |
| 많이 쓰인 제품 4 · 솔루션 4 | `{name}` `{n}건` | insights `products` · `solutions` 상위 4. 솔루션이 없으면 `솔루션 없이 제품만 도입` |
| 적용하면 | `고객 요구사항 ← 요구 {k}개` / `경쟁 비교 기준 ← 같은 {k}개` / `제안서 MI 레이아웃 ←` `MI-{코드}-A · B · C` | 클라이언트 계산(k = 체크한 수) |

**문구**: `업종을 고르면 삼성 도입사례에서 그 업종 고객이 요구한 것과 많이 쓰인 제품 · 솔루션을 분석 출발점으로 채워 드려요. 고객사만의 요구사항은 다음 단계에서 더하거나 뺄 수 있어요.` / `업종 감지` / `업종 인사이트 프리셋` / `직접 입력으로` / 라벨 `업종 검색`, 자리 `업종 검색 (예: 호텔, 무인 매장)` / `이 업종 고객이 요구한 것` · `분석에 넣을 항목 {k}개` / `많이 쓰인 제품` / `많이 쓰인 솔루션` / `적용하면` / `사례 수는 도입사례 본문을 자동 분류한 값이에요. 업종 하나에 사례 하나씩 셉니다.` / `직접 입력` / `이 프리셋으로 분석 범위 선택`.

**동작**

- 처음 선택 업종: `?segment=` → 감지 업종 → 첫 타일(`FB`).
- 검색: full · short · 별칭(예 `무인 매장`→SV, `호텔`→HT)으로 타일을 거른다. 결과 없음 (제안) `맞는 업종이 없어요 · 범용으로 분석해요`.
- 요구 체크: 기본으로 위 **4개**가 켜진다. 업종을 바꾸면 그 업종 기본값으로.
- `이 프리셋으로 분석 범위 선택` → (작업이 없으면 만들고) `PATCH /v1/analyses/{id} {segment:{code, mode:"pin"}, preset:{segment, req_items[]}}` → 요구 항목은 `requirements[]`(origin `preset`)에, 같은 항목은 비교 기준(출처 `업종 사례 {n}건`, 가중치 2)으로, 레이아웃 후보는 `MI-{코드}-A · B · C` 로 → MI2.
- `직접 입력` · `직접 입력으로` → MI1(적용 안 함).

**데이터 출처 주의**: 업종별 사례 수 · 요구 유형 · 제품 · 솔루션 집계는 "사례 1건 = 업종 1개" 분류표가 필요하다. 지금 KB 에는 이 분류표(보드 주석의 `data/industry_matrix.json`)와 요구 태그 R01~R24 의 한국어 이름표가 없다 → kb 서비스 요청(§8, §11 Q2).

### 4.9 `MI2C` — 경쟁사 · 비교 기준 설정 (`/mi/:id/competitors`)

**목적**: 비교할 경쟁사와 기준 · 가중치, 제안서 익명 표기를 정한다.

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 사용자 말풍선 | 문자열 | 이 작업에 마지막으로 보낸 설계 메모(MI2A · MI3G). 없으면 숨김 (예 `경쟁사는 두세 곳, 본사 통합 관리와 전기료를 가장 중요하게 봐 주세요.`) |
| 경쟁사 목록 | 행: 글자 칩 · 표기 · 태그 · 설명 · 빼기 | `analysis.competitors`(`removed=false`) |
| 집계 | `· {n}곳` · `자동 추천 {a} · 직접 추가 {b}` | 같은 목록 |
| 익명 표기 | 스위치 + 방식 | `analysis.anonymize`, `naming_mode` |
| 비교 기준 | 행: 이름 · 출처 칩 · 가중치 5칸 · `{pct}%` | `analysis.criteria` |
| 추천 기준 | `+` `{name}` `{n}건` 최대 2 | 업종 insights 의 요구 유형 중 아직 기준에 없는 것 |

- **행 표기 규칙(보드 로직)**: 익명 켜짐 + 방식 `letter` → `경쟁사 {글자}` · 설명 `{유형} · {설명}` / 익명 켜짐 + 방식 `type` → `{유형}`(예 `국내 대형 가전 · 사이니지`) · 설명 `{설명}` / 익명 꺼짐 → `{실명} · 사내용`(보드 `[실명] · 사내용`) · 설명 `{유형} · {설명}`. 작업 화면이므로 익명이 켜져 있어도 실명을 보조 글자로 함께 보인다(§4.0).
- **태그**: `자동 추천`(파란 칩) / `직접 추가`(회색 칩).
- **기준 출처 칩**: `요구사항`(파란) / `업종 사례 {n}건` / `직접 추가`(회색).
- **가중치 → 비율**: 가중치 w(1~5). 마지막 행을 뺀 행 i 는 `round(w_i ÷ Σw × 100)`, 마지막 행은 `100 − 앞 행 합` → 합계가 늘 `100%`.

**문구**: `비교할 경쟁사와 기준을 정리했어요. 가중치가 높은 기준부터 비교표에 놓고, 삼성 강점도 그 순서로 뽑습니다. 제안서와 내보내기에는 경쟁사를 익명으로 표기해요.` / `경쟁사 · 비교 기준` `· 경쟁사 분석 → 삼성 강점 · 2 / 3` / `분석 범위로` / `비교할 경쟁사` / 라벨 `경쟁사 추가`, 자리 `경쟁사 추가 (회사명 · 제품명)` / 스위치 `aria-label="제안서에 익명으로 표기"` · `제안서에 익명으로 표기` · `분석에는 실명을 쓰고, 제안서 · PDF · 공유 링크에는 아래 표기로 바꿔요. 경쟁사 로고와 제품 사진은 넣지 않아요.` / 방식(`role=radiogroup`, `aria-label="익명 표기 방식"`) `경쟁사 A · B · C` · `유형으로 표기` / `비교 기준 · 가중치` · `끌어서 순서 변경 · 합계` · `100%` / 가중치 칸 `aria-label="{기준} 가중치 {lv}"`, 묶음 `aria-label="{기준} 가중치 {w} / 5"` / `기준 직접 추가` / `{업종 short} 도입사례 {n}건에서 많이 요구된 기준` / `가중치는 비교표 순서와 강점 도출에만 써요. 경쟁사 수치는 공개 자료로만 채우고, 못 찾으면 [확인 필요]로 남깁니다.` / `이전` / `분석 시작 (약 3분)`.

**동작**

| 요소 | 동작 |
|---|---|
| 경쟁사 추가 Enter | `POST /v1/analyses/{id}/competitors {name}` → 202(짧은 잡: 이름 정규화 + 유형 · 설명 한 줄 찾기) → 행 추가(`직접 추가`, `pinned=true`). 이미 있는 이름 (제안) `이미 있는 경쟁사예요` |
| 빼기(`aria-label="경쟁사 {글자} 빼기"`) | `removed=true, pinned=true` — 다시 분석해도 돌아오지 않는다 |
| 익명 스위치 | `PATCH {anonymize}` · 꺼지면 방식 버튼이 회색(`#9aa1ad`)이 되고 고를 수 없다 |
| 방식 | `PATCH {naming_mode: "letter"\|"type"}` |

### 4.11 `MI3S` — 출처 · 근거 패널 (`/mi/:id/result?tab=&panel=sources&claim=`)

- **번호**: 탭 안에서 첫 인용 순서로 1, 2, …. 같은 출처는 탭 안에서 같은 번호.
- **원문 열기**: URL 이 있는 출처만. 새 탭. 수집본과 현재 페이지가 다를 수 있으므로 (제안) 카드에 `수집본 보기`(저장된 텍스트 스냅숏)를 함께 둔다.
- **각주로 복사** 형식: `{발행처}, 「{제목}」, {YYYY.MM}, p.{n}, {URL} (확인 {YYYY-MM-DD})` — 비는 칸은 뺀다. 웹 검색 요약은 `웹 검색 요약, "{검색어}", 검색 {YYYY-MM-DD} (원문 미확인)`.
- **출처 목록 복사**: 이 탭 출처를 번호순 각주 형식으로 여러 줄.
- **근거 질문**: `POST /v1/analyses/{id}/questions {text, tab, claim_id?}` → 저장된 출처 스냅숏 · KB 에서만 답(새 검색 없음). 답 못 하면 (제안) `저장된 출처로는 답할 수 없어요`.
- **다른 출처 찾기**: 그 주장 하나를 범위로 부분 재분석 안을 만든다(`POST /v1/analyses/{id}/revisions {scope:{kind:"claims", ids:[clm]}, instruction:"다른 출처 찾기"}`) → MI3R.
- **값 직접 확정**: → MI3V(그 주장의 확정 필요 항목에 초점).
- **이 출처 빼기**: `DELETE /v1/analyses/{id}/claims/{clm}/sources/{src}` → 주장 상태 다시 계산(남은 출처가 모두 일치면 `원문 일치`). 마지막 출처를 빼면 주장 상태 `missing`(확정 필요).
- **출처 직접 추가**: (제안) 패널 안 작은 폼 — URL 입력 또는 파일 선택(분류 `사내 자료`/`고객 자료`/`대외비`) → `POST /v1/analyses/{id}/sources {url | file_id, classification, claim_id?}` (202) → 수집 · 대조 후 카드로 나타난다.
- **익명화**: 패널은 작업 화면이므로 실명 출처 제목(경쟁사 제품 페이지 등)을 그대로 보인다. `출처 목록 복사` · `각주로 복사` 는 내보내기 표기를 따르지 않는다(사내용 복사) — (제안) 복사 직후 토스트 `실명이 들어 있어요 · 고객 문서에는 익명 표기로 넣어 주세요`.

### 4.12 `MI3V` — 확정 필요 수치 · 사내 자료 (`/mi/:id/verify`)

**목적**: 제안서에 넣기 전에 확정이 필요한 값을 한곳에서 처리한다. 값 입력 · 사내 자료 업로드 · 말로 알려주기.

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 에이전트 말 | `제안서에 넣기 전에 확정이 필요한 값이 {n}건 있습니다. 값을 직접 넣거나 사내 자료를 올려주시면 해당 문장에 반영하고, 출처를 그 자료로 바꿔 둡니다.` | n = 열린 항목 + 확정한 항목(전체) |
| 머리 | `검증 목록` · `{확정 수} / {전체}` · `확정 · 확인 중 {확인 중 수}` | `GET /v1/analyses/{id}/fix-items` |
| 보기(`role=tablist`, `aria-label="보기"`) | `전체 {n}` · `남은 것 {m}` · `확정 {k}` | 같은 목록 |
| 열 머리 | `항목 · 근거 상태` · `확정 값` · `자료 · 다음 할 일` | |
| 행 | 아이콘(삼각형 warn · 체크 ok · 시계 wait) · `{항목}` · 탭 칩 `{탭}` · `{근거 상태}` · 값칸 · 동작 | §5.5 |
| 값칸(입력형) | 입력(`aria-label="{항목} 확정 값"`, 자리 `값 입력` 또는 `직영 : 가맹`) + 단위(`%` · `억 원` · `W` …) | 항목 `unit`, `input_kind` |
| 값칸(파일형) | 파일 칩 `{파일 이름}` + 읽는 중이면 회전 아이콘 | 항목 `file_id` |
| 동작 | 링크/버튼 | 아래 표 |
| 업로드 | `사내 자료 올리기` `· PDF · XLSX · PPTX` · `내부 시장조사 · 구축 결과 보고서 · 고객 제공 자료를 끌어다 놓으면 위 항목의 값을 찾아 채웁니다` · `파일 선택` · 행마다 첨부 버튼(`aria-label="{항목} 근거 파일 첨부"`, `title="파일로 확정"`) | |

**근거 상태 문구(템플릿)**

| 원인 | 문구 |
|---|---|
| 일부 출처에만 수치 | `출처 {n}건 중 {k}건만 수치가 있음` |
| 출처 간 값 차이 ≥ 20% | `출처 {n}건의 값이 서로 다름` |
| 사내 파일로 확정 | `사내 자료로 확정 · p.{n} 근거` (파란 굵은 글자, 행 배경 연파랑) |

| 삼성 스펙이 KB 에 없음 | `사내 스펙 값 필요` |

| 직접 입력으로 확정 | (제안) `직접 입력으로 확정 · {이름}` |

**행 동작**

| 동작 | 보이는 경우 | 이동 · 호출 |
|---|---|---|
| `출처 보기` | 일부 출처에만 수치 | → MI3S(그 주장) |
| `출처 비교` | 값 차이 | → MI3S(그 주장, 두 출처 카드) |
| `되돌리기` | 확정됨 | `POST .../fix-items/{fix}/revert` → 이전 상태 |
| `고객 질문 복사` | 고객만 아는 값 | 클립보드에 질문 문장(LLM 생성, 예 (제안) `A 커피의 직영점과 가맹점 비율을 알려 주실 수 있을까요?`) |
| `Spec 시트에서` | 삼성 스펙 없음 | → Spec 시트(SP0, 그 모델 미리 채움) |
| `취소` | 파일 읽는 중 | `POST /api/jobs/v1/jobs/{job}/cancel` |

**문구**: `수치 확정` `· 남은 {m}건` / 체크 `남은 값은 [확정 필요]로 표시하고 제안서의 사실 확인 목록에 넘기기`(기본 켬) / 라벨 `값 알려주기`, 자리 `말로 알려주셔도 돼요 (예: 시장 규모는 내부 보고서 기준으로)` / `출처 패널` / `확정값 반영하고 결과 보기`.

**동작**

1. 값 입력 후 포커스 이동 → `PATCH /v1/analyses/{id}/fix-items/{fix} {value, unit}` → 숫자 검증(쉼표 · 소수 허용, 비율형 `a : b`) → `status=ok`, 출처 `user`.
2. 파일 올림(업로드 영역 또는 행 첨부) → files 업로드 → `POST /v1/analyses/{id}/fix-items/scan {file_id, classification, fix_ids?}` (202, `mi.fixscan`) → 해당 행 `wait` · `올린 … 에서 값을 찾는 중` → 값을 찾으면 페이지 원문 대조(§7.6) 후 `ok` · `사내 자료로 확정 · p.{n} 근거`, 못 찾으면 원래 상태 + (제안) `올린 자료에 이 값이 없어요`. 분류 기본 `internal`, 사용자가 `대외비` 를 고르면 `confidential`(넘길 때 묻기 3).
3. `값 알려주기` → `POST .../fix-items/parse {text}` → LLM 이 항목 · 값 · 근거를 짝지어 제안 → (제안) 행마다 `제안 값` 표시 · 행 클릭으로 수락(자동 확정하지 않음).
4. `확정값 반영하고 결과 보기` → `POST .../fix-items/apply {carry_remaining}` → 확정 값을 주장 문장 · 표 칸 · 시트에 반영하고 출처를 그 자료로 바꾼 새 버전(`kind=fix`) → MI3. `carry_remaining=true` 면 남은 항목이 넘김 묶음의 `fact_check[]` 로 들어간다(제안서 확정 필요 목록 PR7Q).

**삼성 쪽 값의 자동 처리**: 삼성 제품 수치(소비전력 · 밝기 등)는 분석 단계에서 KB 스펙(`spec_value`, T2)으로 먼저 채우고 `원문 일치` 로 둔다. KB 에 없을 때만 `사내 스펙 값 필요` 항목이 생긴다. 같은 정규 키에 값이 여럿이면(예 소비전력 `154 W` 와 대기 `0.5 W`) 속성 이름으로 고르고, 고르지 못하면 항목으로 남긴다.

### 4.13 `MI3R` — 부분 재분석 · 대화형 수정 (`/mi/:id/revise?rev=`)

**목적**: 영역 · 행 · 강점 문장만 다시 분석하거나 대화로 고친다. 결과는 바로 반영하지 않고 **변경 안**으로 보여 준 뒤 적용한다.

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 요청 말풍선 | `{범위 이름}` + `· {요청 문장}` (예 `경쟁사 탭` `· 경쟁사 비교에 유지보수 · AS를 넣고, 저전력은 사내 스펙 기준으로 바꿔줘`) | `revision.instruction`, `scope` |
| 에이전트 말 | 범위 `area`: `{탭} 탭만 다시 분석했습니다. 다른 {k}개 탭은 그대로이고, 바뀐 곳은 파란 표시로 남겨 두었어요.` / `rows`: (제안) `선택한 행 {n}개만 다시 분석했습니다. 바뀐 곳은 파란 표시로 남겨 두었어요.` / `strengths`: (제안) `강점 문장만 다시 썼습니다. 바뀐 곳은 파란 표시로 남겨 두었어요.` / `claims`: (제안) `이 주장의 출처를 다시 찾았습니다.` | |
| 탭 | MI3 와 같음, 범위 탭 선택 | |
| 재분석 요약 | `재분석` 칩 · `바뀐 곳 {n}` · 변경 칩(`행 추가 {a}` · `값 수정 {b}` · `강점 수정 {c}`, 그 밖 (제안) `행 삭제 {d}` · `문장 수정 {e}`) · `· 출처 +{k} · {s}초` | `revision.changes`, `sources_added`, `duration_s` |
| 변경 표시 | 수정 칸: `수정` 칩(파랑) + 새 값 + 옛 값 취소선(회색) + `되돌리기` / 추가 행: `추가` 칩 + `빼기`, 행 배경 연파랑 / 강점: `수정` 칩 + `강점 · {제목}` + `— {새 근거}` + `되돌리기` | `change.kind/before/after` |
| 출처 줄 | `출처 {n}건 (+{k}) · 사내 스펙 {a} · 공개 자료 {b} · 사내 사례 DB {c}` + 출처가 없는 칸이 있으면 `· {대상} {항목}은 출처 없음`(예 `경쟁사 B 정책은 출처 없음`) + `출처 보기` | |

**문구**: `전체 다시 분석` / `전부 되돌리기` / `다시 분석할 범위`(`role=radiogroup`, `aria-label="다시 분석할 범위"`) · `{탭} 탭` · `선택한 행 {n}` · `강점 문장만` / 빠른 요청 `더 간결하게` · `{경쟁사 표기} 빼기` / 라벨 `수정 요청`, 자리 `이어서 수정 요청 (예: 경쟁사 B 정책은 출처 찾아서 채워줘)` / `적용 안 함` / `변경 {n}건 적용`.

**동작**

| 요소 | 동작 |
|---|---|
| 진입(새 요청) | `POST /v1/analyses/{id}/revisions {scope, instruction}` (202, `mi.revise`) → (제안) 표 자리에 `다시 분석하는 중 · 약 {s}초` → `proposed` 가 되면 변경 표시 |
| 범위 라디오 | 다음 요청의 범위. `선택한 행 {n}` 은 표에서 행을 고르면(제안: 행 앞 체크) 켜진다 |
| 수정 요청 · 빠른 요청 | 같은 변경 안에 라운드를 더한다(`POST /revisions/{rev}/rounds {instruction, scope}`) — 변경 목록은 늘 **기준 버전 대비 누적 차이** |
| 빠른 요청 만들기 | `더 간결하게` 는 항상. 두 번째는 LLM 이 변경 안을 보고 하나 제안(예 출처 없는 칸이 가장 많은 경쟁사 → `경쟁사 B 빼기`) |
| `되돌리기` · `빼기` | `PATCH /revisions/{rev}/changes/{chg} {reverted:true}` → 적용 수 다시 계산 |
| `전부 되돌리기` | 모든 변경 `reverted` → 큰 버튼 비활성((제안) `적용할 변경이 없어요`) |
| `전체 다시 분석` | 변경 안 폐기 확인 없이 `POST runs {mode:"full"}` → MI3G |
| `적용 안 함` | `POST /revisions/{rev}/discard` → MI3 |
| `변경 {n}건 적용` | `POST /revisions/{rev}/apply` → 되돌리지 않은 변경만 반영한 새 버전(`kind=revision`) → MI3(그 탭) |

**규칙**: 범위 밖 탭 · 행은 절대 바뀌지 않는다(AC). 사람이 고정한 시트에 걸린 값이 바뀌면 적용 때 묻기 4번을 넘김 시점으로 미룬다(제안서 고정 시트는 덮어쓰지 않음).

|---|---|---|---|
| `업종` | `{업종 full short} ({코드}) · {확신도}` (예 `외식 · 카페 (FB) · 0.94`) · 범용이면 (제안) `범용 · 16개 업종 밖` · 상속이면 (제안) `{업종} ({코드}) · 상속` | `{단서 나열} 단서 일치` (예 `프랜차이즈 · 가맹점 · 메뉴보드 단서 일치`) | MI1Q(선택지 화면, 현재 값 선택 상태) |

| `사내 자료` | `도입사례 {n}건 · {제외한 자료} 제외` | `대외비 수치는 고객 제출물에 넣지 않음` | (제안) 사내 자료 고르기 시트(보드는 MI3S 로 링크) |
| `깊이` | `약 {m}분 · 출처 {n}곳 내외` | `3시트 분량 조사량 · 대규모 MI면 2배` | MI2 |

**시트 미리보기 카드**: 업종 레이아웃이면 메모 `업종 레이아웃`(파랑), 범용이면 `범용 · {경쟁사 수}사 × {기준 수}기준`(회색). 보드 예: `시장 · 트렌드` `MI-FB-A` / `고객 비즈니스` `MI-FB-B` / `경쟁 환경` `CP-A`.

**문구**: 아래 막대 `분석 설계` `· 2 / 3 · 바꿀 것만 고르세요` · `범위 직접 고르기`(→ MI2) · `경쟁사 · 비교 기준`(→ MI2C) · `판단 규칙`(→ MIR 시트) · 라벨 `설계에 덧붙일 말`, 자리 `설계에 덧붙일 말 (예: 경쟁사는 클라우드 CMS 업체 위주로)` · `이전`(→ MI1) · `분석 시작 (약 3분)`.

**동작**

- 진입 시 design 잡이 돌고 있으면 (제안) 결정 행 자리에 `요구사항과 연결된 자료를 읽고 있어요` + 진행 단계(`step` 이벤트) 를 보인다. `awaiting_input` 이면 MI1Q 로 바꿔 보낸다.
- `바꾸기` 로 값을 바꾸면 그 행 모드가 `고정` 이 되고, 그 결정에 의존하는 행만 다시 계산한다(예 업종을 바꾸면 시트 미리보기 · 사내 자료 · 경쟁사, 범위를 바꾸면 깊이 · 시트).
- 메모 보내기 → `POST /v1/analyses/{id}/design/memo {text}` (202) → 영향받은 행만 바뀌고 (제안) 바뀐 행 배경을 잠깐 연파랑으로 강조.
- `분석 시작 (약 3분)` → `POST runs {mode:"full"}` → MI3G.

### 4.16 `MI1Q` — 업종이 두 갈래일 때 한 번 묻기 (`/mi/:id/design/industry`)

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 에이전트 말 | `{입력 종류}을/를 읽어 보니 업종이 두 갈래로 읽혀요. 업종에 따라 시장 · 비즈니스 · 사용자 레이아웃이 통째로 달라져서, 이것 하나만 여쭤볼게요.` — 입력 종류: `회의록` · `RFP` · `요구사항` · `메모`(받침에 따라 `을`/`를`) | 첨부 분류 · 입력 |
| 질문 카드 | `선택 필요` 칩 · `어느 업종 관점으로 분석할까요?` · `1 · 2위 차이` `{diff}` `· 기준 0.10 미만` | `awaiting_input.data` |
| 읽힌 단서 | 칩 `{단서}` + 업종 코드 태그(1위 업종 = 파란 채움, 나머지 = 회색) | 업종 판별 `clues[]` |
| 선택지 3 | 라디오 · `{이름}` · `추천`(1위만) · `{설명}` · 점수(소수 둘째 자리) + 막대(폭 = 점수 × 100%) · `{레이아웃 코드}` · 썸네일 3(barline · process · journey) | 아래 규칙 |
| 기본 안내 | `답이 없으면 추천({1위 이름})으로 진행하고, 결과 화면의 업종 칩에서 언제든 바꿀 수 있어요.` | |
| 자동으로 정한 것 | 4줄: `쓰임 · {값}` / `범위 · {n}개 영역` / `경쟁사 · {표기 방식} {표기 나열}` / `사내 자료 · {요약}` (예 `사내 자료 · 호텔 17 + 외식 23건`) | 다른 설계 결정 |
| 아래 막대 | `업종 확인` `· 선택 필요 1 · 나머지 {k}개는 자동으로 정했어요` (k = 업종을 뺀 결정 수, 보드 6) | |

**선택지 규칙**

| 선택지 | 이름 | 설명(템플릿) | 점수 | 레이아웃 |
|---|---|---|---|---|
| 1위 | `{업종 full short}` + `추천` | `{업종 관점 설명}. 사례 {n}건` (예 `호텔 운영 관점 — 로비 · 객실 경험, 투숙객 여정, 호텔 매출 구조. 사례 17건`) | 1위 확신도 | `MI-{1위}-A · B · C` |
| 2위 | `{업종}` | 같은 형식 | 2위 확신도 | `MI-{2위}-A · B · C` |
| 섞어서 보기 | `섞어서 보기` | `시장 · 비즈니스는 {1위 짧은 이름}로, 사용자 여정은 {2위 쪽 사용자}으로` | `round((1위 + 2위) ÷ 2, 2)` | `MI-{1위}-A · B + MI-{2위}-C` |

업종 관점 설명(`{…} 관점 — …`)은 업종별 고정 문장(서비스 설정 `segments.yaml`)이다.

**문구**: `언제 묻는지 보기`(→ MIR 시트) · 라벨 `판단에 도움이 될 말`, 자리 `판단에 도움이 될 말 (예: 결재는 호텔 F&B 팀장)` · `이전` · 큰 버튼 `{선택지 이름}로 분석 시작`(받침에 따라 `로`/`으로`, 예 `호텔 · 리조트로 분석 시작`).

**동작**

- 기본 선택 = 추천(1위). 큰 버튼 문구는 고른 선택지를 따라 바뀐다.
- `판단에 도움이 될 말` 보내기 → 같은 design 잡에 메모로 넣고 업종 판별만 다시(힌트 포함) → 점수 · 추천이 바뀔 수 있다. 차이가 0.10 이상이 돼도 이 화면에 남는다(사용자가 CTA 로 확정).
- 큰 버튼 → `POST /api/jobs/v1/jobs/{job_id}/input {value:{segment:"HT"|"FB"|..., mix:{a:"HT", c:"FB"}|null, start_analysis:true}}` → design 잡이 업종을 `pin` 으로 확정하고 나머지 설계를 마친 뒤 run 잡을 만들어 `result.data.next_job_id` 를 낸다 → MI3G.
- `이전` → MI1(design 잡은 `awaiting_input` 그대로, 다시 `다음 · 분석 설계` 를 누르면 기존 잡을 취소하고 새로 시작).

### 4.17 `MI3P` — 결과 → 슬라이드 구성 (`/mi/:id/slides`)

**목적**: 분석 결과의 데이터 모양을 보고 시트마다 고른 레이아웃과 그 이유를 보여 준다. 사람은 바꿀 때만 본다.

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 에이전트 말 | `분석 결과의 데이터 모양을 보고 시트마다 레이아웃을 골랐어요. 업종 레이아웃이 있으면 그것부터, 없으면 데이터 모양과 메시지로 골랐습니다.` | |
| 머리 | `슬라이드 구성` · `{제안서 유형} MI 섹션 {n}시트 + 넣으면 좋은 시트 {k}` · `업종 레이아웃` `{a}` `· 범용` `{b}` | `GET /v1/analyses/{id}/slides` |
| 시트 행 | 체크(`aria-label="{시트} 시트 넣기"`) · `{시트}` · `{결과 출처}`(`MI 결과 · {탭}` 또는 `{n}개 탭 종합`) · 모드 칩 · 썸네일 · `{코드}` `{템플릿 이름}` · `업종` 표시 · `{이유}` · `데이터 적합` `{fit}%` + 막대(≥ 85 파랑 `#1428a0`, 미만 회색 `#8a91a0`) · `대안` `{코드} {fit}%` / `{코드} 불가` | 시트 구성 `sht_` |
| 고르는 순서 | `1 고정한 시트는 그대로` → `2 업종 레이아웃` → `3 데이터 모양` → `4 메시지 (왜 · 얼마나 · 누구)` | 고정 |
| 아래 막대 | `슬라이드 구성` `· {n}시트 · 넣으면 좋은 시트 {k} · 자동 {a} · 확인 권장 {b}` | |

- **포함 기본값**: 쓰임이 정한 시트(§10.4)는 켜짐(`자동`). 분석은 했지만 섹션에 없는 시트는 꺼짐 + `확인 권장`(넣으면 좋은 시트). `MI 시사점`(IM)은 표준에서 꺼짐 + `자동`(보드 이유 `표준은 3시트라 뺐어요 · Solution형이거나 경영진 보고면 자동으로 넣어요`).
- **이유 문장**: 규칙 + 데이터 요약으로 만든다(예 `업종 레이아웃 우선 · 연도별 시장 규모 6개년과 트렌드 4개가 이 틀에 그대로 들어가요`, `업종 틀엔 경쟁 장이 없어 범용 · 경쟁사 3곳 × 요구 기준 5개라 표가 가장 정확해요`).

**문구**: `레이아웃 바꾸기`(→ MI3L, 마지막으로 고른 행 · 없으면 첫 행) · `출처 보기`(→ MI3S) · 라벨 `구성 요청`, 자리 `구성 요청 (예: 경쟁 환경은 포지셔닝 맵으로)` · `결과로`(→ MI3) · `제안서로 보내기`(→ MI4).

**동작**: 체크 → `PATCH /v1/analyses/{id}/slides/{sht} {included, pinned:true}`. 대안 코드를 누르면(제안) 그 템플릿으로 바꾸고 `고정`. 구성 요청 → `POST /slides/requests {text}` → 레이아웃 요청이면 MI3L(그 시트), 포함 · 제외 요청이면 바로 반영.

### 4.18 `MI3L` — 레이아웃 바꾸기 · 데이터 적합도 (`/mi/:id/slides/:sheet`)

**목적**: 요청한 레이아웃에 데이터가 모자랄 때 선택지(데이터를 더 찾기 · 그대로 쓰기 · 유지)와 적합도를 보여 준다.

**표시 데이터**

| 필드 | 형식 | 출처 |
|---|---|---|
| 요청 말풍선 | 사용자 요청(예 `경쟁 환경은 포지셔닝 맵으로 바꿔줘`) | 구성 요청 · 보내기 전 요청 |
| 에이전트 해석 | `{템플릿 이름}({코드})은 {필요 데이터 설명}. 지금은 {현재 상태}라 이렇게 할 수 있어요.` (보드: `포지셔닝 맵(CP-B)은 공급사마다 두 축의 값이 필요하고, 빈자리를 보이려면 5곳 이상이 좋아요. 지금은 3곳이라 이렇게 할 수 있어요.`) | 템플릿 필요 데이터 + 현재 데이터 |
| 선택지 A/B/C | 라디오 · `{글자}` · `{제목}` · `추천` · `{설명}` | 아래 규칙 |
| 후보 머리 | `{시트} · 고를 수 있는 레이아웃` `· {사유} {n}종` (보드 `· 업종 틀엔 경쟁 장이 없어 범용 3종`) · `필요한 데이터가 있는지로 적합도를 매겨요` | |
| 후보 카드 | 썸네일 · `{코드}` · `{이름}` · 태그(`사용 중` 파랑 채움 / `요청` 연파랑 · 점선 / `고를 수 없음` 회색) · 필요 데이터(✓ 파랑 / ✗ 검정) · `적합 {fit}%` 또는 `{대체 안내}`(예 `점유율 자료가 있으면 열려요`) | 템플릿 카탈로그 + §7.8 |
| 고정 | 체크 `이 시트 고정 — 데이터가 바뀌어도 다시 고르지 않아요` | `sht.pinned` |
| 아래 막대 | `레이아웃 바꾸기` `· {시트} · 나머지 시트는 그대로` · 다른 포함 시트 링크 `{시트} {n}종 보기`(보드 `시장 · 트렌드 8종 보기` · `고객 비즈니스 5종 보기`) | |

**선택지 규칙**

| 글자 | 뜻 | 보드 예 | 추천 조건 |
|---|---|---|---|
| A | 모자란 데이터를 더 찾은 뒤 요청 템플릿 | `공급사 3곳 더 찾아 6곳으로 → CP-B` · `사례 DB · 공개 자료에서 메뉴보드 공급사 추가 · 적합도 58% → 85%` | 추가 검색 뒤 예상 적합도 ≥ 85 이면 A 추천 |
| B | 지금 데이터로 요청 템플릿 | `3곳 그대로 CP-B` · `구도는 보이지만 빈자리 메시지는 약해요 · 적합도 58%` | — |
| C | 지금 템플릿 유지 | `비교표 CP-A 유지` · `요구 기준 5개 비교는 그대로 · 적합도 96%` | A 를 추천할 수 없으면 C 추천 |

**문구**: 라벨 `레이아웃 요청`, 자리 `축 지정 (예: 가로는 가격대, 세로는 관리 편의)` · `취소`(→ MI3P) · 큰 버튼 `{글자}로 진행 (약 {초}초)`(A 처럼 검색이 필요할 때만 시간 표시, 보드 `A로 진행 (약 40초)`; B · C 는 (제안) `B로 진행` · `C로 진행`).

**동작**

- A → `POST /v1/analyses/{id}/slides/{sht}/layout {option:"A", template:"CP-B"}` (202, `mi.layout`: 경쟁사 후보 추가 찾기 → 경쟁 영역 표 보강 → 적합도 다시 계산) → MI3G(짧은 진행, 경쟁 영역만) → MI3P.
- B · C → 같은 API, 동기 처리 → MI3P.
- `고를 수 없음`(적합도 −1) 카드는 고를 수 없다.
- `레이아웃 요청`(축 지정) → 템플릿 옵션(`axes:{x, y}`)으로 저장, 축 값이 모자라면 A 처럼 추가 검색 선택지를 다시 보인다.
- `이 시트 고정` → 이후 다시 분석해도 템플릿을 바꾸지 않는다(§3.3 단계 6 · 묻기 4).

### 6.12 넘김 묶음(Bundle)

vp 와 웹이 읽는 읽기 전용 묶음(proposal 은 같은 데이터를 §6.14 `proposal-handoff` 모양으로 읽는다). 대상에 맞게 **익명 처리를 마친 상태**로 나간다(proposal · vp · scenario · storyboard 모두 `export_customer` 규칙 — §5.6 표). 예외: `target=competitor`(CA0 `MI 작업의 경쟁사에서`, 04 문서 §4.2)는 경쟁사 분석 작업 안에서 다시 검색해야 하므로 실명을 담는다 — `{customer, segment, requirements[], competitors[{letter, real_name, aliases, kind_label, desc}], criteria[]}`. 이 묶음은 작업 소유자만 읽을 수 있다.

```json
{ "analysis_id": "mi_…", "version": 3, "handoff_id": "hof_…",
  "customer": {"name": "A 커피 프랜차이즈", "segment": "FB", "segment_name": "외식 · 카페"},
  "usage": "standard",
  "sheets": [
    {"sheet_type": "MS+TR", "sheet_name": "시장 · 트렌드", "template_code": "MI-FB-A", "why": "…",
     "content": {"size_series": [{"year": 2025, "value": 1234, "unit": "억 원", "status": "matched", "footnote_n": 1}],
                 "trends": [{"title": "…", "desc": "…", "implication": "…", "footnote_ns": [3]}]},
     "fact_check": [{"text": "디지털 메뉴보드 도입 매장 증가율", "placeholder": "[00]%", "reason": "출처 2건 중 1건만 수치가 있음"}],
     "footnotes": [{"n": 1, "text": "[발행처], 「제목」, 2025.03, p.12 (확인 2026-10-06)", "status": "원문 일치"}]}],
  "why_samsung": {"strengths": [{"title": "서버 없는 통합 관리", "note": "…", "footnote_ns": [5]}],
                  "comparison": {"criteria": ["본사 원격 통합 관리"], "columns": ["경쟁사 A", "경쟁사 B", "삼성"], "cells": [["…","…","…"]]}},
  "vp_materials": {"challenges": [], "users": [], "strengths": [], "numbers": [{"text": "…", "value": "…", "as_of": "2024-08", "source_age_months": 26, "status": "needs_check", "footnote": "…"}]},
  "options": {"cite_sources": true, "fix_notes": true, "link_why": true},
  "anonymization": {"mode": "letter", "map_ref": "hof_…"} }
```

- 수치 `status` 가 `matched` · `confirmed` 가 아니면 `fix_notes=true` 일 때 `fact_check[]` 로도 나간다(제안서 확정 필요 목록 PR7Q).
- 대외비 값은 묻기 3의 답이 `exclude` 면 `[00]` 로 바꾸고 `fact_check` 에 `reason: "대외비 자료라 뺐어요"`(제안).
- VP 재료(`vp_materials`)는 VP1 의 `과제 6 · 사용자 3 · 삼성 강점 3 · 수치 12` 집계 근거다. 수치마다 기준일(`as_of` = 주 출처 발행 연월, 모르면 `null`) · 출처 나이(`source_age_months`) · 검증 상태 · 각주를 넣는다(VP1A `출처가 26개월 지남` 판단용, 05-vp.md 가 읽는 필드). 묶음 맨 위 `customer.segment` 는 VP 업종 상속에 쓴다.

### 6.14 제안서 서비스용 계약 — ProposalHandoff v1 (10-proposal.md §8.0 · §8.7 M1~M3)

proposal 은 모든 생산 기능에 같은 모양 `ProposalHandoff v1` 을 요구한다. mi 는 아래 세 API 를 낸다. 내용은 §6.12 묶음(`target=proposal_mi` · `proposal_why`)과 **같은 데이터의 다른 모양**이고 익명 · 대외비 · 검증 규칙도 같다(두 응답을 같은 코드 경로에서 만든다).

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `GET /v1/analyses/{id}/proposal-handoff` | `?type=standard\|quickwin\|solution&section=mi\|bigMi\|why&handoff_id=&named=` | `200 ProposalHandoff` · 익명 꺼짐인데 실명 확인 기록이 없으면 `409 ASK_REQUIRED{kind:"real_names"}` |
| `POST /v1/analyses` (`auto_run`) | `{customer_name, rq_ref?: {rq_id, version}, scope?: ("market"\|"customer"\|"user"\|"competitor")[], purpose: "proposal", proposal_type?, auto_run: true}` | `202 {analysis_id, job_id}` |
| `POST /v1/analyses/{id}/facts:lookup` | `{questions: [{key, label, context?, unit?}], research?: bool}` | `200 {items: [{key, candidates: [{value, unit, status, claim_id, source: {kind, ref, label, url?}}]}]}` · `research=true` 면 `202 {job_id}` |

**매핑**

| ProposalHandoff 필드 | mi 값 |
|---|---|
| `source` | `{feature: "MI", ref_id: mi_id, version, title, updated_at, route}` |
| `target` | `{proposal_type: type, section_key: section}` — `type` 이 작업 쓰임과 다르면 §7.8 시트 묶음을 그 유형으로 다시 계산해 낸다(저장하지 않음) |
| `customer` | `{name: customer_name, industry_code: 업종 코드(FB …, GEN 이면 생략)}` |
| `rq_ref` | `links.requirements_id` + 가져온 정의서 버전 |
| `items[]` (`mi` · `bigMi`) | 시트 구성(§5.8) 행마다 1개 = MI4 매핑 표 행. `key` = `sht_…` · `label` = MI4 `{항목}`(예 `시장 규모 · 성장률`) · `from_label` = 탭 이름(`시장조사`) · `sheet_role` = `MS` · `TR` · `CB` · `US` · `CP` · `IM`(KB `seed/sheet_roles.yaml` 코드. 업종 레이아웃 A 는 `MS` 로 내고 트렌드는 같은 `content` 안, B 는 `CB`, C 는 `US`) · `sheet_title` = 시트 이름 · `template_hint` = `{code, name}` · `status`/`status_label` = `warn` `[확정 필요] {n}건` / `ok` `그대로 들어가요` / `add` `섹션에 없는 시트 · 추가` · `include_default` = 포함 여부(`add` 는 false) · `content` = §6.12 `sheets[].content` · `sources` = 그 시트 각주 `{kind: source.kind, ref: src_id, label: 각주 문구, url?: 수집에 성공한 URL 만, tier?: KB tier}` |
| `items[]` (`why`) | 경쟁 영역 → `CM`(비교표, 경쟁사는 `display_name(export_customer)`) · `ST`(삼성 강점 ≤ 3) 2개 |
| `facts[]` | 시트 `content` 안 수치마다 1개: 주장 `matched` · `confirmed` → `confirmed` / `needs_check` · `conflict` · `stale` → `unconfirmed`(값 있음) / `[00]` → `placeholder`(`placeholder: "[00]%"`). `source` = 주 출처 `{kind, ref, label}` |
| `assets` | 없음(경쟁사 로고 · 제품 사진을 넣지 않는다, §5.6) |

- **검증 상태는 옵션과 관계없이 그대로 낸다**: `fix_notes=false` 여도 `facts[].status` 를 `confirmed` 로 바꾸지 않는다(옵션은 시트 노트 문구만 정한다). `cite_sources=false` 면 `items[].sources` 는 비우되 `facts[].source` 는 남긴다(제안서 확인 목록용).
- **`named=true`**(10-proposal.md C3 와 같은 성격): 넘김 기록 `handoff_id` 의 `confirmations.real_names=true` 일 때만 실명을 낸다. 아니면 `409 ASK_REQUIRED`. 실명으로 낸 응답마다 넘김 기록에 `served_named_at` 을 더한다(감사 기록).
- **`auto_run`**(M2 · 제안서 딸깍): 설계 → 분석을 한 잡 사슬로 돈다. 사람이 없으므로 묻기 1(업종 두 갈래)은 추천값(1위)으로 진행하고 모드 `check` + 결과 업종 칩(§10.7 `답이 없으면 추천값`). `scope` 가 오면 고정(`pin`), 없으면 §3.3 규칙. 10-proposal.md 의 `users` 는 이 문서의 `user` 와 같다(별칭으로 받음).
- **`handoff_id`**: 웹은 proposal `imports` 의 `source` 에 MI 넘김 기록 ID 를 함께 넘기고(10-proposal.md 에 필드 추가 요청, §11 Q22), proposal 은 그 값을 `proposal-handoff?handoff_id=` 로 돌려준다 — 묻기 2~4 의 답(실명 · 대외비 · 고정 시트)과 고른 시트가 그 기록에 있다. `handoff_id` 없이 부르면 **안전 기본값**(익명 · 대외비 값 `[00]` · 고정 시트 두기 · 쓰임이 정한 시트)으로 낸다.
- **`facts:lookup`**(M3 · PR7Q `MI에서 확인`): 저장된 주장 중 `metric_key` · 이름 · 단위가 맞는 것을 결정적으로 찾아 후보로 낸다(새 검색 없음, 상태 그대로). `research=true` 면 그 질문들을 범위로 `다른 출처 찾기`(§4.11)와 같은 검색을 돌리되, MI 결과를 바꾸지 않고 후보 목록으로만 돌려준다(제안).

### 7.1 공통

- **잡 종류**: `mi.design` · `mi.analyze` · `mi.revise` · `mi.fixscan` · `mi.layout` · `mi.source_add` · `mi.competitor_add` · `mi.onepager` · `mi.export` · `mi.recheck` · `mi.import_ca`. 기능 API 가 Redis Stream `wm:q:mi` 에 넣고, 같은 코드베이스 워커가 `XREADGROUP` 으로 받아 그래프를 돈다.
- **체크포인트**: `thread_id = job_id`, SQLite 체크포인터 `${DATA_DIR}/mi/checkpoints.sqlite`. 사람 확인(interrupt)은 `mi.design` 의 `ask_segment` 한 곳뿐이다.
- **노드 경계 규칙**: 노드가 끝날 때마다 ① 취소 플래그 `wm:job:<id>:cancel` 확인 → 있으면 `on_cancel` ② 조종 메모 `wm:job:<id>:memos` 의 새 메모를 상태 `memos` 에 넣는다(계획 · 검색 · 작성 노드가 프롬프트에 반영하고 `log` 이벤트를 낸다) ③ `step` 이벤트로 진행을 알린다.
- **모델 호출**: 모두 ai-tools 경유(§8). 모든 LLM 호출은 JSON 스키마 모드, `purpose`(예 `mi.extract_claims`), 고객 자료(요구사항 · 첨부 · 정의서)가 들어가면 `confidential: true`. JSON 이 스키마에 안 맞으면 오류를 붙여 1회 재시도, 그래도 실패하면 규칙 기반 대체(있을 때) 또는 그 노드 실패.
- **검색어 보호(query_guard)**: 외부로 나가는 웹 검색어에는 첨부 · 요구사항 원문 문장(20자 이상 그대로)을 넣지 않는다. 고객사 이름 · 업종 · 지역 · 제품군 · 경쟁사 이름 · 공개 보고서 이름만 쓴다. 고객 계획 수치(매장 수 · 예산 등)는 공개 출처에서 이미 확인된 경우만 넣는다. 지울 것을 지우고 남는 게 없으면 그 검색을 건너뛴다.
- **예산(실행 1회)**: 깊이 `30`(표준 · 퀵윈 · 경영진 · 연결 없음) → 웹 검색 ≤ 16회, 수집 ≤ 30페이지, LLM ≤ 40회 / 깊이 `60`(Solution형) → 32 · 60 · 80. ai-tools 한도 초과 · 장애면 웹 없이(KB · 파일만) 계속하고 `web_unavailable` 을 결과에 남긴다.
- **동시성**: 검색 단계는 영역 4개 동시(`Send`), 정리 단계는 최대 2개(`MI_ORGANIZE_CONCURRENCY=2`, 16GB 단일 PC · 모델 한도), 수집은 4개 동시.
- **웹 검색 모드**(실행 시작 때 `GET /api/ai-tools/v1/capabilities` 로 정해 상태에 고정, 출처마다 `mode` 기록):

| 모드 | 조건 | URL 을 얻는 법 |
|---|---|---|
| `sources` | `WEBSEARCH_RETURN_SOURCES=true` 또는 `SEARCH_API_PROVIDER≠none` | 검색 API 결과 URL(우선) · 요약형 웹 검색의 `sources[]` |
| `summary_only` (현재 기본) | 둘 다 아님 | 요약문 안의 URL, LLM 이 제안한 공식 URL 후보(수집 성공한 것만), 사용자가 붙인 URL, KB 문서 URL |

- **테스트 결정성**: ai-tools 제공자 `mock` 은 입력 해시로 응답을 고른다. 그래프는 같은 목(mock) 입력에 같은 결과를 내야 한다(반복 순서 정렬, ULID 생성기 주입).

### 7.3 업종 확신도 계산

1. **입력 글**: 고객사 + 요구사항 + 첨부 요약(RFP · 회의록 앞 4,000자) + Storyboard Key Message.
2. **KB 근거**: `POST /api/kb/v1/segments/classify {text}` (kb 요청 §8) → 16업종마다 `kb_score`(0~1) · `clue_score`(0~1) · `clues[{text, code, weight}]` · `similar_case_ids[]`.
   - `kb_score` = KR 업종 대응이 있는 업종은 `0.5 × A2대응 + 0.5 × 사례비율`, 없는 6업종(SV · TP · VN · AD · ID · OE)은 `사례비율`. A2대응 = 대응 KR 업종들의 A2 **원점수**(정규화 전) 최댓값을 1로 자른 값. 사례비율 = 문장 유사 사례 상위 10건 중 그 업종 사례 수 ÷ 5 를 1로 자른 값(사례 → 업종 분류표 필요).
   - `clue_score` = 맞은 단서 가중치 합을 1로 자른 값(단서 사전은 kb `segments.yaml`; 예 FB: `프랜차이즈` · `가맹점` · `메뉴보드` · `카페` · `음료 피크타임`, HT: `로비` · `투숙객` · `객실` · `라운지`).
3. **LLM 근거**: 스키마 `{segments: [{code, p: 0~1, clues: string[]}], out_of_scope: bool, reason}` — 16업종 이름 · 한 줄 설명을 주고 업종마다 **독립적인** 그럴듯함 `p` 를 받는다(합이 1일 필요 없음).
4. **합치기**: `conf(s) = round(0.5 × p(s) + 0.3 × kb_score(s) + 0.2 × clue_score(s), 2)`. LLM 이 실패하면 `conf(s) = round(0.6 × kb_score + 0.4 × clue_score, 2)` 로 내고 모드는 최대 `check`(제안).
5. **판정**: §3.3 단계 2 평가 순서. 보드 예 `외식 · 카페 0.94` → 자동, `호텔 0.58 · 외식 0.55` → 선택 필요(차이 0.03), 스크린골프장(모두 < 0.50) → 범용.
6. **읽힌 단서**(MI1Q · MI2A 근거): LLM `clues` 와 kb `clues` 를 합쳐 중복을 빼고, 1 · 2위 업종 단서를 최대 6개(각 업종 3개까지) 보인다.
7. KB 에 사례 → 업종 분류표가 아직 없으면 `사례비율 = 0`(대응 없는 6업종은 LLM · 단서만으로 판정된다) — §11 Q2.

### 7.4 `mi_design` (잡 `mi.design`)

```
load_inputs → read_files → extract_requirements → classify_segment ─┬─(ask)→ ask_segment ⏸ ─┐
                                                                    └─────────────────────────┤
          ┌───────────────────────────────────────────────────────────────────────────────────┘
          ▼
   infer_gaps → decide_usage → decide_scope → decide_competitors → decide_naming
   → decide_internal → decide_depth → preview_sheets → title_topic → save_design ─(start_analysis)→ enqueue mi.analyze
```

| 노드 | 하는 일 | 호출 |
|---|---|---|
| `load_inputs` | 작업 · 연결 · 고정값 읽기. `requirements_id` 가 있으면 정의서 스냅숏 조회(`context.vertical` 은 §3.3 ② 규칙) | requirements `GET /v1/requirements/{id}/versions/{n}` |
| `read_files` | 첨부마다 텍스트 추출, 글자 층 없는 페이지는 i2t 로 받아쓰기(파일당 ≤ 10페이지), 문서 종류 · 기밀 분류 | files `extract` · ai-tools `i2t` · `llm`(`{doc_kind, classification, title, date?}`, confidential) |
| `extract_requirements` | 요구 항목 · 평가 기준 · 일정 · 경쟁사 언급 추출(`RFP · 회의록 첨부` → `요구 · 평가 기준 · 일정 추출`), 범위 키워드 표시, `한 줄 메모뿐` 판정(입력 합계 < 60자이고 첨부 · 연결 없음) | `llm`(`{requirements[], eval_criteria[], schedule[], competitor_mentions[], keywords[]}`, confidential) |
| `classify_segment` | §7.3. 고정 · 상속이면 건너뜀 | kb `segments/classify` · `llm` |
| `ask_segment` ⏸ | `awaiting_input`(§6.2) 내고 멈춤 → 답으로 `segment.mode=pin`, `MIX` 면 `mix={a: 1위, b: 1위, c: 2위}`. 메모가 오면 `classify_segment` 만 다시 돌고 다시 묻는다 | jobs input · memos |
| `infer_gaps` | `한 줄 메모뿐` 이면 업종 사례 공통 요구(KB D2 `common_req_tags`) · 유사 사례 요구(D1 → `deployment_need`)로 요구 항목 최대 3개를 `inferred=true` 로 채움, 결정 메모 `check` | kb D2 · D1 |
| `decide_usage` | §3.3 단계 3. 연결 없으면 workspace 에서 같은 프로젝트 · 고객의 제안서(`feature=PR`)를 찾아 유형을 읽는다. `경영진 한 장`(요구 · 메모의 `경영진 한 장` · `한 장으로` · `1장 요약`)이면 `exec_onepager` | workspace items |
| `decide_scope` | LLM 이 영역마다 넣을지 · 이유(`{areas:{market:{include, reason}, …}}`) → 키워드 규칙은 **추가만**(`경쟁` · `대체` · `교체` → 경쟁, `손님` · `직원` · `동선` · `대기` → 사용자) → 고객 공개 자료 수 확인(아래) → 고정값 우선 | `llm` · `websearch` 1회 |
| `decide_competitors` | 경쟁 영역이 있을 때. 사용자 지정 · RFP 언급은 유지. 지정이 없으면 후보 찾기(04 문서 §7.3 의 가벼운 판: 업종 · 제품군 검색 → 후보 추출 → 신뢰 점수) 상위 3곳(신뢰 ≥ 0.50), 모드 `check`, 근거 `지정 없음 → {업종 short} 사례 빈도 상위 3` | `websearch` · `llm` · kb D2 |
| `decide_naming` | 고객 제출 쓰임이면 익명(`auto`), `none` 이면 실명 | — |
| `decide_internal` | KB 업종 사례 수(업종 두 갈래 · 섞어 보기면 두 업종 합, 예 `호텔 17 + 외식 23건`), 첨부 중 `confidential`(단가표 · 견적 · 원가)은 제외 | kb insights |
| `decide_depth` | `solution` → 60, 그 외 30, 예상 시간 | — |
| `preview_sheets` | §7.8 을 데이터 없이 적용(업종 레이아웃 여부만) | export 템플릿 카탈로그 |
| `title_topic` | 작업 제목 · 주제 · MI2 영역 설명 4 · 요구 요약(≤ 60자) | `llm` |
| `save_design` | 결정 저장(`depends_on`, `input_hash`), workspace 색인, `start_analysis` 면 `mi.analyze` 를 넣고 `result {next_job_id}` | jobs · workspace |

**고객 공개 자료 수**: `sources` 모드 = `{고객사} 사업보고서 OR IR OR 보도자료` 검색 결과의 서로 다른 고객 도메인 · 공시 URL 수 + 첨부 중 `ir` 문서 수. `summary_only` 모드 = 요약에서 LLM 이 뽑은 서로 다른 공개 문서 이름 수 + 첨부 `ir` 수(제안). 3 미만이면 고객사 영역 `reduced`(CB-A 고정, 검색 예산 절반).

`step` 이벤트 이름(MI2A 로딩용, 제안): `입력 읽기` · `첨부 읽기` · `업종 판별` · `쓰임 · 범위 정하기` · `경쟁사 찾기` · `설계 정리`.

### 7.5 `mi_analyze` (잡 `mi.analyze`)

```
load → plan ─Send×영역→ gather(area) ─join(검색 완료)→ Send×영역(동시 2) organize(area) ─join→
   build_comparison → derive_strengths → implications? → reconcile → compose_slides → make_fix_items → finalize
                                                                     (on_cancel: save_partial)
```

| 노드 | 단계(MI3G) | 하는 일 |
|---|---|---|
| `load` | — | 작업 · 결정 · 이전 버전 · 의존 해시. 해시가 같은 영역은 이전 버전 결과를 복사(재사용)하고 `areas_todo` 만 남김 |
| `plan` | 검색 | 영역마다 조사 질문 · 웹 검색어(한국어 우선, 필요 시 영어) · KB 질의 · 파일 찾을 말. LLM `{area: {questions[], web_queries[{q, purpose, recency_months}], file_terms[]}}`, 실패 시 영역별 템플릿 검색어. 메모 반영 |
| `gather(area)` | 검색 | 아래 영역별 근거 모으기 → 출처 등록(중복 · 오래됨 걸러냄) → `step`(출처 수 · 최근 출처) |
| `organize(area)` | 정리 | `extract_claims`(LLM) → `verify`(§7.6) → 영역 내 충돌 · 오래됨 → 영역 결과 저장(미리 보기 가능) → `step`(영역 `정리 완료`) |
| `build_comparison` | 작성 | 경쟁 영역: 기준 × (경쟁사 + 삼성) 칸 만들기(§7.7) |
| `derive_strengths` | 작성 | 삼성 강점 최대 3(§7.7) |
| `implications` | 작성 | 쓰임이 `solution` · `exec_onepager` 일 때 IM 시트 내용(발견 → 시사점 → 방향 / 4분면 + 결론) |
| `reconcile` | 작성 | 영역 사이 같은 지표(`metric_key`) 충돌, 출처 중복 정리, 탭별 출처 번호 매기기, 숫자 지어내기 검사(§7.6.6) |
| `compose_slides` | 작성 | §7.8 시트 구성 · 적합도 · 이유 · 대안 |

### 7.6 주장 검증 알고리즘 (결정적)

모델 판단 없이 문자열 · 숫자 비교로만 상태를 정한다. 입력: 주장 `c`(문장 · 수치), 인용 목록(출처 · 구절 · 페이지), 출처 텍스트(스냅숏 · KB 원문 · 파일 페이지), 실행일 `D`.

**7.6.1 정규화 `N()`**: NFKC → 공백 · 줄바꿈 하나로 → 따옴표 · 대시 · 말줄임표 통일 → 폭 넓은 숫자 · 기호(`％`) 변환 → 숫자 속 천 단위 쉼표 제거 → 영문 소문자. 구절 앞뒤 `…` 는 떼고 비교한다.

**7.6.2 수치 해석**: 숫자 + 한국어 큰 단위(`만` · `억` · `조`) + 단위(`%`, `%p`, `원`, `억 원`, `조 원`, `개`, `곳`, `매장`, `대`, `명`, `개월`, `년`, `nit`, `W`, `kW`, `인치`/`"`, `mm`, `㎡`, `배`)를 `(값, 기준 단위)` 로 바꾼다(예 `1.2조 원` → 1.2×10¹² 원, `1,234억 원` → 1.234×10¹¹ 원). `%` 와 `%p` 는 다른 단위다. 연도(`2025년`)는 `year` 로 정확히 같아야 한다. 범위(`3~5`)는 두 값.

**7.6.3 인용 하나 검사**

| 검사 | 통과 조건 | 실패 사유 코드(카드 문구) |
|---|---|---|
| 구절 `quote` | `N(구절)` 이 `N(출처 텍스트)`(페이지가 있으면 그 페이지)에 그대로 있음. 아니면 최장 공통 부분 문자열 ≥ 구절 길이의 90% → `partial`(통과로 보되 강조 없음) | `QUOTE_NOT_FOUND`(제안 `원문에서 이 구절을 찾지 못했어요.`) |
| 수치 `numbers` | 주장의 수치마다 구절 안에 같은 기준 단위 값이 있고 차이 ≤ max(값의 0.5%, 주장 표기 마지막 자리의 절반) | 수치 없음 `NUMBER_MISSING`(`수치 없이 흐름만 말해 {주장 수치}를 뒷받침하지 못해요.`) / 다름 `NUMBER_MISMATCH`(제안 `원문 값은 {원문 값}이에요.`) |
| 개체 `entities` | 주장 속 모델코드 · 제품명 · 회사명이 출처 텍스트에 있거나 KB A1 별칭으로 같은 개체 | `ENTITY_MISMATCH`(제안 `원문에 {이름}이 나오지 않아요.`) |
| 날짜 `date` | 발행일 있고 `D` 기준 24개월 이하 | 넘음 `STALE`(제안 `{YYYY}년 자료예요 · 더 최근 자료를 찾지 못했어요.`) / 수치 주장인데 발행일 모름 `DATE_UNKNOWN`(제안 `발행 시점을 확인하지 못했어요.`) |
| 텍스트 있음 | 출처 텍스트를 얻음 | 수집 실패 · 유료 `FETCH_FAILED`(제안 `원문을 열지 못해 확인하지 못했어요.`) / 요약만 `SUMMARY_ONLY`(제안 `검색 요약에서 나온 내용이라 원문과 대조하지 못했어요.`) |

인용 상태: 모두 통과 → `matched` / 텍스트 없음(요약 · 수집 실패) → `unverifiable` / 날짜만 넘음 → `stale` / 그 밖 → `needs_check`. 카드 상태 칩은 `matched` 만 `원문 일치`, 나머지는 `확인 필요`.

**7.6.4 출처 종류별 규칙**

| 종류 | 대조 대상 텍스트 | 규칙 |
|---|---|---|
| `web` | 수집 스냅숏(PDF 는 페이지) | 위 검사 그대로 |
| `websearch_summary` | 요약문 | **어떤 경우에도 `matched` 가 아니다**(`unverifiable`, `SUMMARY_ONLY`). 구절 · 수치 검사는 요약문을 대상으로 그대로 해서, 구절이 요약문에 없으면 그 인용은 버린다(남은 인용이 없으면 주장은 `missing`). 요약문에 주장 수치조차 없으면 그 수치는 근거가 없는 것으로 보고 §7.6.6 에 따라 `[00]` 처리 |
| `kb_official` (T2) | 스펙 행 `{속성}: {원값}` · 메시지 원문 · 특장점 본문 | 위 검사. `claim_flag=1` 이면 상태는 그대로 두고 표시 `대외 사용 전 확인` |
| `kb_case` (T3) | 사례 페이지 원문 청크 | 위 검사 |
| `kb_case` (T5 KPI · 이전 LLM 추출) | 그 사례 문서의 원문 블록 | 원문에 있으면 `matched`, 없으면 `needs_check` + 제안 `사례 원문과 문장이 달라요.` |
| `file` | 페이지 텍스트(글자 층 또는 i2t 받아쓰기) | 위 검사. i2t 면 `method=i2t` 표시 |
| `user` | 입력 값 | 항상 확정(검사 생략) |

**7.6.5 주장 상태 모으기**(위에서부터 먼저 걸리는 것)

1. 사용자 · 파일로 확정된 확정 필요 항목이 있음 → `confirmed`(`확정`)
2. 대조 잡이 도는 중 → `checking`(`확인 중`)
3. 인용 없음 → `missing`(라벨 `확인 필요`, 확정 필요 항목)
4. 같은 지표 값끼리 차이 ≥ 20% → `conflict`(`출처 간 값 다름`)
5. 모든 인용이 `stale` → `stale`(`자료 연도 오래됨`)
6. `matched` 가 아닌 인용이 n ≥ 1 → `needs_check`(`확인 필요 {n}`)
7. 나머지 → `matched`(`원문 일치`)

- 정리: 주장에 `matched` 인용이 하나라도 있으면, 같은 수치만 되풀이하는 `websearch_summary` 인용은 떼어 낸다. 떼어 낸 뒤 그 요약 출처에 남은 인용이 없으면 출처 상태 `excluded` · 사유 `superseded`(MI3G (제안) `제외 · 원문으로 대체`). 요약이 유일한 근거인 주장만 요약을 단다.
- **충돌 차이** = `|a − b| ÷ min(|a|, |b|)` (큰 값이 작은 값보다 20% 이상 크면 충돌). **주 값** = 발행일이 가장 최근인 출처(날짜 모름은 뒤로), 같으면 `authority` 숫자가 작은(공신력 높은) 출처. 문장은 주 값을 쓰고 다른 값을 함께 적는다 — (제안) `{주 값}({출처 n}) · 다른 출처 {값}({출처 m})`. 표 칸처럼 좁은 곳은 주 값 + 각주 표시.
- **요약 교차 확인**(`summary_only` 모드): 레이아웃이 쓰는 핵심 지표(시장 규모 연도 계열 · 성장률 · 점유율)가 요약으로만 뒷받침되면 다르게 쓴 검색어로 1회 더 검색한다. 두 요약 값의 차이 < 20% → 사유 `SUMMARY_CORROBORATED`(제안 `검색 요약 2건이 같은 값을 말해요 · 원문은 확인 전이에요.`, 상태는 여전히 `needs_check`), ≥ 20% → `conflict`.

**7.6.6 숫자 · 이름 지어내기 검사**(`reconcile`)

- 화면에 나가는 모든 수치(블록 · 표 칸 · 강점 · 이유 문장)는 ① 그 주장 인용의 구절(또는 요약문)에 있거나 ② KB 삼성 값 인용이거나 ③ 확정 값이어야 한다. 아니면 그 수치를 `[00]`(단위 유지)로 바꾸고 사유 `NUMBER_UNSUPPORTED`, 확정 필요 항목을 만든다.
- 모델코드 · 제품명은 KB A1 로 이어지거나 근거 텍스트에 있어야 한다. 아니면 `[확인 필요]`.
- 경쟁사 수치는 `web` · 공개/고객 분류 `file` 출처만 허용한다(`경쟁사 수치는 공개 자료로만 채우고, 못 찾으면 [확인 필요]로 남깁니다.`). 사내 대외비 파일 값은 경쟁사 칸에 쓰지 않는다.

### 7.7 비교표 · 삼성 강점

- **삼성 비교 제품**: TopBar 로 추가한 제품 → 요구 문장의 A1 제품 → S1 공간별 추천 1순위 제품군의 대표 모델. 모델 표시명(예 `QM55C`)은 셸 · kb 의 표시명 규칙을 따른다 — KB v1 에는 `QM55C` 같은 별칭이 없고 모델코드(`LH55QMCEBGCXKR`)만 있으므로 규칙 승인 전에는 모델코드를 쓴다(00-shell.md 갭 G-PRD-1).
- **칸 채우기**: 기준마다 경쟁사 근거(웹)에서 LLM 이 칸 문장 + 인용을 뽑는다. 삼성 칸은 KB 에서만 — 기준 이름 → 정규 스펙 키(예 `저전력 · 전기료` → `power_consumption` + E2 `에너지 절감` 메시지, `본사 원격 통합 관리` → 솔루션 메시지 · 특장점)로 찾고, 같은 키에 값이 여럿(`154 W` · `0.5 W`)이면 속성 이름으로 고른다.
- **판정**: LLM `{rows: [{criterion_id, verdicts: {cmp_…: samsung_better|similar|samsung_worse|unknown}, rationale, claim_ids}]}` — 근거가 `[확인 필요]` 인 칸은 `unknown`.
- **강점 고르기**: 기준을 가중치 순으로 보고 `점수 = 가중치 × (samsung_better 인 경쟁사 수)` 상위 최대 3. 강점 제목 ≤ 12자, 근거 한 줄 ≤ 40자(예 `— 미수신 자동 재전송, 유관 사례(800개 매장) 보유`). 근거 한 줄의 수치는 KB 사례 · KPI 인용이 있어야 한다(§7.6.6). 후보가 3 미만이면 있는 만큼.

### 7.8 레이아웃 선택 · 데이터 적합도

**시트 묶음(쓰임 · 범위)**: 표준 = 시장 · 고객 · 경쟁 순 최대 3(범위에 없으면 빠지고 사용자 영역이 있으면 그 자리에, MIC 2번 `표준 · 2시트로 줄임`). 넘치는 분석 영역(예 사용자)은 `넣으면 좋은 시트`(꺼짐 · `check`). Solution형 = MS · TR · CB · US · CP + IM-A (업종 A 를 쓰면 MS+TR 이 한 장이고 트렌드가 5개 이상이면 TR-C 를 더한다, MIC 8번). 경영진 한 장 = IM-B + 부록 2장(MS · CP 중 데이터가 있는 것, MIC 9번). 퀵윈 = 시트 없음(VP 재료). 연결 없음 = 리포트(시트는 보낼 때 다시 매핑).

**시트마다 고르기**

1. 사람이 고정한 시트 → 템플릿 그대로. 데이터가 바뀌어 맞지 않으면 바꾸지 않고 자리표시 `[00]` + 확정 필요 항목(단계 6).
2. 업종 ≠ GEN 이고 그 시트 유형에 업종 레이아웃이 있고(MS · TR → A, CB → B, US → C) 그 레이아웃의 필수 데이터가 있으면 → 업종 레이아웃. **CP · IM 은 업종 레이아웃이 없다**(`업종 틀 없음 → 범용`, `범용`).
3. 아니면 데이터 모양 표(§10.5)의 후보 중 적합도가 가장 높은 것. 5점 안으로 비기면 대표 메시지(왜 · 얼마나 · 누구 — LLM 분류)에 맞는 것, 그래도 비기면 표 순서.
4. 고른 템플릿의 필수 데이터가 없으면 → 그 데이터만 1회 추가 검색 → 그래도 없으면 다음 대체 템플릿(예 `MS-B → MS-E`) + `[확정 필요]`.
5. 고객 공개 자료 3건 미만이면 CB 는 `CB-A` 고정(MIC 7번).

**적합도**: 템플릿마다 필요 데이터 목록(서비스 설정 `templates_needs.yaml`, export 서비스 템플릿 카탈로그 코드와 같은 코드)을 둔다. 필요 데이터 i 는 필수/선택, 가중치 `w_i`, 충족도 `s_i ∈ [0, 1]`.

- 필수 하나라도 못 채우면 `fit = −1`(`불가`, 카드 문구는 템플릿별 열림 조건 예 `점유율 자료가 있으면 열려요`).
- 아니면 `fit = round(100 × Σ w_i·s_i ÷ Σ w_i)`.
- 막대 색: `fit ≥ 85` 파랑, 미만 회색.

### 7.9 `mi_revise` (잡 `mi.revise`) · 후속 질문

```
load_base → interpret → targeted_gather? → apply_ops → verify → diff(scope 강제) → save_proposal
```

- `interpret`: LLM `{operations: [{op: add_row|remove_row|edit_cell|edit_strength|research_claim|shorten|remove_competitor|use_internal_spec, target, detail}], needs_search: bool}`.
- `targeted_gather`: 범위 안 대상만 KB · 웹 · 파일 근거를 더 모은다(예 `유지보수 · AS` 행 → 경쟁사 AS 정책 검색, `사내 스펙 기준` → KB 스펙).
- `apply_ops`: 새 문장 · 칸 · 강점(LLM, 인용 필수) → §7.6 검증.
- `diff`: 기준 버전과 비교해 변경 목록을 만든다. **범위 밖 변경은 버린다**.
- 걸린 시간 → `{s}초`, 새 출처 수 → `출처 +{k}`. 빠른 요청 제안 1개(LLM).
- 라운드를 더하면 이전 안 상태 위에서 다시 돌고, 변경 목록은 늘 기준 버전 대비.
- **후속 질문 의도**: LLM `{intent: "question"|"revision", scope?, instruction?}`. `question` 은 저장된 스냅숏 · KB 로만 답하고(새 웹 검색 없음), 답의 수치는 §7.6.6 과 같은 검사를 거친다. 못 하면 `저장된 출처로는 답할 수 없어요`(제안).

### 7.10 `mi_fixscan` (잡 `mi.fixscan`)

1. files `extract` 로 페이지 텍스트, 글자 층 없는 페이지는 i2t(≤ 20페이지).
2. 열린 확정 필요 항목마다 항목 이름 · 단위 낱말로 후보 구절 찾기 → LLM `{matches: [{fix_id, value, unit, page, quote}]}`(confidential).
3. 결정 검사: 구절이 그 페이지 텍스트에 있고 값이 구절 안에 있어야(§7.6.3) `ok` · `사내 자료로 확정 · p.{n} 근거`. 출처 등록(`kind=file`, 분류) 후 해당 주장의 인용을 이 출처로 바꾼다(`출처를 그 자료로 바꿔 둡니다`).
4. 못 찾으면 원래 상태 + (제안) `올린 자료에 이 값이 없어요`. 경쟁사 항목은 파일 분류가 `confidential` 이면 쓰지 않는다.

### 7.11 `mi_recheck` (잡 `mi.recheck`) — 30일 재확인

- **예약**: `finalize` 가 `POST /api/jobs/v1/schedules {service: "mi", kind: "mi.recheck", ref: "mi_…", run_at: analyzed_at + 30일}` (기존 예약 교체). jobs 서비스 정렬 집합 `wm:sched` 가 때가 되면 잡을 넣는다.
- **노드**: `load` → `competitor_news`(경쟁사마다 `{실명} 신제품 출시` 검색, 기간 = 분석일 이후 → LLM `{items: [{product, date, summary}]}` → 분석일 뒤 날짜면 `competitor_new_product`) → `report_revisions`(출처 중 `시장 보고서` · `정부·통계` 의 발행처 · 제목으로 최신판 검색 → 더 새 판이면 `report_revised`) → `refetch`(URL 있는 출처 다시 수집, 내용 해시가 바뀌고 인용 구절이 사라졌으면 `source_changed`) → `kb_version`(KB 빌드 버전이 바뀌었으면 KB 질의 다시 → 인용 값이 달라졌으면 `kb_updated`) → `decide`.
- **판정**: 변경 ≥ 1 → 상태 `upd`, 변경 저장(영향 영역: 신제품 → 경쟁, 보고서 → 시장, 출처 변경 → 그 출처의 영역, KB → KB 를 인용한 영역), 알림. 0 → 상태 그대로(`done`), (제안) 메모 `30일 재확인 · 바뀐 자료 없음`, 30일 뒤 다시 예약.
- **검증 표시**: `sources` 모드에서 URL 을 수집해 날짜까지 확인한 변경은 `matched`, 요약으로만 찾은 변경은 `needs_check`(배너 · 메뉴 머리 상자 문구는 같고, `바뀐 자료 보기` 목록에 `확인 필요` 표시).
- **`바뀐 부분만 다시 분석`**: `runs {mode: "changed_only", areas: 영향 영역}` → 영향 영역의 바뀐 대상만 다시 모으고, 그 영역 주장은 모두 다시 검증. 고정 시트는 덮어쓰지 않는다(MIC 11번 `CP-A 갱신` · `고정 2 유지`).

## 10. 규칙 · 임계값

모두 mi 서비스 설정(`services/mi/config/*.yaml`)에 두고 MIR 시트가 같은 값을 읽는다. 보드 숫자는 그대로, (제안) 표시는 이 문서가 정한 기본값.

### 10.1 업종 판별

| 규칙 | 값 |
|---|---|
| 자동 확정 | 1위 확신도 **≥ 0.80** |
| 확인 권장(진행 + 결과에 업종 확인 칩) | **0.50 ~ 0.79** |
| 한 번 묻기(섞어서 보기 포함) | 1 · 2위 차이 **< 0.10** (1위 ≥ 0.50 일 때, 자동 확정보다 먼저 평가) |
| 범용 | 1위 < 0.50 → `16개 업종 밖` → 범용 레이아웃 |
| 상속 · 고정 | 연결 업종 상속(자동), MI1I · 사람이 정함(고정) |
| 확신도 식 (제안) | `0.5 × LLM + 0.3 × kb_score + 0.2 × clue_score`, 소수 둘째 자리 반올림. LLM 실패 시 `0.6 × kb + 0.4 × clue`, 모드 최대 `check` |
| 섞어서 보기 점수 | `(1위 + 2위) ÷ 2` (보드 0.58 · 0.55 → 0.57) |
| 업종 수 | 16 + 범용 |

### 10.2 입력 판별

| 규칙 | 값 |
|---|---|
| 한 줄 메모뿐 | 입력 합계 < 60자 · 첨부 없음 · 연결 없음 (제안) → 사례 DB 로 빈칸 추론 최대 3개 (제안) · 확인 권장 |
| RFP · 회의록 첨부 | 요구 · 평가 기준 · 일정 추출(자동) |
| i2t 받아쓰기 | 설계: 파일당 ≤ 10페이지, 확정 스캔: ≤ 20페이지 (제안) |

### 10.3 범위 · 경쟁사

| 규칙 | 값 |
|---|---|
| 경쟁 영역 키워드 | `경쟁` · `대체` · `교체` |
| 사용자 영역 키워드 | `손님` · `직원` · `동선` · `대기` |
| 고객사 영역 축소 | 고객 공개 자료 **< 3건** → CB-A |
| 경쟁사 지정 없음 | 상위 **3곳**(신뢰 ≥ 0.50, 제안) · 확인 권장 |
| 고객에게 내는 제안서 | 경쟁사 익명 표기 (A · B · C) |

### 10.4 쓰임 → 시트

| 쓰임 | 시트 |
|---|---|
| 표준 제안서 연결 | MI 섹션 **3시트** (시장 · 고객 · 경쟁) |
| Solution형 연결 | 대규모 MI **5~6시트** + 시사점 |
| 퀵윈 연결 | MI 섹션 없음 → 리포트 + VP 재료로 |
| '경영진 한 장' 요청 | IM-B **1장** + 부록 **2장** |
| 연결 없음 | 리포트 · 보낼 때 다시 매핑 |

### 10.5 레이아웃 밴드 (MIR 5)

순서: `고정한 시트는 건너뜀 → 업종 레이아웃 (16개 업종 × 3장) → 데이터 모양 → 메시지`.

| 코드 | 시트 | 업종이 정해지면 | 데이터 모양 → 템플릿 |
