> 원천: `docs/screens/webapp1/<보드>.dc.html`(보드 끝 로직 클래스의 예시 데이터 · 상태 포함), canvas 노트 `caRule`, `docs/ARCHITECTURE.md`, `config/services.yaml`, `winmate-kb/docs/*`

**표기 규칙**

- `백틱` 안은 보드 문구 그대로다. `{변수}` 부분만 데이터로 바뀐다.
- **(제안)** = 보드에 없는 문구 · 동작으로 이 문서가 정한 것(§11 검토 대상).
- 보드 예시 수치(`0.91`, `후보 6`, `출처 16` …)는 예시 데이터다. 규칙 · 임계값의 원천은 §10.
- 모르는 값은 `[확인 필요]`(글) · `[00]`(수치, 단위 유지)로 남긴다. **추정 금지**(`모르는 값은 [확인 필요] · [00] (추정 금지)`, canvas `caRule`).

## 1. 목적과 진입점

### 1.1 목적

고객이 제안을 비교하게 될 경쟁사를 찾고(후보 → 유저 확인) 분석한다 — 제품 · 가격대 · 솔루션 · 레퍼런스 · 최근 동향 · 삼성 대비. 결과는 MI 작업의 경쟁사 영역 · Storyboard 비교 기준 · 제안서 Why Samsung · 경쟁 비교 시트로 보낸다(canvas `caRule`).

- 입력은 두 가지: **고객 요구사항에서**(저장된 정의서를 고르면 고객사 · 업종 · 장소 · 제품을 꺼내 채움, CA1R) / **자유 양식**(한 문단을 적으면 에이전트가 네 가지를 읽음, CA1).
- 안내 문구는 항상 보인다: `고객사 · 업종 · 장소 · 제품까지 알려 주면 경쟁사를 훨씬 잘 찾아요. 업종만 있어도 찾긴 하지만 후보가 넓어져요.`
- 화면마다 할 일 하나(넣기 / 후보 확인 / 기준 바꾸기 / 결과 보기 / 보낼 곳 고르기), 가운데 한 줄(820px), 큰 버튼 하나, 한 번에 보는 항목 7개 이하. 후보는 6곳까지 한 화면.

## 3. 사용자 흐름

### 3.1 기본 흐름

UC_CA `기본 흐름`: `Main 홈` → `CA1 넣기` → `CA2 경쟁사 확인` → `CA3 분석` → `CA4 결과` → `CA5 보내기`. 찾는 중(CA1G)은 자동으로 넘어간다.

```
 Main/사이드바 ─→ CA1(자유 양식) ⇄ CA1R(고객 요구사항에서)
                   │ [경쟁사 찾기]
                   ▼
                 CA1G(find 잡) ──(고객사 · 장소 없음 + 업종 두 갈래)──→ CA2Q ──[답하고 찾기 · 건너뛰기]──→ CA1G
                   │ (끝나면 자동)
                   ▼
                 CA2(후보 확인) ──[{n}곳으로 분석]──→ CA3(analyze 잡) ──(끝나면 자동)──→ CA4(한눈에) ⇄ CA4D(상세)
                                                        ⇅ [바꾸기]                         │ [저장 · 보내기]
                                                      CA3C                                 ▼
                                                                                          CA5 ─→ MI3 / 제안서 PRS7 / SB1Q3 / PDF
```

### 3.2 갈래

| 갈래 | 경로 | 조건 · 비고 |
|---|---|---|
| 고객 요구사항에서 | CA1 탭 `고객 요구사항에서` · CA0 `고객 요구사항 정의서에서` → CA1R → `경쟁사 찾기` → CA1G | 정의서에 없는 항목은 `비어 있음` |
| 되묻기 | CA1G 중 find 잡 `awaiting_input` → CA2Q → `답하고 찾기` / `건너뛰기 — 업종 기준으로 찾기` → CA1G | §3.3 묻기 1. `뒤로` → CA1(잡 취소) |
| 찾는 중 미리 보기 | CA1G `지금까지 찾은 후보 보기` → CA2(찾는 중 상태) | 큰 버튼은 찾기가 끝나야 켜짐 |
| 입력 다시 | CA2 `바꾸기` · `뒤로` → CA1 | 다시 찾으면 사용자가 넣고 뺀 후보는 유지 |
| 기준 바꾸기 | CA3 `바꾸기` → CA3C → `이 기준으로 분석` → CA3 | 이미 모은 경쟁사 사실은 재사용(다시 모으지 않음)하고 판정부터 다시 |
| 결과 상세 | CA4 경쟁사 행 → CA4D → `다른 경쟁사` 전환 / `한눈에` → CA4 | |
| 이 경쟁사 더 찾기 | CA4D `이 경쟁사 더 찾기` → (짧은 잡) → CA4D | 그 경쟁사만 다시 |
| 다시 분석 | CA4 `다시 분석` → CA3 / CA0 배너 `다시 분석` → CA3 | 30일 재확인으로 바뀐 경쟁사만 |
| 경쟁사 넣고 빼기(다시) | CA4 → (제안) `경쟁사 바꾸기` → CA2 → CA3 | UC_CA `경쟁사 넣고 빼기` · `직접 추가 · 뺀 곳은 재분석에도 유지` |
| MI 작업에서 시작 | CA0 `MI 작업의 경쟁사에서` → MI 작업 고르기(제안 시트) → CA1G(추가 후보만 찾기) → CA2(후보 = MI 경쟁사 고정 · 켜짐 + 새 후보) | §1.3 E5 · CAR 단계 1 `MI 작업에서 넘어옴` |
| 중지 | CA3 `중지` → CA4(분석한 곳만, 제안) | |
| 보내기 | CA4 · CA4D `저장 · 보내기` → CA5 → 각 대상 | §4.9 |

### 3.3 라우팅 규칙 (CAR 원문 · 판단 모드)

판단 모드 4가지는 MI 와 같다(03-mi.md §3.3): `자동` `진행` · `확인 권장` `진행 + 결과에 표시` · `선택 필요` `답 받고 진행` · `고정` `사람이 정함`.

**단계 1 · 입력 판별** — `무엇으로 시작했나 — 정의서 · 자유 양식 · 첨부 · MI 작업`

| 신호 | 결정 | 모드 |
|---|---|---|
| `요구사항 정의서 연결` | `고객사 · 업종 · 장소 · 제품 상속` | 자동 |
| `자유 양식 한 문단` | `4가지 읽기 · 읽힌 것 칩으로` | 자동 |
| `RFP · 회의록 첨부` | `경쟁사 언급 · 평가 기준 추출` | 자동 |
| `MI 작업에서 넘어옴` | `그 작업의 경쟁사 후보 상속` | 자동 |
| `업종 · 제품만 있음` | `찾되 '업종 기준' 칩` | 확인 권장 |

**단계 2 · 빈 정보** — `고객사 · 업종 · 장소 · 제품 중 비어 있는 것`

| 신호 | 결정 | 모드 |
|---|---|---|
| `고객사 · 장소 둘 다 없음` | `한 번 묻기 (CA2Q · 건너뛰기 가능)` | 선택 필요 |
| `장소만 없음` | `전국 기준 · 결과에 '지역 미반영' 칩` | 확인 권장 |
| `제품 없음` | `업종 사례 상위 제품군으로` | 자동 |
| `업종 못 읽음` | `MI 업종 판별 규칙 재사용` | 자동 |
| `고객사만 있음` | `공개 자료에서 업종 · 장소 추정 · 칩` | 확인 권장 |

**단계 3 · 후보 선정** — `신뢰 점수 · 유저가 넣고 뺀 것 · 개수`

| 신호 | 결정 | 모드 |
|---|---|---|

**묻기 1 판정 규칙(구현)**: 보드가 두 가지로 적혀 있다 — 단계 2 행 `고객사 · 장소 둘 다 없음` 과 묻는 경우 `고객사 · 장소가 모두 없고 업종이 두 갈래`(canvas `caRule` 도 후자). 기본은 **후자(AND)** 로 한다: 고객사 · 장소가 둘 다 비어 있고 **그리고** 업종 1 · 2위 확신도 차이 < 0.10 이면 CA2Q. 업종이 분명하면 묻지 않고 단계 1 `업종 · 제품만 있음` → `업종 기준` 칩(확인 권장)으로 진행한다. 설정 `CA_ASK_SLOTS_REQUIRE_AMBIGUOUS_INDUSTRY`(기본 `true`)를 `false` 로 바꾸면 업종과 관계없이 둘 다 비면 묻는다(§11 Q1).

**평가 순서(find 잡 `check_slots`)**: ① 정의서 · MI 상속 값 채움 → ② 업종 판별(03-mi.md §7.3 와 같은 식, 단 업종 칩 · 고정 없음) → ③ 묻기 1 판정 → ④ 빈 칸 처리(`장소만 없음` → `지역 미반영`, `제품 없음` → 업종 사례 상위 제품군, `고객사만 있음` → 공개 자료로 업종 · 장소 추정 + 칩) → ⑤ 후보 찾기.

### 4.4 `CA1` — 넣기 · 자유 양식 (`/competitor/new`, `/competitor/:id/input`)

**표시 · 입력**

| 요소 | 문구 · 형식 | 출처 |
|---|---|---|
| 머리 | `넣기 · 자유 양식` / `어떤 고객의 경쟁사를 찾을까요?` / `고객 요구사항 정의서를 고르거나, 아래에 자유롭게 적어 주세요.` | 고정 |
| 입력 방식 탭(`role=tablist`, `aria-label="입력 방식"`) | `자유 양식`(선택: 흰 바탕 + 파란 테두리) · `고객 요구사항에서`(→ CA1R) | |
| 글 입력 | 라벨 `고객 · 사업 설명`, 자리 `고객사 · 업종 · 장소 · 제품을 한 문단으로 적어 주세요`, ≤ 2,000자 | 사용자 입력 |
| 파일 | `파일 올리기` + `RFP · 회의록을 올리면 경쟁사 언급과 평가 기준도 읽어요` | files 업로드 |
| 큰 버튼 | `경쟁사 찾기` | |
| 읽은 것 | `입력에서 읽은 것` + 칩 4(`고객사` · `업종` · `장소` · `제품` 순서), 칩 = `{항목} · {값}`(초록) 또는 `{항목} · 비어 있음`(점선) + `{찾은 수} / 4` | `POST /v1/parse` |
| 안내 | `고객사 · 업종 · 장소 · 제품까지 알려 주면 경쟁사를 훨씬 잘 찾아요. 업종만 있어도 찾긴 하지만 후보가 넓어져요.` | 고정(항상 보임, 4/4 여도) |

**칩 값 형식**: 고객사 = 회사 이름(예 `A 커피 프랜차이즈`) · 업종 = 업종 short 이름(03-mi.md §5.7, 예 `외식 · 카페`) · 장소 = 지역 · 장소 요약(예 `수도권 직영점`) · 제품 = 제품 요약(예 `55" 사이니지 + 배포 솔루션`). 값이 모호하면(업종 두 갈래 · 제품군만 읽힘) 칩 뒤 `일부`(CA2Q 표기)를 붙인다.

**동작**

1. 글이 10자 이상이면 600ms 디바운스로 `POST /v1/parse {text, file_ids}` → 칩 갱신(동기, ≤ 3초 목표). 파일을 올리면 파일 추출이 끝날 때까지 (제안) 칩 자리에 `파일 읽는 중`.
2. 파싱은 LLM(`ca.extract_slots`) + KB(A1 제품 · 카테고리 · 공간, 업종 판별)로 한다. LLM 이 실패하면 KB 만으로 업종 · 제품을 채우고 고객사 · 장소는 비운다.
3. `경쟁사 찾기`(글 또는 파일이 있어야 켜짐) → 작업이 없으면 `POST /v1/analyses {input_mode:"free", text, file_ids}` → `POST /v1/analyses/{id}/find` (202) → CA1G.
4. 입력은 800ms 디바운스로 자동 저장(`draft`).

### 4.5 `CA1G` — 찾는 중 (`/competitor/:id/finding`)

**표시**

|---|---|---|---|
| 1 | `입력 읽기 — 고객사 · 업종 · 장소 · 제품` | 고정 | 칸 읽기 · 업종 판별 · 묻기 판정 |

### 4.6 `CA2` — 경쟁사 확인 (`/competitor/:id/candidates`)

**표시 데이터**

| 요소 | 문구 · 형식 | 출처 |
|---|---|---|
| 머리 | `확인 1 / 1` / `이 경쟁사들로 분석할까요?` / `입력에서 읽은 {k}가지로 후보 {N}곳을 찾았어요. 추천 {r}곳은 켜 두었고, 빼거나 더할 수 있어요.` | 작업 · 후보 집계(N = 목록 전체, `더 보기` 포함) |
| 읽은 칩 | `{항목} · {값}`(읽은 것만, 예 `고객사 · A 커피 프랜차이즈`) + `바꾸기`(→ CA1/CA1R) | `slots` |
| 확인 권장 칩(제안 위치 — CAR `못 읽은 신호는 결과에 칩으로 남겨요`) | `업종 기준` · `지역 미반영` · (제안) `업종 추정` · `장소 추정` · `업종 확인` | `analysis.chips` |
| 후보 목록(`role=group`, `aria-label="경쟁사 후보 {N}곳"`) | 행 최대 6 + (제안) `후보 {m}곳 더 보기` | `GET /v1/analyses/{id}/candidates` |
| 후보 행 | 스위치(`role=switch`, `aria-checked`, `aria-label="경쟁사 {글자} 빼기"`/`"경쟁사 {글자} 넣기"`) · 글자 칩(켜짐 검정 · 꺼짐 회색) · `경쟁사 {글자}`(+ 실명 보조) · 유형(예 `국내 대형 가전 · 사이니지`) · 근거 칩(`업종` · `장소` · `제품` · (제안) `고객사`) · 근거 한 줄 · 배지 · 신뢰(`0.91` 형식) | 후보 |
| 직접 추가 | 라벨 `경쟁사 직접 추가`, 자리 `경쟁사 직접 추가 (회사명 · 제품명)` | |
| 안내 | `실명은 이 작업 안에서만 보여요 · 내보내기엔 익명(경쟁사 A · B …) · 직접 넣거나 뺀 곳은 다시 분석해도 유지돼요` | 고정 |
| 아래 막대 | `뒤로`(→ CA1) · `선택` `{n}` `곳` · 큰 버튼 `{n}곳으로 분석` | 켜진 후보 수 |

- **배지**: 신뢰 ≥ 0.70 `추천`(기본 켜짐) / 0.50 ~ 0.69 `확인 필요`(기본 꺼짐) / < 0.50 `제외 제안`(기본 꺼짐, 목록엔 남음). 사용자가 직접 추가한 곳: (제안) 배지 `직접 추가`, 신뢰 표시 없음.
- **정렬 · 글자**: `추천` → `확인 필요` → `제외 제안`, 각 묶음 안은 신뢰 내림차순. 찾기가 끝날 때 이 순서로 `A, B, C …` 를 붙이고 이후 바꾸지 않는다(보드 A 0.91 · B 0.86 · C 0.78 · D 0.74 · E 0.52 · F 0.31). 직접 추가는 다음 글자.
- **근거 칩**: 신호 강도 ≥ 0.5 인 신호만 칩으로(§7.4). 근거 한 줄 예: `같은 업종 도입사례 6건 · 55" 라인업 · 자체 CMS`, `메뉴보드 콘텐츠 배포 · 하드웨어 없음 (제품 일부 겹침)`, `가격대 겹침 · 레퍼런스 미확인`, `업종 겹침 · 제품 다름`.
- **신뢰 표시**: 소수 둘째 자리 숫자만(색 없음). 꺼진 행은 글자 · 이름 · 설명이 회색 `#8a91a0`.

**동작**

| 요소 | 동작 |
|---|---|
| 스위치 | `PATCH /v1/analyses/{id}/candidates/{cmp} {on}` → `pinned=true`(다시 찾기 · 다시 분석해도 유지) |

| 출처 요약 | `출처 {n} · 공개 자료 {a} · 사내 사례 DB {b} · [수치는 확인 후 확정]`(확정 안 된 수치가 없으면 마지막 구절 생략) | 결과 출처 |
| 아래 막대 | `다시 분석`(→ CA3) · 큰 버튼 `저장 · 보내기`(→ CA5) | |

- **우위 · 비슷 · 열위**는 **삼성 쪽에서 본 판정**이다: 기준마다 그 경쟁사와 비교해 삼성이 낫다(`우위`) · 비슷하다(`비슷`) · 못하다(`열위`). 판정 못 한 기준(`[확인 필요]` 칸)은 세지 않는다(세 수의 합 ≤ 켜진 기준 수).
- **포지셔닝 한 줄**: 경쟁사 사실(§5.5)로 만든 ≤ 40자 요약(예 `자체 CMS 기반 풀 라인업 · 500매장 이상은 서버 추가`). 사실에 없는 수치는 쓰지 않는다.
- **`비교표` 보기**(제안): 행 = 켜진 기준(CA3C 순서), 열 = 경쟁사들 + `삼성`(파란 배경). 경쟁사 칸 = 짧은 사실 + 판정 점(우위 초록 · 비슷 회색 · 열위 주황 · 판정 없음 회색 테두리) + 출처 번호. 삼성 칸 = KB 근거 문장. 모르는 값 `[확인 필요]` · `[00]`.
- **`삼성 강점` 보기**(제안): 강점마다 근거 기준 · 이긴 경쟁사 · 근거 출처(KB 사례 · 스펙 인용), 주의할 점마다 근거 출처.
- **`다시 분석`**: 같은 경쟁사 · 기준으로 분석 다시(`runs{mode:"full"}`) → CA3. 바뀐 입력이 없으면 (제안) 확인 창 없이 수집부터 다시.
- **부분 결과**(분석 중 · 중지): 끝난 경쟁사만 행, 나머지는 (제안) 회색 행 `분석 중` / `분석 안 함`. 큰 버튼은 `stopped` 면 켜지고, 분석 중이면 꺼진다.

### 5.7 주장 · 인용 · 출처

03-mi.md §5.4 와 같다. 종류 표기: 경쟁사 사실은 `web`(`공개 자료 · {제품 페이지|기사|공시·IR|기타}`) · `websearch_summary`((제안) `웹 검색 요약`) · 사용자가 올린 공개 자료 `file`. 삼성 칸은 `kb_official`((제안) `사내 스펙` · `삼성 공식`) · `kb_case`(`사내 사례 DB`). 요약 줄의 `공개 자료` = web + websearch_summary, `사내 사례 DB` = kb_case + kb_official(보드 분류 2가지에 맞춤).

### 5.8 `recheck` (`chk_`) · `handoff` (`hof_`)

- `recheck`: 03-mi.md §5.10 과 같고 변경 종류는 `competitor_new_product` · `source_changed`.
- `handoff`: `target: mi|proposal_why|storyboard|report`, `target_id?`, `target_title?`, `status: prepared|delivered|failed`, `confirmations{real_names?}`, `anonymization_map{cmp: "경쟁사 A"}`, `served_named_at[]`(실명 응답 감사, §6.11), `created_at`. CA0 `보낸 곳` 의 근거.

### 5.9 workspace 색인

`PUT /api/workspace/v1/items/{ca_id}` — `feature: "CA"`, `title`, `status`(`완료` · `확인 중` · `업데이트 필요`), `summary: "{업종 short} · 경쟁사 {n}곳 · 출처 {m}"`(**실명 금지**), `route`(§3.4 표 이동 화면, 사용자가 마지막에 머문 화면 우선), `project_id`.

| `source` | `{feature: "CA", ref_id: ca_id, version, title, updated_at, route}` |
| `customer` · `rq_ref` | 고객사 칸 값 · 업종 코드 / 정의서에서 시작했으면 그 정의서 · 버전 |
| `items[]` | `CM` 경쟁 비교 1개(`content = {criteria[], columns["경쟁사 A", …, "삼성"], cells[][], verdict_marks[][], confidence: {경쟁사 A: 0.91, …}}`) + `ST` 삼성 강점 1개(`content = {strengths[{title, note, criterion_names[]}]}`). `status` = 확인 안 된 칸이 있으면 `warn` `[확정 필요] {n}건`, 없으면 `ok` `그대로 들어가요`. `sources` = 각주(수집에 성공한 URL 만) |
| `facts[]` | 칸 · 강점 문장 속 수치마다 03-mi.md §6.14 와 같은 상태 매핑(`confirmed` · `unconfirmed` · `placeholder`) |
| 넣지 않는 것 | 주의할 점(`cautions`, 내부용) · 실명 · 별칭(`named=true` 예외) · 로고 · 제품 사진 · 사용자가 끈 경쟁사 |

- **`handoff_id`**: 03-mi.md §6.14 와 같다(웹이 proposal `imports.source.handoff_id` 로 넘김, 없으면 안전 기본값 = 익명).
- **`named=true`**(C3): 넘김 기록의 `confirmations.real_names=true`(CA5 묻기 2 에서 `실명으로 보내기`)일 때만 실명을 내고, 응답마다 `served_named_at` 에 기록한다. proposal 은 실명을 저장하지 않는다(10-proposal.md).
- **`auto_run`**(C2 · 제안서 딸깍, 경쟁사 작업이 없을 때): 찾기 → 분석을 사람 확인 없이 잇는다. 묻기 1 은 건너뛰기와 같게(`업종 기준` 칩), CA2 확인은 생략하고 `추천`(신뢰 ≥ 0.70)만 켜서 분석한다. 결과에 칩 (제안) `후보 자동 확정` 을 남기고, 사용자가 나중에 CA2 에서 바꾸면 그 변경은 고정된다(§3.3 단계 3). `추천` 이 0곳이면 `확인 필요` 상위 2곳을 켜고 같은 칩을 단다(제안).

## 7. 워크플로 (LangGraph)

### 7.1 공통

03-mi.md §7.1 과 같다. 차이만 적는다.

- 큐 `wm:q:competitor`, 잡 종류 `ca.find` · `ca.analyze` · `ca.research` · `ca.candidate_add` · `ca.export` · `ca.recheck`. 체크포인트 `${DATA_DIR}/competitor/checkpoints.sqlite`, `thread_id = job_id`. 사람 확인(interrupt)은 `ca.find` 의 `ask_slots` 한 곳뿐.
- **query_guard**: 경쟁사 이름 · 고객사 이름 · 업종 · 지역 · 제품군은 검색어에 써도 된다. 정의서 · RFP · 회의록 원문 문장(20자 이상 그대로), 예산 · 일정 같은 고객 계획 값은 쓰지 않는다.
- **예산**: 찾기 — 웹 검색 ≤ 8회 · 수집 ≤ 12페이지 · LLM ≤ 10회. 분석 — 경쟁사마다 웹 검색 ≤ 5회(사실 항목마다 1) · 수집 ≤ 6페이지 · LLM ≤ 4회. 동시에 2곳(제안).
- **웹 검색 모드**(`sources` / `summary_only`)와 URL 확보 · 수집 규칙은 03-mi.md §7.1 · §7.5 표와 같다. 특히 **LLM 이 짐작한 경쟁사 공식 사이트 URL 은 수집에 성공했을 때만 출처가 되고, 실패하면 어디에도 보이지 않는다.**
- **자기 회사 · 고객 제외**: 후보에서 삼성전자 · 계열사 목록(설정 `self_entities`)과 이 작업의 고객사 자신은 뺀다.

### 7.2 네 칸 읽기 (`/v1/parse` · find `extract_slots`)

1. LLM `ca.extract_slots`(confidential): `{customer: {value, confidence}, place: {value, kind: region|site|scale}, product: {value, categories: [], specific: bool}, industry_hint, competitor_mentions: [], eval_criteria: []}`.
2. KB: A1(문장 → 카테고리 · 제품군 · 공간 · 업종 별칭), 업종 판별 `POST /api/kb/v1/segments/classify`(03-mi.md §7.3 의 kb 근거) + LLM 근거 → 확신도.
3. 칸 판정: `found` = 값이 있고 신뢰 ≥ 0.6(제안) / `partial` = 값은 있으나 제품이 카테고리만 읽힘(`specific=false`) 또는 업종 1 · 2위 차이 < 0.10 / `empty` = 없음.
4. 정의서(CA1R)면 §4.10 `정의서 → 4칸` 규칙(`origin=definition`). 스냅숏의 `context` 가 비어 있는 칸만 1~2 로 읽는다.

### 7.3 `ca_find` (잡 `ca.find`)

```
read_input → extract_slots → classify_segment → check_slots ─(묻기 1)→ ask_slots ⏸ ─┐
                                                              └────────────────────────┤
     ┌──────────────────────────────────────────────────────────────────────────────────┘
     ▼
  fill_gaps → Send×신호 gather_candidates(industry · product · place · customer · explicit) → resolve_entities
  → score → select → make_criteria → title → save
```

| 노드 | 작업 줄 | 하는 일 |
|---|---|---|
| `read_input` | 1 | 글 · 첨부(files 추출, RFP 의 경쟁사 언급 · 평가 기준) · 정의서 · MI 묶음 읽기 |
| `extract_slots` · `classify_segment` | 1 | §7.2 |
| `check_slots` | 1 | §3.3 평가 순서 ③ 묻기 1 판정 |
| `ask_slots` ⏸ | — | `awaiting_input{kind:"slots"}`. 답 → 칸 채우고 `classify_segment` 다시, `skip` → 칩 `업종 기준`(업종 두 갈래면 + `업종 확인`) |
| `fill_gaps` | 1 | `장소만 없음` → 칩 `지역 미반영`(전국 기준) / `제품 없음` → 업종 사례 상위 제품군(kb insights · D2)으로 제품 칸 `inferred` / `고객사만 있음` → 고객사 공개 자료 검색으로 업종 · 장소 추정 + 칩 / `업종 · 제품만 있음`(묻지 않은 경우) → 칩 `업종 기준` |
| `gather_candidates(industry)` | 2 | KB D2(업종 KR 업종들의 사례가 쓴 제품군 · 카테고리) → 그 제품군 공급사 검색(`{업종} {제품군} 공급 업체` 등) |
| `gather_candidates(product)` | 3 | `{제품} 제조사` · `{제품군} 솔루션 업체 비교` 등 |
| `gather_candidates(place)` | 3 | `{지역} {제품군} 설치 업체` · `{지역} {제품군} 레퍼런스` |
| `gather_candidates(customer)` | 3 | `{고객사} {제품군} 도입` · 공공 고객이면 조달 · 입찰 공고 검색. (사내 지난 제안 · 입찰 DB 는 없음, §11 Q3) |
| `gather_candidates(explicit)` | 3 | RFP 언급 · 덧붙일 내용 `include` · MI 묶음 경쟁사 → 반드시 후보(켜짐 · 고정) |
| `resolve_entities` | 4 | 이름 정규화(`주식회사` · `(주)` · `Co., Ltd.` 제거), 한/영 별칭 합치기(LLM `{groups: [{canonical, aliases[]}]}`), 자기 회사 · 고객 · `exclude` 제외 |
| `score` | 4 | §7.4 신뢰 점수 |
| `select` | 4 | 상태(추천 · 확인 필요 · 제외 제안) · 정렬 · 상한(§10.2) · 글자 · 근거 한 줄(LLM, 근거에 없는 수치 금지) · 사용자 고정값은 그대로 |
| `make_criteria` | 4 | §7.5 |
| `title` · `save` | 4 | 작업 제목, workspace 색인, `status=confirming` |

- **이미 고정된 후보**(사용자가 켜고 끄거나 추가한 것)는 다시 찾을 때 상태 · 켜짐을 바꾸지 않는다. 다시 찾기에서 사라진 자동 후보는 지운다.
- `summary_only` 모드: 후보 이름은 요약문에서 LLM(`ca.candidates_from_text`)이 뽑고, 그 근거는 `websearch_summary` 출처다. 공식 사이트 수집에 성공하면 그 페이지로 유형 · 근거를 보강한다.

### 7.4 후보 신뢰 점수

- 신호 k ∈ {업종, 제품, 장소, 고객사} 마다 강도 `s_k ∈ [0, 1]` 을 LLM(`ca.score_signals`)이 근거 출처 번호와 함께 낸다. 결정 규칙으로 덮는다:
  - 근거 출처가 없으면 `s_k = 0`.
  - 근거가 모두 `websearch_summary` 이면 `s_k ≤ 0.7`.
  - 제품이 일부만 겹치면(예 하드웨어 없이 소프트웨어만) `s_product ≤ 0.6`, `partial=true`, 근거 한 줄에 `(제품 일부 겹침)`.
- 가중치(제안): 업종 0.30 · 제품 0.40 · 장소 0.15 · 고객사 0.15.
- **신뢰** = `round(Σ_{k∈A} w_k·s_k ÷ Σ_{k∈A} w_k, 2)`, A = 입력에 있는 칸(답 · 추정 포함, 업종 · 제품은 늘 포함). 장소 · 고객사가 비면 그 가중치를 빼고 나눈다.
- 근거 칩 = `s_k ≥ 0.5` 인 신호.
- 상태: ≥ 0.70 `추천`(켜짐) · 0.50~0.69 `확인 필요`(꺼짐) · < 0.50 `제외 제안`(꺼짐, 목록에 남김).

### 7.5 비교 기준 자동 구성 — `요구사항 3 + 업종 사례 1 + 기본 2`

1. **요구사항 3**: RFP 평가 기준 → 정의서 요구(가중치 순) → 자유 양식 요구 순으로 LLM 이 비교 기준 이름(≤ 10자, 예 `본사 일괄 배포` · `매장별 가격 차등` · `전기료`)으로 바꿔 최대 3. 중요도 5 · 4 · 4(보드 값).
2. **업종 사례 1**: 업종 insights 요구 유형 상위 중 1~번과 겹치지 않는 것(예 `디자인 조화`), 출처 `업종 사례 {n}건`(n = 그 요구 유형 사례 수), 중요도 3.
3. **기본 2**: `가격대`(중요도 3) · `레퍼런스 · AS`(중요도 2).
4. 요구 기준이 3개가 안 되면 업종 사례 기준으로 채워 합계 6.
5. 추천(CA3C `추천`): 업종 요구 유형 중 아직 없는 상위 2(예 `설치 속도` `업종 사례 12건` · `콘텐츠 제작 지원` `업종 사례 8건`).

### 7.6 `ca_analyze` (잡 `ca.analyze`)

```
load → plan_facts → Send×경쟁사(동시 2) [gather_facts → extract_fact_claims → verify] ─join→
   samsung_side → judge → positioning → strengths_cautions → reconcile → finalize   (on_cancel: save_partial)
```

| 노드 | 하는 일 |
|---|---|
| `load` | 켜진 경쟁사 · 기준 · 이전 버전. 모드별 재사용할 사실 결정(`rejudge` = 사실 모두 재사용 · 수집 0회, `changed_only` · `resume` = 지정 · 미완료 경쟁사만 수집, `full` = 모두 다시 수집) |
| `plan_facts` | 경쟁사 × 사실 5항목 검색어(실명 · 별칭 · 제품군 · 업종 · 지역) |
| `gather_facts(cmp)` | `제품 라인업` → `솔루션` → `레퍼런스` → `가격대` → `최근 동향`(최근 12개월) 순서로 검색 · 수집, 항목마다 `step`(CA3 문장) |
| `extract_fact_claims` | LLM `ca.extract_facts` → 항목별 짧은 사실 + 주장 · 인용. 근거가 없으면 `[확인 필요]`(가격대에 흔함) |
| `verify` | 03-mi.md §7.6 그대로(두 모드 · 충돌 20% · 24개월 · 지어내기 검사) |
| `samsung_side` | 기준마다 KB 로 삼성 칸(03-mi.md §7.7 과 같은 방법: 정규 스펙 키 · E2 메시지 · D1/D3 사례 · KPI · 솔루션 메시지), 삼성 비교 제품은 TopBar 추가 → 요구 A1 → S1 순 |
| `judge` | LLM `ca.verdicts` 기준 × 경쟁사 판정(`samsung_better` · `similar` · `samsung_worse` · `unknown`), 근거가 `[확인 필요]` 인 칸은 `unknown` |
| `positioning` | 경쟁사마다 한 줄(≤ 40자, 사실 안의 표현만) |
| `strengths_cautions` | §7.7 |
| `reconcile` | 지어내기 검사, 출처 번호, 집계(우위 · 비슷 · 열위 · 출처) |
| `finalize` | 새 버전, `status=done`, 30일 재확인 예약(`POST /api/jobs/v1/schedules {service:"competitor", kind:"ca.recheck", ref, run_at: analyzed_at + 30일}`), workspace 색인, 완료 알림 |
| `save_partial` | 취소 시 끝난 경쟁사만 `stopped` 버전 |

**진행률**(제안): `pct = round(90 × 끝난 사실 수 ÷ (경쟁사 수 × 5) + 10 × 마무리 단계 완료)`.

### 7.7 삼성 강점 · 주의할 점

- **강점**: 기준마다 `점수 = 중요도 × (samsung_better 인 경쟁사 수)`, 상위 최대 3. 이름 ≤ 12자(예 `서버 없는 통합 관리`), 한 줄 ≤ 30자(예 `MagicINFO · 별도 서버 없이 전 매장 관리`). 한 줄의 수치 · 사례 규모(예 `800매장 사례`)는 KB 사례 · KPI 인용이 있어야 한다.
- **주의할 점**: `samsung_worse` 인 (경쟁사, 기준) 쌍을 중요도 순으로 상위 최대 2. 이름 = `경쟁사 {글자}`, 한 줄 = `{그 경쟁사 강점} · {우리에게 미치는 영향}`(예 `소프트웨어 단가 · 하드웨어 없이 가격만 비교되면 불리해요`). 주의할 점은 내부용 — 고객 제출 묶음에 넣지 않는다.

### 7.8 `ca_research` · `ca_candidate_add` · `ca_recheck` · `ca_export`

| 잡 | 노드 요지 |
|---|---|
| `ca.research` | 한 경쟁사의 지정 사실(없으면 `[확인 필요]` 항목 우선)을 다른 검색어(영문 · 공식 사이트 · 보도자료)로 다시 모음 → 검증 → 판정 · 강점 · 주의할 점 다시 → 새 버전(`kind=research`) |

### 9.2 수용 기준 (Given / When / Then)

**넣기 · 읽기**

1. **AC-CA-01** Given CA1 글 `A 커피 프랜차이즈가 전국 320개 매장의 메뉴보드를 디지털로 바꾸려고 해요. 수도권 직영점부터 시작하고, 55인치 사이니지와 본사에서 콘텐츠를 일괄 배포하는 솔루션이 필요해요.`, 읽기 목 4칸 / When 600ms 뒤 / Then 칩 `고객사 · A 커피 프랜차이즈` · `업종 · 외식 · 카페` · `장소 · 수도권 직영점` · `제품 · 55" 사이니지 + 배포 솔루션`(초록), `4 / 4`.

**찾기 · 라우팅**

## 10. 규칙 · 임계값

모두 competitor 서비스 설정(`services/competitor/config/*.yaml`)에 둔다. 보드 숫자는 그대로, (제안)은 이 문서의 기본값.

### 10.1 후보 선정

| 규칙 | 값 |
|---|---|
| 추천 · 켜 둠 | 신뢰 **≥ 0.70** |
| 확인 필요 · 꺼 둠 | **0.50 ~ 0.69** |
| 제외 제안 · 목록엔 남김 | **< 0.50** |
| 유저가 넣거나 뺀 곳 | 재분석해도 유지(고정) |
| 한 화면 | 후보 **6곳**, 7곳 이상이면 상위 6 + `더 보기`(CAR 문구 `후보 7곳 넘음`, §11 Q2) |
| 신뢰 식 (제안) | 업종 0.30 · 제품 0.40 · 장소 0.15 · 고객사 0.15, 입력에 있는 칸만으로 나눔, 소수 둘째 자리 |
| 강도 상한 (제안) | 근거가 웹 검색 요약뿐 0.7 · 제품 일부 겹침 0.6 · 근거 없음 0 |
| 근거 칩 (제안) | 신호 강도 ≥ 0.5 |
| 신뢰 표시 | 소수 둘째 자리(`0.91`) |

### 10.2 찾는 순서 · 후보 수

| 신호 | 후보 | 꼬리표 | 후보 폭 | 상한(구현, 제안) |
|---|---|---|---|---|
| 업종만 | **8~12** | 넓음 | 100% | 추천 + 확인 필요 ≤ 12 |
| + 제품 | **5~8** | 좁힘 | 65% | ≤ 8 |
| + 장소 | **4~6** | 지역 반영 | 42% | ≤ 6 |
| + 고객사 | **3~5** | 가장 정확 | 28% | ≤ 5 |

`제외 제안` 은 상한 밖으로 최대 3곳 더(제안 — A 커피 `후보 6 · 추천 4` = 추천 4 + 확인 필요 1 + 제외 제안 1). 하한보다 적게 찾아도 채우려고 지어내지 않는다.

### 10.3 빈 정보 · 묻기

| 규칙 | 값 |
|---|---|
| 묻기 1(CA2Q) | 고객사 · 장소 **둘 다 없음** 그리고(기본) 업종 1 · 2위 차이 **< 0.10** — 설정 `CA_ASK_SLOTS_REQUIRE_AMBIGUOUS_INDUSTRY=true` |
| 장소만 없음 | 전국 기준 · `지역 미반영` 칩 |
| 제품 없음 | 업종 사례 상위 제품군 |
| 업종 못 읽음 | MI 업종 판별 규칙 재사용(03-mi.md §7.3 · §10.1) |
| 고객사만 있음 | 공개 자료에서 업종 · 장소 추정 · 칩 |
| 업종 · 제품만 있음(묻지 않음) | `업종 기준` 칩 |
| 묻기 2 | 경쟁사 실명을 고객 제출물에 넣을 때(CA5) |
| 답이 없으면 | 업종 기준 · 익명 표기 |
| 칸 `found` (제안) | 값 있음 · 신뢰 ≥ 0.6 |

### 10.4 기준 · 분석

| 규칙 | 값 |
|---|---|
| 비교 기준 자동 | 요구사항 **3** + 업종 사례 **1** + 기본 **2**(`가격대` · `레퍼런스 · AS`) = **6** |
| 기본 중요도 (보드 값) | 요구 5 · 4 · 4, 업종 사례 3, `가격대` 3, `레퍼런스 · AS` 2, 직접 추가 3 (제안) |
| 중요도 | **1~5** |
| 추천 기준 | 최대 **2** |
| 경쟁사 수치 못 찾음 | `[확인 필요]` · 추정 금지 |
| 출처끼리 차이 | **≥ 20%** → 둘 다 표시(확인 권장), 식은 03-mi.md §10.6 |
| 오래된 출처 | 24개월(03-mi.md §10.6 과 같음) |
| 사실 항목 | 제품 라인업 · 가격대 · 솔루션 · 레퍼런스 · 최근 동향(최근 동향은 최근 **12개월**, 제안) |
| 강점 · 주의할 점 | 최대 **3** · 최대 **2** |
| 포지셔닝 한 줄 | ≤ 40자 (제안) |

### 10.5 시간 · 갱신

| 항목 | 값 |
|---|---|
| 찾기 | `약 30초` |
| 분석 | `약 2분`(4곳) — 예상 `20 + 25 × 경쟁사 수` 초를 분 단위 반올림 (제안 식) |
| 동시 분석 | 2곳 (제안) |
| 재확인 | 분석 완료 + **30일**, 경쟁사 신제품이면 `업데이트 필요`(업데이트 권유) |
| 진행률 (제안) | `round(90 × 끝난 사실 ÷ (경쟁사 × 5) + 10 × 마무리)` |
| 예산 (제안) | 찾기: 웹 검색 8 · 수집 12 · LLM 10 / 분석: 경쟁사마다 웹 검색 5 · 수집 6 · LLM 4 |

### 10.6 표기

익명 `경쟁사 A · B · C …`(고객 제출물 · 공유 · 목록 · 색인), 작업 화면은 글자 + 실명 보조, 사내용 리포트는 실명. 로고 · 제품 사진은 고객 제출물에 넣지 않는다. 자리표시 `[확인 필요]` · `[00]`.
