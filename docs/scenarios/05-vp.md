# 05. Value Proposition (VP) — 화면 수용 기준

> 대상 보드(webapp1, 14개): `UC_VP` `VP0` `VPR` `VPC` `VP1` `VP2` `VP3` `VP1A` `VP1Q` `VP3G` `VP3L` `VP3N` `VPI` `VP4`
> 원천: `docs/screens/webapp1/<보드>.dc.html`(정본 — 보드 끝 로직 클래스에 예시 데이터·상태), `docs/screens/_text/webapp1/<보드>.txt`(요약, `<` 뒤가 잘려 있어 HTML을 정본으로 씀), canvas 노트 `vpRoute` · `srcRule`(`docs/screens/webapp1/canvas.json`), `docs/screens/webapp1/data/image_sources.json`, 제안서 쪽 레이아웃·업종 코드 `docs/screens/webapp3/SectionStep.dc.html`, `winmate-kb/seed/sheet_roles.yaml`, `winmate-kb/docs/*`, `winmate-kb/build/query.py`, `docs/ARCHITECTURE.md`, `config/services.yaml`
> 이 문서는 vp 서비스(`services/vp/**`)와 웹 모듈(`web/src/features/vp/**`)을 구현하는 코드 에이전트 세션의 수용 기준이다. 애플리케이션 코드는 담지 않는다. 판단 모드·업종 판별기·레이아웃 적합도 표시는 MI와 공유한다(`03-mi.md`).

**표기 규칙**

- `백틱` 안은 보드 문구 그대로다. `{변수}` 부분만 데이터로 바뀐다. 문장부호(`·`, `→`, `—`, `' '`)와 띄어쓰기도 그대로 쓴다.
- **(제안)** = 보드에 없는 문구·동작으로 이 문서가 정한 것. 구현은 따르되 디자인 검토 대상이다(§11).
- 보드의 예시 수치(`0.52`, `94%`, `64%` …)는 예시 데이터다. 규칙·임계값의 원천은 §10이다.
- 모르는 수치는 `[00]`(단위는 남김: `[00]억`, `[0.0]%`, `[0]일` 처럼 보드가 쓴 자릿수 모양도 허용), 모르는 글은 `[확인 필요]`, 추정값은 값 뒤 `[추정]` 표시. 모델이 수치·고객명·문구를 지어내는 것은 금지다(§7.7).
- 레이아웃 코드 표기: 화면에는 `VP-F·3`처럼 가운뎃점, 저장·계약에는 `VP-F3`(가운뎃점 제거)를 정본 코드로 쓴다. 검색은 둘 다 받는다(§4.15).

## 1. 목적과 진입점

### 1.1 목적

고객 과제 → 가치 → 기대 효과로 핵심 메시지를 세우고, 시트마다 레이아웃·이미지 칸·근거 수치를 채워 제안서 'Value Props' 섹션(표준 `PRS2` · 퀵윈 `PRQ1` · Solution형 `PRX2`)으로 보낸다. 홈 카드 문구 `고객 과제 → 가치 → 기대 효과로 핵심 메시지를 세워요.` · 결과가 들어가는 곳 `제안서 Value Props 섹션`.

원칙(보드·노트 `vpRoute`):

1. 구조와 레이아웃은 에이전트가 스스로 고르고, 사람에게는 다섯 경우만 묻는다(VPR `구조와 레이아웃은 스스로 고르고, 다섯 경우만 묻습니다`).
2. 판단 모드 4종(자동 · 확인 권장 · 선택 필요 · 고정)을 MI와 공유한다.
3. 한 화면에 한 가지 — 가운데 800px 한 줄 + 아래 입력 도크(제목 · 단계 · 빠른 칩 · 입력창 · 보조 버튼 · 큰 버튼 하나).
4. 이미지 칸은 공식 실사 우선, 모든 이미지에 출처 메타데이터(`srcRule`).
5. 범용 35종으로 만들고, 업종판(16 업종 × 3장)이 나오면 작업마다 바꿀지 묻는다.
6. 같은 결과도 보낼 제안서 유형에 따라 시트 수가 달라진다: 표준 3장 · 퀵윈 1장(VP-G) · Solution형 고객 과제 생략.

## 3. 사용자 흐름

### 3.1 기본 흐름

```
 E1/E2/E8 ─→ VP1 ──[가치 구조 만들기]──→ materials 잡 ─┬─(fixes 있음)────────→ VP1A ──[가치 구조로]──┐
 E3/E6/E7 ─→ (소스 연결 + materials 잡 자동 시작) ──────┤                                            │
                                                       ├─(묻는 질문 있음)────→ VP1Q ──[이대로 진행]───┤
                                                       └─(없음)────────────────────────────────────→ VP2
                                                                                                     │
                                                                              [3장 만들기 (약 1분)]   ▼
                       VP4 ←[제안서 Value Props로]── VP3 ←──(끝나면 자동)── VP3G (generate 잡 · 5단계)
                        │                              │  ⇄ VP3L(레이아웃) ⇄ VP3N(수치) ⇄ VPI(이미지)
                        └─[제안서에 3시트 보내기]──→ 넘김 생성 → 제안서 PRS2 · PRQ1 · PRX2 (proposal이 당겨 감)
```

- VP1A 와 VP1Q 가 둘 다 필요하면 VP1A(재료 확인, 단계 1) → VP1Q(되묻기, 단계 2) → VP2 순서다. VP1A의 `가치 구조로`는 열린 `선택 필요` 질문이 있으면 VP1Q로 보낸다.
- VP2 에서 `3장 만들기`를 누르기 전까지 생성은 없다. VP2의 구조는 결정적 계산(§7.3)이라 대안 칩을 누르면 즉시 바뀐다.
- 생성이 끝나면 VP3G 에서 VP3 로 자동 이동한다. 화면을 떠나도 잡은 계속되고 끝나면 완료 알림(jobs)이 간다(`이 화면을 떠나도 계속 진행되고, 끝나면 알려 드립니다.`).

### 3.2 갈래

| 갈래 | 경로 | 조건 · 비고 |

### 3.3 라우팅 규칙 (VPR 원문 · 판단 모드)

판단 모드 4가지(MI와 같음). 화면의 모드 칩 문구는 그대로 쓴다.

| 모드 | 칩 | 뜻(범례) | 칩 모양(보드) | 동작 |
|---|---|---|---|---|
| `auto` | `자동` | `진행` | 연한 파랑 바탕 `#eaeefb` · 파랑 글자 · 번개 아이콘 | 에이전트가 정하고 진행, 결정 기록에 이유 한 줄 |
| `check` | `확인 권장` | `진행 + 결과에 표시` | 흰 바탕 · 파랑 테두리 · `!` 아이콘 | 진행하되 결과(VP3 `확인할 것`, 카드 칩)에 남김 |
| `ask` | `선택 필요` | `답 받고 진행` | 검정 바탕 · 흰 글자 · `?` 아이콘 | 답을 받아야 진행(추천값이 미리 골라져 있음) |
| `pin` | `고정` | `사람이 정함` | 회색 `#f0f2f5` · 핀 아이콘 · 칩 글자 `{코드} 고정` | 사람이 정한 값은 다시 고르지 않음 |

**단계 1 · 재료 판별** — `과제 · 가치 · 근거 · 이해관계자 · 제품 5축으로`

| 신호 | 결정 | 모드 |
|---|---|---|
| `Storyboard 연결` | `Key Message → 가치 축 · 요구 → 과제 축` | 자동 |
| `MI 결과 연결` | `과제 · 사용자 · 삼성 강점 · 수치` | 자동 |
| `RFP 첨부` | `평가 기준 · 배점 · 결재 구조` | 자동 |
| `유관 사례 · 견적 연결` | `전 → 후 수치 · 제안 제품 → 공식 실사` | 자동 |
| `한 줄 메모뿐` | `사례 DB로 과제 추론 · 추론 표시` | 확인 권장 |

**단계 2 · 업종 · 업종판** — `MI와 같은 판별기 · Value Props 업종판 준비 여부`

| 신호 | 결정 | 모드 |
|---|---|---|
| `연결한 MI · Storyboard에 업종` | `그대로 상속` | 자동 |
| `연결된 업종이 없음` | `MI와 같은 기준으로 판별` | 자동 |
| `1 · 2위 차이 0.10 미만` | `한 번 묻기 (업종 칩)` | 선택 필요 |
| `업종판 준비됨` | `VP-XX-A · B · C를 먼저` | 자동 |
| `업종판 제작 중` | `범용으로 · 출시 때 교체 제안` | 자동 |

평가 순서(MI와 같은 판별기, `03-mi.md` §3.3 단계 2): ① 사람이 정한 업종(VP1 `바꾸기`) → `pin` ② 연결한 MI · Storyboard · 제안서 · 정의서에 업종이 있으면 상속 → `auto` ③ 확신도 1위 < 0.50 → 범용 `auto` ④ 1위 − 2위 < 0.10 → `ask`(업종 칩 질문, VP1Q 카드) ⑤ 1위 ≥ 0.80 → `auto` ⑥ 0.50 ≤ 1위 < 0.80 → `check`. 16개 업종 밖이면 범용.

**단계 3 · 메시지 구조** — `누구에게 · 무엇을 먼저 말하나`

| 신호 | 결정 | 모드 |
|---|---|---|
| `고객이 과제를 직접 말함 (RFP · 회의록)` | `과제 → 가치 → 효과` | 자동 |
| `결재자 1명 · 짧게 · 퀵윈` | `한 문장 + 제품 사진 (VP-G)` | 자동 |
| `의사결정자 3명 이상 · KPI가 다름` | `이해관계자 + 쓰는 제품 (VP-H)` | 자동 |
| `평가 기준에 경제성 배점` | `기대 효과를 투자 회수로 (EF-B)` | 자동 |
| `방향 두 갈래 · 점수 차 0.10 미만` | `한 번 묻기 · 답 없으면 둘 다` | 선택 필요 |

**단계 4 · 시트 수** — `보낼 제안서 유형에 맞춰`

| 신호 | 결정 | 모드 |
|---|---|---|
| `표준 제안서 연결` | `고객 과제 + 가치 제안 (+ 기대 효과)` | 자동 |
| `퀵윈 제안서 연결` | `가치 제안 1장 (VP-G)` | 자동 |
| `Solution형 연결` | `고객 과제 생략 — 대규모 MI가 말함` | 자동 |
| `연결 없음` | `3장 기본 · 보낼 때 줄이기` | 자동 |
| `제안서에 이미 고정한 시트` | `건드리지 않고 나머지만` | 고정 |

추가 규칙(VPC 7번에서 도출): 과제 축 재료가 0개면(Key Message만 있음) 고객 과제 시트를 만들지 않는다 — 결정 기록 **(제안)** `과제 재료 없음 → 고객 과제 시트 생략`.

**단계 5 · 레이아웃 선택 — 시트마다** — `고정한 시트는 건너뜀 → 업종판 → 재료 모양 → 메시지 · 이미지 칸은 공식 실사 → 일러스트 순 · 고른 이유를 시트에 한 줄로`. 시트별 선택표는 §3.5, 카탈로그는 §4.15.

**단계 6 · 결측 · 충돌 처리** — `스스로 메우는 순서 · 고객 자료 → 유관 사례 → 업종 평균 범위 → 고객에게 요청`

|---|---|---|
| `근거 수치 [00]이 비어 있음` | `사례 검색 → 업종 평균 범위 [추정] → 요청 초안` | 자동 |
| `EF-A에 쓸 수치가 3개 미만` | `EF-C(정량 + 정성)로 자동 전환` | 자동 |
| `투자 회수가 필요한데 투자비가 없음` | `견적 연결 요청 · 없으면 EF-A로` | 확인 권장 |

### 3.4 사람에게 묻는 다섯 경우

`사람에게 묻는 경우는 이 다섯뿐`

| # | 문구 | 모드 | 언제 · 어디서 | 답이 없을 때 |
|---|---|---|---|---|
| 1 | `메시지 방향이 두 갈래 — 비용 vs 매출, 점수 차 0.10 미만` | 선택 필요 | materials 잡 → VP1Q 질문 카드 | `③ 둘 다`(추천) |
| 2 | `결재자를 모르고 RFP도 없을 때 (기본값을 두고 확인 권장)` | 확인 권장 | materials 잡 → VP1Q 질문 카드 | 업종 기본값(VP1Q 예: `운영본부장`) |
| 3 | `투자 회수에 쓸 투자비(견적)가 없을 때` | 확인 권장 | 구조 결정(VP2 대안 `EF-B`, generate 잡) | EF-A로(§3.3 단계 6) |
| 4 | `고객 내부 인터뷰 수치를 고객 제출물에 쓸 때` | 선택 필요 | 넘길 때 · 내보낼 때(VP4) — 보낼 시트에 출처 `고객 인터뷰` 수치가 있으면 | 그 수치를 `[00]`으로 바꾸고 노트 `[확인 필요]` **(제안)** |
| 5 | `Storyboard Key Message와 MI 과제가 부딪칠 때` | 선택 필요 | materials 잡 reconcile 노드 → VP1Q 질문 카드(`Storyboard 기준` · `MI 기준` · `둘 다 살려 고쳐 쓰기`) **(제안 선택지)** | 둘 다 살려 고쳐 쓰기 |

- 업종 두 갈래(단계 2 ④)도 같은 VP1Q 카드로 묻는다(MI 판별기 규칙, VPR 다섯 경우에는 세지 않음).
- "답이 없으면"의 뜻: 사용자가 묻는 화면에서 바꾸지 않고 CTA(`이대로 진행`)를 누르거나, 작업이 `auto_answer=true`(제안서 딸깍 · 일괄 생성)로 실행될 때 추천값을 쓴다. 시간 경과로 자동 진행하지 않는다 **(제안, §11 Q5)**. VP0 바닥글 `답이 없는 질문은 추천값으로 진행돼요`.
- 추천값으로 정한 결정은 모드 `확인 권장`으로 기록하고 VP3 `확인할 것`에 남긴다.

### 3.6 작업 상태

```
draft ──materials──→ collecting ──┬→ ask(VP1Q 미응답) ──answer──┐
                                  └→ planned ───────────────────┤
                                                                ▼
                     (3장 만들기) generating ─┬→ done ──(레이아웃 요청 · 업종판 교체 제안 대기)──→ check
                                             ├→ stopped(중지 · 끝난 시트 보존) → draft(step 2)
                                             └→ failed ──다시 시도──→ generating
          done · check ──(수치 ask · 후속 요청)──→ ask / generating(revise) ──→ done
```

| 내부 상태 | VP0 상태 칩 · 문구 | 칩 모양 | 행 동작 | `resume_route` |
|---|---|---|---|---|
| `draft`, `planned`, `stopped` | `작성 중 {step}/3` | 흰 바탕 · 점선 테두리 | `이어서` | 마지막 화면(VP1 · VP1A · VP2) |
| `collecting`, `generating`(잡 실행) | `생성 중 {pct}%` | 연한 파랑 | `진행 보기` | VP3G |
| `ask` | `방향 선택 {n}` · `수치 선택 {n}` · `업종 선택 {n}` · `결재자 확인 {n}` **(제안: 질문 종류별)** | 검정 | `답하기`(파랑 채움) | VP1Q · VP3N |
| `check` | `레이아웃 요청 {n}` · `업종판 교체 {n}` **(제안)** | 흰 바탕 · 파랑 테두리 | `확인` | VP3L · VP3 |
| `done` | `완료` / `완료 · 추정 {n}` | 회색 | `열기` | VP3 |
| `failed` | **(제안)** `작성 중` + `만들기를 마치지 못했어요` | 점선 | **(제안)** `다시 시도` | VP3G |

- 상태 우선순위: 실행 중 잡 > 미응답 `선택 필요` > 대기 중 제안(`확인 권장`) > 작성 중 > 완료.
- VP0 `답을 기다리는 작업 {n}건` = `ask` + `check` 수(보드 로직 `waiting = count('ask') + count('check')`).
- 상태가 바뀔 때마다 workspace 색인을 갱신한다(§6.1 공통).

### 4.7 VP1Q — 되묻기 (`/vp/:id/questions`)

사용자 말풍선: `{작업 고객/주제}` `· {연결 요약}`(예 `N 체인 무인 매장` `· Storyboard · MI 연결 · RFP 없음`). 에이전트: `두 가지만 확인할게요. 나머지 6개는 정한 대로 진행합니다.` — 수는 데이터(**제안** `{q}가지만 확인할게요. 나머지 {a}개는 정한 대로 진행합니다.`; q=1 `한 가지만`).

**질문 1 · 방향(선택 필요)** — `1 · 이번 제안의 첫 메시지는?` · 오른쪽 `매출 {s1} : 비용 {s2} · 차이 0.10 미만` · 설명 `Storyboard는 '매출'(객단가 · 24시간 판매)을, MI는 '인건비'(점원 없는 운영)를 가장 큰 과제로 봐요.`(LLM 요약, 원문 근거에서만) · 선택지 3(라디오):

| 키 | 제목 | 첫 메시지(설명) | 썸네일 | 코드 | 이렇게 바뀌어요 | 추천 |
|---|---|---|---|---|---|---|
| ① | `① 매출 먼저` | `'24시간 매장의 객단가를 올립니다' — 판매 화면 · 추천 상품` | cards3img·3 | `VP-F·3` | `매출 기둥 2 + 운영 기둥 1` | |
| ② | `② 비용 먼저` | `'점원 없이도 돌아가는 운영비' — 원격 관리 · 무인 결제` | chain·3 | `CH-A + VP-E` | `과제 3 ↔ 제품 3으로 짝지어요` | |
| ③ | `③ 둘 다` | `매출과 비용을 나란히 — 경영진이 둘 다 볼 수 있게` | cards3img·2 | `VP-F·2` | `기둥 2개 · 기대 효과 EF-C` | `추천` |

**질문 2 · 결재자(확인 권장)** — `2 · 누가 결재하나요?` · 오른쪽 `RFP가 없어 생활 편의 사례 기준으로 기본값을 뒀어요`(업종 이름은 데이터) · 체크 칩(복수): 보드 `대표` `운영본부장`(기본 선택) `재무` `가맹점주 협의회` · 오른쪽 `2명 이상이면 VP-H 이해관계자형으로`. 칩 목록 출처: RFP 결재 구조 → Storyboard 청중 → 업종 기본 목록(설정 `approver_defaults.{업종}`) 순 **(제안)**.

### 4.12 VP3N — 수치 보강 (결측 처리) (`/vp/:id/result/numbers?sheet=`)

#### 4.15.5 적합도(VP3L · MI3L 공통 표시)

원칙(MI3L 문구 `필요한 데이터가 있는지로 적합도를 매겨요`): 레이아웃마다 `needs[]`(데이터 모양 요구, 가중치)를 두고 `fit = round(100 × Σ wᵢ·sᵢ / Σ wᵢ)`, sᵢ ∈ [0, 1](개수 요구는 비율로 부분 점수, 짝 맞춤 같은 엄격 요구는 0/1) — LLM 없음. 업종판 `in_production` 은 `fit=-1`(`준비 중`, 고를 수 없음). 강조 임계 85. needs 가중치 초기값은 설정 파일 **(제안)** 이고 보드 예시 숫자를 맞추도록 튜닝한다(§11 Q9). 이유 문장은 충족 · 미충족 needs 에서 만든다(예 `과제 4 · 제품 3 — 짝이 안 맞음`).

### 4.16 이미지 칸 채우기 규칙

노트 `vpRoute`: `이미지 칸은 제안 제품에서 시작 → ① 고객 현장 사진(공간 칸만) ② 삼성 공식 제품 컷 ③ 공식 설치 사례 ④ 솔루션 실제 화면 ⑤ 없으면 일러스트(Prod)`. VPI 출처 5단계 순서: `고객 현장 사진` → `공식 제품 컷` → `설치 사례` → `솔루션 화면` → `일러스트`.

1. **칸의 대상(subject)**: 기둥 · 이해관계자 · 과제마다 "그 가치를 만드는 제품 · 솔루션"(재료의 product_refs, KB 해소된 `family`/`model`/`solution`). 과제 칸 · 공간 칸은 대상이 공간이다.
2. **단계 적용표**(위에서부터 첫 번째로 있는 것):

| 대상 | ① 고객 현장 사진 | ② 공식 제품 컷 | ③ 설치 사례 | ④ 솔루션 화면 | ⑤ 일러스트 |
|---|---|---|---|---|---|
| 제품(모델 · 제품군) | — | `KB:G4(family_id)` (PDP 갤러리, 등급 C) — 정확 모델 > 같은 계열(시리즈) > 유사 모델(`유사 모델` 표시, 확인 권장) | `KB:G2('family'\|'category', id)` 사례 사진 우선(등급 A) | — | ai-tools T2I(`Prod` 톤) |
| 솔루션 | — | — | `KB:G2('solution', id)` 사례 사진 | `KB:G2('solution', id)` 등급 D(도식 · UI) · 솔루션 페이지 이미지 → `"실제 데이터 아님"` 표시 | T2I |
| 공간(과제 · 공간 칸) | 첨부한 고객 사진(i2t 공간 분류 일치) — `고객 확인 전 외부 사용 불가` | — | `KB:G1(space, category, vertical)` 등급 A (폴백 `fallback_level` 기록) | — | T2I + 사진 요청 초안 |
| 추가 제안(VP-Q · VP-N) | — | — | `KB:D1(vertical, spaces, targets)` → `KB:G5(deployment_id)` 같은 업종 사례 사진 | — | — |

3. **모드**: 정확 모델 · 공식 화면 = 자동. 설치 사례(다른 고객사 브랜드 노출) = 확인 권장 `외부 제출 전 인용 확인`. 같은 계열 · 유사 모델 = 확인 권장. 일러스트 = 확인 권장(사진 요청 초안 준비, 받으면 자동 교체). 고객 사진 = 확인 권장.
4. **표시 · 캡션 규칙**: 솔루션 화면은 `"실제 데이터 아님"` 표시. 도입사례 사진은 `“도입사례 사진” 표기 필수`, 캡션 `도입사례 사진`. 공식 제품 · 솔루션 이미지는 `예시 사진(삼성 공식 이미지)`. T2I 생성물은 `생성 이미지`(권리 `generated`, T6). 고객 사진은 **(제안)** `고객 제공 사진`.
5. **맞춤**: 제품 컷 · 솔루션 화면 일부 = `contain`, 사진 · 화면 = `cover`(VPI 예: qm55c · stpEnergy contain).
6. **메타데이터(srcRule — 모든 이미지 필수)**: `모든 이미지에 출처 페이지 · 원본 파일 URL · 원본 해상도/형식/용량 · 저장본 · 수집일 · 사용 조건 · 사용 이력을 붙인다`. 필드는 `image_sources.json` 과 같다(§5.2 `ImageMeta`). 원본 URL · 출처 페이지가 없는 자산(생성 · 고객 사진)은 그 사실을 값으로 남긴다(`생성 이미지 · {모델} · {날짜}` / `고객 업로드 · {파일명}`).
7. **사용 이력**: 넘김 · 내보내기에 들어간 자산은 사용 이력 +1(`Winmate 제안서 {n}건`) — kb I3 계약이 없으면 vp 가 자체 기록 **(제안)**.
8. **추가 제안 칸**: 같은 업종 사례 사진이 있으면 `추가 제안 · VP-Q` `같은 문제를 먼저 푼 곳` 칸을 1개 낸다(확인 권장). 보낼 때 기본 미포함 **(제안)**.

### 4.17 수치 채우기 규칙 (`[00]` · `[추정]` · 확정 필요)

1. **지어내지 않는다**: 시트 문장 속 모든 수치는 재료 · KB 결과 · 사용자 입력에 있는 수치를 id 로 참조해서만 들어간다(§7.7 검증). 없으면 `[00]` 자리표시(단위 유지).
2. **찾는 순서**(VP3N 머리 · VPR 6): `고객 자료 → 유관 사례 → 업종 평균 → 고객에게 요청`.
   - 고객 자료: RFP · 정의서(RQ) · Storyboard · 고객 인터뷰 메모 · 견적 → `확보`.
   - 유관 사례: `KB:D1` 상위 사례 → `KB:D3(deployment_ids)` KPI 문장 → LLM `vp.kpi_metric_extract.v1` 로 지표 대응 · 수치 추출(T5) → 2건 이상이면 범위 `[a~b]`, `[추정]` 표시(`사례 2건 범위로 표기`).
   - 업종 평균: 같은 업종 사례(`KB:D2(vertical)` → `KB:D3`) n건의 범위(`{업종} 사례 {n}건 평균 범위 · [추정] 표시`), 없으면 연결한 MI의 업계 수치, 그것도 없으면 ai-tools 요약형 웹 검색(사내 제약 — §11 Q21). 모두 없으면 `업종 평균` 처리는 고를 수 있어도 값은 `[00]` 로 남고 `요청하기` 가 추천이 된다.
   - 고객에게 요청: 요청 초안(§4.12) 생성, 값은 `[00]`, 답을 받으면 사용자가 VP3N 직접 입력으로 반영.
3. **범위 표기**: 근거가 2건 이상이면 단일 값 대신 범위(`절감액 근거 사례 3건 · 단일 값 대신 범위로 표기`).
4. **EF 자동 전환**: 쓸 수 있는 전 → 후 수치(`확보` + `추정`, `빼기` · `요청`(값 없음) 제외) < 3 → EF-C. `EF-B` 는 투자비(견적) 필요, 없으면 확인 권장 + EF-A(→ <3 이면 EF-C).
5. **투자 회수(EF-B) 계산(결정적)**: 투자비 I(견적 총액) · 연간 절감액 범위 [S_low, S_mid, S_high](사례 · 업종 평균) → 회수 기간 `I / (S/12)` 개월을 3개 시나리오로. 결정 기록 `투자 회수 기간 계산 중 — 견적 v2 · 절감액 범위 3개 시나리오`.
6. **출처 기한**: 24개월 지난 출처 수치는 제외하고 최신 자료로 대체(`다시 찾음`), 못 하면 `[확인 필요]` 표시.
7. **고객 내부 인터뷰 수치**: 고객 제출물(넘김 · 내보내기)에 쓰기 전에 묻는다(§3.4 4번).
8. **claim**: KB 메시지 · KPI 의 `claim_flag=1` 문구를 쓰면 확인 권장(`claim(수치·최상급) 문구는 대외 사용 전 원문 확인`).
9. **넘길 때**: 옵션 `[추정] 값은 노트로 남기기` 가 켜지면 추정 수치의 근거(`유관 사례 2건의 범위 …`)를 발표자 노트로.

## 6. API 스케치

모든 경로는 서비스 내부 `/v1/...`(게이트웨이 `/api/vp/v1/...`). ARCHITECTURE §3 규약: ID 형식, ISO 8601 UTC, 오류 `{"error": {"code", "message", "details"}}`, 목록 `?limit=&cursor=` → `{items, next_cursor}`, 오래 걸리는 작업은 `202 {"job_id", "status": "queued"}` 후 SSE · 자원 재조회, 문서형 자원 `version` + `/versions` · `/versions/{n}/restore`, 고객 자료가 든 모델 호출은 `confidential: true`.

**공통 부수효과**: 작업을 만들거나 상태 · 제목 · 단계가 바뀔 때 `PUT /api/workspace/v1/items/{vp_id}` `{feature: 'VP', title, status: ui_status, summary: status_text, route: resume_route, project_id}`.

### 7.3 결정적 계산 모듈

- **`coverage_preview` / `coverage`**: 축별 percent = min(100, round(100 × 가진 수 / 필요 수)) **(제안)** — 과제: 필요 3(시트 과제 수) · 가치: 필요 = 기둥 후보 수(KM 수, 없으면 3) · 근거 수치: 필요 = 플랜이 쓰는 수치 칸 수(과제 영향 + EF 지표 × 2), 가진 = 확보 + 추정 · 이해관계자: 필요 = 3(결재 · 운영 · 이용자), 가진 = 덮은 그룹 수. 수준: ≥ 90 `충분`, ≥ 50 `보통`, < 50 `부족` **(제안 경계)**. 할 일 문장은 축 · 부족 원인별 고정 문구(보드 예시 4개 + **제안** 보완).
- **방향 점수**: `vp.direction_tags.v1` 이 재료마다 테마 관련도(0~1)를 매기면, 테마 점수 = Σ w(출처) × 관련도 / Σ w. 출처 가중치 초기값 RFP 1.0 · 정의서 0.9 · SB KM 0.8 · MI 과제 0.7 · 사례 0.4 · 메모 0.5 **(제안)**. 1 · 2위 차 < 0.10 → 질문 1.
- **`planner(PlannerInput) → Plan`**: §3.5 표. 입력 `PlannerInput = {target_type, pinned_sheets, industry{code, pack_ready}, has_customer_challenges, challenge_count, challenges_with_cost, to_be_clear, repeated_symptom, km_count, approvers_confirmed, decision_makers_inferred{count, distinct_kpi}, economic_points, investment_available, usable_numbers, per_product_numbers, product_count, single_product_feature, solution_screen_focus, space_journey_count, replacement, field_questions, no_image, answers}`. 출력에 결정(stage, key, value, why, mode) 목록 포함.
- **적합도**: §4.15.5. **패키지 맞춤**: §4.14. **EF 전환**: §4.17-4. **투자 회수**: §4.17-5.

### 7.7 결정적 검증(검토 노드)

1. 시트 문장 속 숫자 토큰(`\d`가 든 토큰)마다 참조 id 가 있어야 하고 그 값과 같아야 한다. 없으면 `[00]`(단위 유지)으로 바꾸고 확인할 것(태그 `추정` 아님 — **제안** `요청`)을 남긴다.

## 11. 열린 질문

1. **Thumb 정의 누락**: `Thumb.dc.html` 이 캔버스 목록에만 있고 파일이 없다. VP-I · J · K · L · EF-D · VP-U · U·C · U·S · VP-N~T · EF-E 와 CH-B(`asis`) · CH-C(`tree`) · VP-A(`rows`) · VP-C(`statement`) 의 썸네일 그림을 'Winmate PPT · 02 Value Props' 캔버스에서 내보내야 한다.
2. **업종판 역할 대응 충돌**: VPC 12번(CH→A · VP→B · EF→C) vs VPR 밴드(VP 가치 제안 → `A · B`, 제품 · 장면 → `B 장면판`) vs SectionStep `IND_FOR`(CH→A · VP→A · EF→C) vs 노트(`B 이해관계자`). 기본값은 VPC 12번으로 두고 설정으로 바꿀 수 있게 했다. 확정 필요.
3. **VP-H 임계**: VPR `의사결정자 3명 이상 · KPI가 다름` vs VP1Q `2명 이상이면 VP-H`. "추론 3명 이상 / 사용자 확인 2명 이상"으로 나눴다. 맞는지 확인.
4. **VP3N 전환 문장 모순**: 보드 상태(확보 2 + 추정 1 = 3)에서 `'오출고율'을 빼면 EF-C로 바뀌어요` 는 성립하지 않는다(빼도 3). 계산으로만 문장을 내기로 했다.
5. **"답이 없으면" 시점**: 시간 경과 자동 진행이 필요한가? 지금은 CTA(추천값) · `auto_answer` 로만 진행.

8. **방향 점수 가중치**: 출처 가중치 초기값(제안) 확인.
9. **적합도 계산**: VPR 에 적합도 설명 절이 없다(VP3L `적합도 매기는 법` 링크 대상 부재). 레이아웃별 needs · 가중치와 `sheet_roles.yaml` 의 `<<FILL>>`(VP-E 이미지 수, VP-I features_min) 확정 필요.

11. **인터뷰 수치 질문(묻는 경우 4) UI**: 보드에 없다. VP4 모달로 정했다.
12. **작업 고르기 대화상자**: VP0 `Storyboard에서` · `MI 결과에서` · `이전 가치 제안 복제` 의 원본 고르기 화면이 보드에 없다.
13. **제안서 넘김 계약**: proposal 이 handoff 를 당겨 가는 방식과 PRS2 SectionStep 기본값(이미지 없는 VP-B · CH-B)이 VP 결과 레이아웃을 받는 방식 합의 필요.
